# LEDGER — the over-arching list (every arch, every shared seam)

> Peter's rule (2026-09-05): **each track keeps its arch ledger, and there is ONE over-arching
> ledger for what crosses arches.** Audits and inventories are high value; the waste is trashing
> their results and re-deriving them. So: every finding lands on exactly one list the turn it is
> found; the arc that closes it ticks it in the same commit; every audit is briefed with the list and
> reports only what is new or changed.
>
> Arch ledgers: `docs/dev/OS/orin-ledger.md` · `docs/dev/OS/pi-ledger.md` · `docs/dev/OS/rmbp-ledger.md`
> (the latter two: to be created by their seats). An item goes HERE when it lives in a shared file,
> affects more than one board, or is a gate/process rule; it goes on an arch ledger when it lives in
> that arch's lane. Cross-reference by id (`S<n>` here, `<A|B|C|D><n>` on an arch ledger).

**ID ALLOCATION — SEAT-PREFIXED, agreed over ccd 2026-09-06 (pi 7 proposed, orin 15 voted, rmbp 12 invited the proposal and accepted either scheme). NOT a Peter decision: naming and process.** New shared rows take a SEAT PREFIX — `SP<n>` pi · `SR<n>` rmbp · `SO<n>` orin — so two seats physically cannot mint the same id. **Why, and it is not tidiness: sequential `S<n>` allocation is STRUCTURALLY broken here.** Three seats commit to unpushed branches, so no seat can see another's latest id; `S25` collided once on 2026-09-06 and `S31` collided again the same evening — the second time even though pi deliberately skipped 29-30 to leave room. A reserved gap only works if every seat can see it, and none can. Blocks (per-seat number ranges) were the alternative and were declined: they keep shared state a seat must remember, a prefix cannot be gotten wrong. **`S1`-`S32` FREEZE exactly as they are** — nothing renumbers and every existing cross-ref keeps resolving (`S32` is orin's, on hw-jetson, not yet visible in this tree). GATE-LEDGER's id check is already `^[A-Z]+[0-9]+` so a prefixed id passes untouched. **The cross-ref resolver needed widening and rmbp LANDED it — `3867365c` (hw-rmbp), `→\s*([SP][0-9]+)` → `→\s*((?:S[PRO]?|P)[0-9]+)`. `SP<n>` is mintable now.** ⚠ And the reason it was not optional corrects pi's own stated reason: pi wrote that a `→ SP<n>` cross-ref *"would fail the gate"*. **It would NOT have. It would have been SILENTLY SKIPPED** — in `[SP][0-9]+` the `S` of `SP32` is followed by `P`, not a digit, and the pattern is anchored to the literal `→`, so `re.findall` returns `[]` and the row passes UNCHECKED (verified both ways: old `[]`, new `['SP32']`). A dangling prefixed cross-ref would have read as green forever. **The gate was not protecting the migration, it was ignoring it** — S31's shape aimed at a gate, and the direction of the error is what mattered: pi believed the check was stricter than it was. rmbp proved the fix BY MUTATION, not by reading it (`-> SP99` RED exit 1 — **written here with an ASCII arrow ON PURPOSE: with the Unicode `→` this very sentence becomes a parseable cross-ref to a row that does not exist, and the widened resolver reds on the prose documenting its own test fixture. Found by pi 7 running the widened pattern over this file before folding the gate; P14/S17 in one line.** Control `→ S6` → OK; unmutated tree → OK, 108 rows), which is the standard a gate change has to meet.

Status enum (a cell BEGINS with one of): `open` · `fixed-unflown` · `flown` · `landed` · `dropped`; free text after " — ". `owner` ∈ {orin, pi, rmbp, shared-gate}; `flies-on` = the bench that scores it. Evidence paths point into git (`docs/dev/evidence/`): reports, reviews, and capture EXCERPTS (item-scoped, ~50 KB, first line = the loader identity anchor that names the boot — a bare line range into an append-only capture rots the moment the file grows). Full captures stay on the bench (unversioned, unbacked: `~/unaos-bench` is not a git repo — pi 6 measured).

- **P2** — `git merge -F -` does not read stdin (write the message to a file); `unwrap80.sh` takes a FILE, not stdin *(standing)*
- **P3** — A boot's loader anchor may land in `raw.log`/`unknown.log`, not the board log; pin by anchor in whichever file carries it, then prove board purity *(standing)*
- **P4** — A peer's relay of Peter's word is a report, not the word; focus is assigned in your own session *(standing)*
- **P5** — ONE-TIME BACKLOG SWEEP, each seat: every track-named file in any plan surface (`batons/ whiteboards/ queue/ review/ wip/ active/ future/ metal/ past/`, memory, scratch — pi measured 12 surfaces, 383 files) with no closure marker and mtime > 14 days gets a ledger row or a DROPPED ruling. The ledger only accretes from the first audit forward; the rot is in what predates it *(owed (pi, rmbp) — orin swept 2026-09-05 6cc8de8c: 25 surfaces, 767 files, 355 orin-named, 193 stale, 41 unmarked → 30 already-landed, 2 dropped, 9 not-work-items, 0 open; two rows exposed on the way, C10 + S27 — `docs/dev/evidence/orin14/P5-SWEEP.md`)*
- **P6** — `affects` is NOT a judgment call: the finder states the FILE; every lane that compiles that file is affected by construction *(standing)*
- **P7** — A LINE-NEUTRAL append placed AFTER a line's trailing `//` comment is prose: it compiles nothing and the check stays green (PRTSCR-ORIN `2000608a`, and the ORINRX census at the seat's union merge — both caught by a position check at the fold). The append goes BEFORE the first `//`; prove it with `python3 -c` position check or a grep that the statement precedes `//` *(standing)*
- **P8** — `git cherry-pick --continue` commits whatever is staged, conflict markers included, if the resolver failed before `git add`; `bash -n unaos/arroyo` (and a `grep -c '^<<<<<<<'` on every unmerged file) before any continue (orin 13, a20839c6 → fixed 2e149665) *(standing)*
- **P9** — a check that runs while the tree is being edited reports the tree AT READ TIME, file by file: a knob declared in Cargo.toml and read before arroyo's leg list was resolved reds the coverage check on a state that never existed as a commit. Never edit the tree under a running check; if you did, discard the verdict and re-run on the commit *(standing)*
- **P10** — A parked artifact that does not apply is NOT evidence of loss: `git apply --check` failing says the tree differs, not in which direction. Determine direction before triage — is the change ABSENT, or already PRESENT? Check the artifact's distinctive content in the tree. Three instances in one evening (pi's S22, S23; rmbp's E2) all failed the same way: an item assumed open because nobody asked whether it had already closed. The backlog's danger is phantom obligations that cause work to be redone, not lost work (pi 6) *(standing)*
- **P11** — A backgrounded shell that `cd unaos && ./arroyo check` and then `git add unaos/scripts/…` doubles the path (`unaos/unaos/…`): the commit silently does not happen while the check reports green. Chain commits from the repo root or use `git -C <root>`; read `git status` after, the exit code does not say (rmbp 11) *(standing)*
- **P12** — `TaskStop` on a backgrounded `./arroyo check` kills the shell, not its cargo children; they keep running against the same target dir and a fresh check started beside them dies mid-run (exit 144). `pgrep -fa '[c]argo'` and kill the orphans before restarting (orin 13) *(standing)*
- **P13** — `pkill -f 'cargo'` matches the shell that issued it (the pattern is in its own command line) and kills your session's command; write the pattern as `'[c]argo'` so it cannot match itself — the same trap as the baton's `pgrep` warning about the butler (orin 13) *(standing)*


- **P14** — **A cross-ref to another seat's not-yet-folded row gates DIFFERENTLY depending on whose tree runs the check, and one of the three verdicts is silence.** With seat-prefixed ids live and GATE-LEDGER's widened resolver on only one branch, the same `→ SR1` text yields three answers: **resolves** on a tree that has both the widened resolver and the row; **REDs** on a tree with the resolver but not yet the row (any seat that adopts the gate before the fold); **silently skipped** on a tree with neither — the worst case, because the row reads as checked and is not. **Norm (pi 7, 2026-09-06, adopted): a cross-ref to a row that has not folded yet stays PROSE — "rmbp SR1 `9d92f32c`" — and becomes `→ SR1` only after the fold puts the row in the same tree.** pi 7 wrote the first one this way deliberately rather than minting a cross-ref that could not be correct in any tree. **FOURTH verdict (pi 7, found by running the widened resolver over their own file before folding the gate): a checker that scans free text cannot distinguish a MENTION of an id from a REFERENCE to one.** Every id quoted in ledger prose — go-red fixtures, examples, a commit message pasted into a cell — is live input to the resolver, so the sentence DOCUMENTING a gate's test can become a failing input to it. **AMENDED 2026-09-06 (pi 7 corrected their own account; rmbp 13 had propagated it): that was true for an ARCH ledger and INERT in `LEDGER.md` itself.** The resolver carried `and path != "docs/dev/LEDGER.md"`, exempting the over-arching ledger's own cross-refs from resolution entirely — so the `SP99` fixture that supposedly demonstrated this would have passed silently, forever. Proved by mutation on two trees: `-> S777` injected into a LEDGER.md table row passed at exit 0 while the same ref in an arch ledger red at exit 1. The exemption is now GONE, along with two siblings of it, so the claim above is true everywhere for the first time — which is the better reason to keep citing fixtures with an ASCII arrow, not a weaker one. This is S17 (prose counted as code) and P14 meeting in one line. **The escape is the arrow glyph and it is now a contract: a UNICODE arrow is a reference the gate resolves; an ASCII `->` is a mention it ignores.** No gate change was needed — the resolver already matched the Unicode arrow only, so the escape existed accidentally and is now documented at the code and in `STRUCTURAL_GATES.md` §GATE-LEDGER, whose own `-> S999` fixture citation was this tree's latent instance *(standing)* **RESOLVED IN THE GATE, not left as a norm (pi 7 found the live instance, rmbp 13 settled it, 2026-09-06).** The norm above and the id contract COLLIDE: `STRUCTURAL_GATES.md` sanctions the suffix form `A36 (-> SR2)` in the id cell, but P14 says an unfolded cross-ref stays prose, and an id-suffix cross-ref cannot be prose without breaking the id convention — so the sanctioned form lost silently. Live instance: `A36 (-> SR2)` on hw-jetson, where SR2 lives on hw-rmbp and that tree has ZERO `SR` rows in any of its three ledger files. The gate now SPLITS the verdict instead of asking seats to remember a norm: shared ids (`S<n>`, `P<n>`) live in every tree (measured: 27-31 S-rows on main, hw-jetson, hw-pi4 and hw-rmbp alike), so an unresolved one is still RED; seat-prefixed ids (`SR`/`SO`/`SP`) are branch-local by construction, so an unresolved one is **DEFERRED** — printed, counted, named in the summary, never silently skipped — and `UNAOS_LEDGER_STRICT=1` turns every deferral into a red. **The TRUNK enforces automatically** — the trigger is the branch, not an exported variable (pi 7 caught that the first cut left the backstop to a seat's memory: exactly one un-environmented call site and no landing gate command to hold the export): a track branch defers, the trunk reds, and the landing merges to trunk and runs the battery there. The sharper discriminator (defer only when the prefix has zero rows here) was rejected on purpose: it false-reds in the partial-fold window, which is the surprise this change exists to prevent. Prose cross-refs remain fine and are still the right choice in body text; the id-suffix form is now safe to use.
- **P15** — **An edit to a refusal or error message ships with the OUTPUT, not with the diff.** Formulated by pi 7 (2026-09-06) from an instance in rmbp 13, and filed here because the instance is this seat's. rmbp 13 built `./arroyo knoboff` and proved five arms — usage, undeclared feature, armed env, PASS, GO-RED — then took a request to reword a SIXTH, the control-failure refusal. pi 7's request was a question nobody had asked: **has that branch ever executed?** It had not. **Editing text on a branch is a claim that the branch produces text; a message never seen printed is unverified code, not documentation.** Making it run found TWO defects, neither visible in any diff. (1) `_knoboff_checkout` ran `git checkout --detach` BEFORE the `reset --hard` that clears the previous run's applied patch, so git aborted and the `&&` chain died — the tool worked on a session's first run and failed on every later one whose baseline differed from the throwaway tree's commit, which is all of them. (2) The new guidance was in the WRONG ARM: a `baremetal`-gated feature does not build-and-match, its armed build FAILS on Pi-only imports (`piinstall` reaches for `crate::drivers::emmc2`), so the reader landed in the other branch and was told to hunt a partner knob that does not exist. Both were found by running the branch and reading its output. **This sits one level below the round's other rule** ("a check that cannot fire must SAY so rather than return green"): that one is about a comparison with no power; this is about a branch whose EXISTENCE is untested, where the message is the only evidence it would ever emit and nobody has watched it emit. Practice: quote the printed output in the commit or the review, never the intended wording.
