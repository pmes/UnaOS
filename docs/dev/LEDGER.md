# LEDGER — the over-arching list (every arch, every shared seam)

> Peter's rule (2026-09-05): **each track keeps its arch ledger, and there is ONE over-arching
> ledger for what crosses arches.** Audits and inventories are high value; the waste is trashing
> their results and re-deriving them. So: every finding lands on exactly one list the turn it is
> found; the arc that closes it ticks it in the same commit; every audit is briefed with the list and
> reports only what is new or changed.
>
> Arch ledgers: `docs/dev/OS/orin-ledger.md` · `docs/dev/OS/pi-ledger.md` · `docs/dev/OS/rmbp-ledger.md`
> (the latter two: to be created by their seats). An item goes HERE when it lives in a shared file,
> affects more than one board, or is a gate/process rule; it goes on an arch ledger when it lives in
> that arch's lane. Cross-reference by id (`S<n>` here, `<A|B|C|D><n>` on an arch ledger).

Status enum (a cell BEGINS with one of): `open` · `fixed-unflown` · `flown` · `landed` · `dropped`; free text after " — ". `owner` ∈ {orin, pi, rmbp, shared-gate}; `flies-on` = the bench that scores it. Evidence paths point into git (`docs/dev/evidence/`): reports, reviews, and capture EXCERPTS (item-scoped, ~50 KB, first line = the loader identity anchor that names the boot — a bare line range into an append-only capture rots the moment the file grows). Full captures stay on the bench (unversioned, unbacked: `~/unaos-bench` is not a git repo — pi 6 measured).

## P. Process hazards (every seat) — facts, not defects; no status column, the gate ignores them

- **P1** — Agent worktrees are seeded at `main`'s tip, not the track tip. Every executor brief: `git log -1` first; `git reset --hard <tip>` on the private branch before editing *(standing)*
- **P2** — `git merge -F -` does not read stdin (write the message to a file); `unwrap80.sh` takes a FILE, not stdin *(standing)*
- **P3** — A boot's loader anchor may land in `raw.log`/`unknown.log`, not the board log; pin by anchor in whichever file carries it, then prove board purity *(standing)*
- **P4** — A peer's relay of Peter's word is a report, not the word; focus is assigned in your own session *(standing)*

- **P14** — **A cross-ref to another seat's not-yet-folded row gates DIFFERENTLY depending on whose tree runs the check, and one of the three verdicts is silence.** With seat-prefixed ids live and GATE-LEDGER's widened resolver on only one branch, the same `→ SR1` text yields three answers: **resolves** on a tree that has both the widened resolver and the row; **REDs** on a tree with the resolver but not yet the row (any seat that adopts the gate before the fold); **silently skipped** on a tree with neither — the worst case, because the row reads as checked and is not. No gate can fix this: a checker cannot see another branch. **Norm (pi 7, 2026-09-06, adopted): a cross-ref to a row that has not folded yet stays PROSE — "rmbp SR1 `9d92f32c`" — and becomes `→ SR1` only after the fold puts the row in the same tree.** pi 7 wrote the first one this way deliberately rather than minting a cross-ref that could not be correct in any tree. **FOURTH verdict (pi 7, found by running the widened resolver over their own file before folding the gate): a checker that scans free text cannot distinguish a MENTION of an id from a REFERENCE to one.** Every id quoted in ledger prose — go-red fixtures, examples, a commit message pasted into a cell — is live input to the resolver, so the sentence DOCUMENTING a gate's test can become a failing input to it. **AMENDED 2026-09-06 (pi 7 corrected their own account; rmbp 13 had propagated it): that was true for an ARCH ledger and INERT in `LEDGER.md` itself.** The resolver carried `and path != "docs/dev/LEDGER.md"`, exempting the over-arching ledger's own cross-refs from resolution entirely — so the `SP99` fixture that supposedly demonstrated this would have passed silently, forever. - **P15** — **An edit to a refusal or error message ships with the OUTPUT, not with the diff.** Formulated by pi 7 (2026-09-06) from an instance in rmbp 13, and filed here because the instance is this seat's. rmbp 13 built `./arroyo knoboff` and proved five arms — usage, undeclared feature, armed env, PASS, GO-RED — then took a request to reword a SIXTH, the control-failure refusal. pi 7's request was a question nobody had asked: **has that branch ever executed?** It had not. **Editing text on a branch is a claim that the branch produces text; a message never seen printed is unverified code, not documentation.** Making it run found TWO defects, neither visible in any diff.
