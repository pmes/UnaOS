# LEDGER — the over-arching list (every arch, every shared seam)

> Peter's rule (2026-09-05): **each track keeps its arch ledger, and there is ONE over-arching
> ledger for what crosses arches.** Audits and inventories are high value; the waste is trashing
> their results and re-deriving them. So: every finding lands on exactly one list the turn it is
> found; the arc that closes it ticks it in the same commit; every audit is briefed with the list and
> reports only what is new or changed.
>
> Arch ledgers: `docs/dev/OS/orin-ledger.md` · `docs/dev/OS/pi-ledger.md` (created 2026-09-11) ·
> `docs/dev/OS/rmbp-ledger.md` — all three now exist and all three are scanned by `ledger-check.sh`. An item goes HERE when it lives in a shared file,
> affects more than one board, or is a gate/process rule; it goes on an arch ledger when it lives in
> that arch's lane. Cross-reference by id (`S<n>` here, `<A|B|C|D><n>` on an arch ledger).

**ID ALLOCATION — SEAT-PREFIXED, agreed over ccd 2026-09-06 (pi 7 proposed, orin 15 voted, rmbp 12 invited the proposal and accepted either scheme). NOT a Peter decision: naming and process.** New shared rows take a SEAT PREFIX — `SP<n>` pi · `SR<n>` rmbp · `SO<n>` orin — so two seats physically cannot mint the same id. **Why, and it is not tidiness: sequential `S<n>` allocation is STRUCTURALLY broken here.** Three seats commit to unpushed branches, so no seat can see another's latest id; `S25` collided once on 2026-09-06 and `S31` collided again the same evening — the second time even though pi deliberately skipped 29-30 to leave room. A reserved gap only works if every seat can see it, and none can. Blocks (per-seat number ranges) were the alternative and were declined: they keep shared state a seat must remember, a prefix cannot be gotten wrong. **`S1`-`S32` FREEZE exactly as they are** — nothing renumbers and every existing cross-ref keeps resolving (`S32` is orin's, on hw-jetson, not yet visible in this tree). GATE-LEDGER's id check is already `^[A-Z]+[0-9]+` so a prefixed id passes untouched. **The cross-ref resolver needed widening and rmbp LANDED it — `3867365c` (hw-rmbp), `→\s*([SP][0-9]+)` → `→\s*((?:S[PRO]?|P)[0-9]+)`. `SP<n>` is mintable now.** ⚠ And the reason it was not optional corrects pi's own stated reason: pi wrote that a `→ SP<n>` cross-ref *"would fail the gate"*. **It would NOT have. It would have been SILENTLY SKIPPED** — in `[SP][0-9]+` the `S` of `SP32` is followed by `P`, not a digit, and the pattern is anchored to the literal `→`, so `re.findall` returns `[]` and the row passes UNCHECKED (verified both ways: old `[]`, new `['SP32']`). A dangling prefixed cross-ref would have read as green forever. **The gate was not protecting the migration, it was ignoring it** — S31's shape aimed at a gate, and the direction of the error is what mattered: pi believed the check was stricter than it was. rmbp proved the fix BY MUTATION, not by reading it (`-> SP99` RED exit 1 — **written here with an ASCII arrow ON PURPOSE: with the Unicode `→` this very sentence becomes a parseable cross-ref to a row that does not exist, and the widened resolver reds on the prose documenting its own test fixture. Found by pi 7 running the widened pattern over this file before folding the gate; P14/S17 in one line.** Control `→ S6` → OK; unmutated tree → OK, 108 rows), which is the standard a gate change has to meet.

Status enum (a cell BEGINS with one of): `open` · `fixed-unflown` · `flown` · `landed` · `dropped`; free text after " — ". `owner` ∈ {orin, pi, rmbp, shared-gate}; `flies-on` = the bench that scores it. Evidence paths point into git (`docs/dev/evidence/`): reports, reviews, and capture EXCERPTS (item-scoped, ~50 KB, first line = the loader identity anchor that names the boot — a bare line range into an append-only capture rots the moment the file grows). Full captures stay on the bench (unversioned, unbacked: `~/unaos-bench` is not a git repo — pi 6 measured).
