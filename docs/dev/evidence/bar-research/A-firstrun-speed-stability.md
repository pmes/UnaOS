# Research A: first run, responsiveness, stability (vocabulary from blueprint INDEX.md + boot.md read at HEAD; "new line" = not in the tree, unbuilt)

## 1. First run and onboarding
| what they do wrong | evidence (source, number) | what UnaOS does instead | the measurable bar |
|---|---|---|---|
| A cloud account is forced before the desktop | Win11: `BypassNRO` removed (build 26200.5516, Mar 2025) and `ms-cxh:localonly` removed (26220.6772, Oct 2025) [TR][EI] | The first-user form asks for a name, a password and a retype. That user is the local administrator and root is locked (BP-boot-7). The network is not touched before the desktop, because net/wifi starters wait on `services_up()` (BP-boot-3). | twoboot boot 1: `[login] installer: first-user form open` → `[login] session open user=… role=admin`, and zero net/wifi lines before `[boot] services up` |
| Setup takes up to an hour and downloads updates mid-setup | Win11 OOBE "over an hour", updates alone 20-50 min; MS promised a faster OOBE by end-2026, still not free of the Microsoft account [PI][WL] | Setup has no update step: the image is the system, and features join only by a commit to `image-line.env` (BP-boot-11). | Machine time from boot 1 `KELF` to the form ≤ 10 s; `:: BOOT: phase=desktop … login->desktop=` ≤ 1000 ms; total wall time ≤ 60 s including typing |
| Choice and upsell screens | Win11: OneDrive / M365 / Game Pass promo panes [PI]; macOS: separate Siri, Screen Time, FileVault and analytics panes, which only MDM can suppress [AD][STIG] | One screen with three fields. Every other choice has an OS default and lives in settings after the desktop. | twoboot spec asserts exactly 1 form, 3 fields, 0 extra prompts between `held_ms` and `session open` |
| The installer demands disk and partition decisions (Linux) | Ubuntu / Fedora installers ask for a partition scheme, keyboard and time zone before first use (knowledge) | Root is found by content (storage.md) and the installer advances itself to `user-created` | `[boot] step=root-mount … end ms=` within budget, no `OVER`; 0 disk questions |
| Setup comes back after updates | Win "Let's finish setting up your device" re-prompts (SCOOBE) after feature updates (knowledge) | `Desktop` is latched by the first session and never un-latches. Later boots go to the login screen (BP-boot-2, -8). | twoboot boot 2 prints `[login] boot 2:` and never `installer`; `[boot] phase=desktop` once per boot |

## 2. Responsiveness
| what they do wrong | evidence (source, number) | what UnaOS does instead | the measurable bar |
|---|---|---|---|
| Keypress-to-photon got slower over 40 years | Apple IIe 30 ms; modern machines 100-200 ms in a terminal; keyboard scan 556 Hz on the Apple IIe vs 100-200 Hz now [LUU][SW] | One path from the HID decode to `pal::Event`, then to the in-kernel compositor on render cores. There is no IPC chain and no app round-trip for the echo (input.md, cores.md). | New line `[input] k2p p50= p99=`, rdtsc from the HID IRQ to the flip; p99 ≤ 1 vblank + scanout (≤ 25 ms at 60 Hz); a 240 fps camera on the bench against Luu's table |
| Dropped frames under background load | 60 Hz leaves 16.7 ms per frame; RAIL says < 16 ms per frame and visible response < 100 ms [RAIL] | The split puts the compositor on render cores and services on service cores, and the compositor gate preempts (cores.md). | New `[wc] missed_vblank=` per minute; 0 across a 60 s window drag while `tests` runs (`UNAOS_WC=1` + kepler knobs, `KEPLER_VBLANK`) |
| Touch and trackpad drag lag behind the finger | Commodity touch about 100 ms, so a drag trails by about 10 cm at 1 m/s; MSR prototype at 1 ms [NW] | The compositor draws the cursor and the dragged window from the newest trackpad sample at each vblank, not from the app's last frame. | New `[input] drag_age_ms` p99 ≤ 1 vblank (16.7 ms) |
| Slow app launch is tolerated | Android vitals flags a cold start only at ≥ 5 s (warm ≥ 2 s); Apple targets about 400 ms to first frame [AV][WWDC] | A ring-3 ELF loads straight into a slot (ring3.md), with no dyld/JIT/runtime warm-up and no splash per app | New `[app] <name> exec->frame ms=` ≤ 400 ms cold, p99 over 20 launches |
| Boot time grows without bound and nothing says why | Ubuntu `snapd.service` 4-24 s in common reports, 8 min in a regression [SNAP] | Each boot step is bracketed with a budget and says `OVER` every 5 s (BP-boot-9). Services wait for the desktop (BP-boot-3), and tests are deferred (BP-boot-4). The splash is hard-bounded at 5000 ms (BP-boot-5). | `KELF` → `[desktop] built … bar_ms=` ≤ 3 s on the rMBP; `[splash] held_ms` < 5000; 0 `OVER`; `:: TESTS: deferred=<n>` present |
| Sleep that is not sleep | Modern Standby (S0ix) wakes in the bag, drains the battery and overheats; firmware removes S3 [DELL][MN] | Lid-close is a full stop with lid and power key as the only wake sources. There is no connected standby. (`LIDSLEEP` behaviour: unverified.) | New `[power] wake src= ms=` lid-open → first frame ≤ 1000 ms; 8 h lid-closed drain ≤ 2 % |

## 3. Stability and updates
| what they do wrong | evidence (source, number) | what UnaOS does instead | the measurable bar |
|---|---|---|---|
| Forced reboots destroy work | UCL survey (n=93): 50 % had unexpected restarts, 28 % knew of "active hours"; 21 of 47 common apps lost unsaved data [UCL][PCW] | An update stages a new image beside the current one. The loader switches only on a restart the user starts. (Unbuilt: needs a seat decision.) | New `[update] staged kelf=` line; `KELF min= max=` changes only after a boot whose previous shutdown printed `why=user` |
| Updates that brick or corrupt | CrowdStrike: 8.5 M Windows machines down from one ring-0 content push [TC]; KB5063878 SSD reports (12 of 21 drives misbehaved in one test; MS and Phison found no link) [NEO][PCW2] | No third-party ring-0 code: drivers are in the tree (ONE OS, shape.md). The previous image stays bootable, and the loader falls back if the new one never prints `DESKTOPBUILT PASS`. | A twoboot variant injects a panicking image; boot 2 must print the old `KELF` and `:: DESKTOPBUILT: … -> PASS ::` |
| Background services multiply | Win11 63-117 services and 82-312 processes on ordinary machines [MSQ][EF] | A starter exists only through `services_gate(name)`, and a knob joins the image only by a commit (BP-boot-3, -11) | The `held_starters=` count is identical across N boots and only changes in a commit that is visible to gate `image-line` |
| Performance decays over months | Startup items, scheduled tasks and indexers accumulate; vendors publish no decay figure (knowledge: unmeasured) | Apps cannot register autostart. The boot runs only the boot (BP-boot-4), and every boot puts its own timings on the wire (BP-boot-12). | BPACE rungs and `bar_ms` on day 180 stay within ±10 % of day 1; a drift turns the bench score red |
| Session state rots until a reboot | Windows/macOS "have you tried restarting" folklore; desktop shells leak (knowledge) | The desktop is built at login and torn down at Log Out (BP-boot-6), so Log Out gives a clean desktop | Log Out then log in: `[desktop] built bar_ms=` within ±10 % of the first build; a new heap high-water line returns to its first value |

**The three decisions that matter most.** (1) Setup is local-first, one form long, and nothing networked runs before the desktop. BP-boot-3 and BP-boot-7 already make this mechanical rather than a promise. Keeping it means refusing every later "just one more first-run screen". (2) The input-to-photon path belongs to the kernel and carries a timestamp at each end: HID IRQ → `pal::Event` → compositor on reserved render cores → flip. The wire should print `k2p` and `missed_vblank` the way it already prints `bar_ms`, so latency becomes a gate and not an opinion. Without those two lines the 30 ms Apple IIe bar cannot be scored. (3) The image is the unit of change: no third-party ring 0, A/B images with automatic fallback when `DESKTOPBUILT` does not pass, and no restart the user did not start. Every budget is on the wire (`OVER`, BPACE, `held_starters`), so decay and update breakage show up as a red line on the bench and not as a user's slow Tuesday. Decisions (2) and (3) are unbuilt and need a seat ruling.
