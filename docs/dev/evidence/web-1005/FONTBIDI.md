# FONTBIDI — font_core shapes the world's scripts, in both directions (LEDGER SR56)

Branch `exec-text-fontbidi`, cut at `4f5ecd7d`, with `exec-media-svgcore` (@91beae20, font_core + svg_core) merged
first. Crate: `unaos/libs/text/font_core`. It is still `#![no_std]` + `alloc` and `#![forbid(unsafe_code)]`, and
it still has **zero dependencies**, dev-dependencies included. `cargo check -p font_core --target
aarch64-unknown-none-softfloat` passes. No new crate. `handlers/aether` is untouched.

## Finding

Before this arc FONTCORE shaped only Latin, Greek and Cyrillic. Arabic came out unjoined, Devanagari came out
unreordered, Hebrew and Thai marks were not positioned, and there was no bidi. Every right-to-left run was drawn
in logical order. FONTBIDI adds all of this:

* UAX #9 bidi
* UAX #29 grapheme clusters and the script itemizer
* UAX #15 NFC/NFD
* the full OpenType lookup engine
* the Arabic, Indic (Devanagari), Thai and Hebrew shapers
* UAX #14 for every class

Every Unicode table is generated into the crate from the UCD 17.0.0 files (data only). Every stage is proven
against an oracle: Unicode's own conformance files, HarfBuzz for glyph output (it is the shaper inside Chromium),
and Chromium itself for widths, visual order and pixels.

All tables are generated by `oracle/gen_ucd.py` from the UCD 17.0.0 files (URLs and sha256 are in
`oracle/vectors.txt`). Each generated module names its sources and their sha256. Together they take 544 KB of
source. The one non-UCD table is `ucd/vowel_constraints.rs`, from Microsoft's IndicShapingInvalidCluster.txt,
which shaping engines use. www.unicode.org is refused by this host's proxy, so the files come from the
unicodetools repository.

## Oracles and method

1. **Unicode conformance files, run in full** (fetched at test time, sha-pinned, SKIP offline;
   `FONTBIDI_UCD_DIR` can point at a local copy):
   * BidiTest.txt: 770,241 cases (every class sequence × every paragraph direction in its bitset), checking levels
     and visual order.
   * BidiCharacterTest.txt: 91,707 lines (code points with paired brackets), checking paragraph level, levels and
     order.
   * GraphemeBreakTest.txt, NormalizationTest.txt and LineBreakTest.txt.
2. **HarfBuzz 14.5.0, glyph for glyph.** It runs through uharfbuzz (pip) at test time only and is never linked.
   `oracle/gen_shape_kat.py` shapes the same strings with the same fonts. HarfBuzz's own itemized script is
   recorded, as Chromium would pass it. `tests/complex_shape.rs` requires identical glyph ids, advances, x/y
   offsets **and clusters**. The fonts are:
   * Noto Sans Arabic, Hebrew, Devanagari and Thai, and Noto Nastaliq Urdu (heavy cursive attachment)
   * DejaVu Sans
   * a 20 KB synthetic font, built with fontTools feaLib, that exercises GSUB 3 and 8, LTR GPOS 3 and
     contextual GPOS, which the Noto fonts do not use under default features

   The corpus has real words and sentences plus seeded random strings over each script's letters and marks
   (broken clusters, stacked marks, ZWJ/ZWNJ). Larger sweeps were run while developing
   (`FONTBIDI_SEED`/`FONTBIDI_SCALE`, `FONTBIDI_HB_KAT`).
3. **Chromium 1194** (`oracle/run_fontbidi.sh`). 24 paragraphs × 12/16/24/48 px = 96 jobs, covering:
   * Arabic (incl. harakat, lam-alef, Arabic-Indic and European digits)
   * Urdu Nastaliq
   * Hebrew with niqqud
   * Devanagari conjuncts/reph/matras
   * Thai
   * 8 mixed-direction paragraphs (Latin+Arabic/Hebrew/Devanagari/Thai, numbers, brackets, quotes)

   Each job is set in a font stack (the Noto face, then DejaVu Sans) with `dir=auto`, no hinting and grayscale AA.
   Chromium falls back per cluster, and so does `font_core::shape_fallback`. Recorded per job:
   * `canvas.measureText`
   * a screenshot
   * the visual order of grapheme clusters: Intl.Segmenter graphemes sorted by `Range.getClientRects()` x, written
     as UTF-8 byte offsets

   The widths and orders are frozen in `tests/data/fontbidi_chrome.tsv`, so the gate checks real Chromium output
   on a host without Chromium. The rasters are compared by the opt-in `chromium_oracle_rasters`: registration by
   the best integer shift in ±2 px, then the per-glyph mean |coverage error| over each glyph box (FONTCORE's
   method).
4. **SVGCORE's own oracle** (resvg suite vs Chromium `<img>`) for the svg_core face. The 15 text files whose
   rendering changed were re-scored and re-pinned.

Chromium rasters, per-glyph share within 8 levels, 773 glyphs per size:

| size | `exact` (font_core default) | `exact+pre` | `aaa+pre` (`RenderMode::SkiaAaa` + Skia pre-blend) |
|---|---|---|---|
| 12 px | 85.0 % (mean 5.74) | 88.6 % | 97.3 % |
| 16 px | **90.2 %** (mean 4.95) | 90.4 % | 97.7 % |
| 24 px | **93.0 %** (mean 4.40) | 95.7 % | 97.8 % |
| 48 px | **98.7 %** (mean 2.61) | 98.8 % | 97.8 % |

* The SR56 target of ≥ 90 % within 8 levels at 16 px and above is met by the default exact mode across all
  scripts.
* Per script it is not met everywhere. In exact mode Arabic reaches 82.0 / 88.8 / 97.6 % at 16/24/48 px and Thai
  reaches 86.6 / 92.5 / 100 %.
* In `SkiaAaa` mode every script is at or above 92 % at 16 px+ (Arabic 98.5 / 99.0 / 95.1 %, Devanagari 100 %).
* The residual is the rasterizer model, not the shaping: widths agree to 0.002 px. FONTCORE documented the cause:
  Skia snaps edges to quarter-pixel rows, and Arabic's thin horizontal strokes are where that shows.

svg_core face (resvg suite vs Chromium), after `<text>` started using bidi + the complex shapers:

* All 1,118 files: 99.28 % → **99.31 %** of pixels within 8 levels; mean error 0.590 → **0.524**; files ≥ 99 %:
  1,004 → **1,011**.
* The 224 text files: 98.72 % → **98.87 %**. Arabic files went, for example, from 93.9 % to 99.5 % (fill-rule),
  95.2 % to 99.5 % (rotate-on-Arabic), 93.3 % to 98.9 % (text-anchor on Arabic) and 97.0 % to 99.2 %
  (bidi-reordering).
* One file dropped slightly: complex-grapheme-split-by-tspan, 99.44 → 99.37 %.

Two svg_core changes made this possible. Glyphs now arrive in visual order, so a run's absolute x/y is applied
before its first glyph. The paragraph direction comes from CSS `direction` (initial `ltr`), as in a browser,
rather than from P2/P3.

### What the oracles taught us (all now implemented)

* sos/eos must compare *explicit* embedding levels. Comparing the levels I1/I2 already raised fails 138 BidiTest
  cases.
* HarfBuzz/Chromium semantics:
  * ZWNJ blocks GSUB input matching unless it sits in context.
  * `mark`/`mkmk` treat ZWJ as non-skippable, so a mark after ZWJ stays unattached.
  * A default-ignorable that GSUB substituted stops being ignorable.
  * Arabic `liga`/`clig`/`mset` and the joining features ignore ZWJ manually.
* Hebrew needs the traditional mark order: modified combining classes, plus the meteg swap. Arabic needs MCM
  reordering. Devanagari needs the invalid-vowel-cluster dotted circles and Microsoft's grammar quirks: a vowel
  syllable may take `ZWJ + matra`, and a broken `Ra+H+H` cluster gets its dotted circle before the Ra.
* Clusters merge the way HarfBuzz does, extending over neighbours that share a cluster, which matters for Indic
  post-base reordering and Thai SARA AM.

## Ceiling: what is NOT done

* **Shapers.** Only Devanagari goes through the Indic model. Bengali, Gurmukhi, Gujarati, Oriya, Tamil, Telugu,
  Kannada, Malayalam and Sinhala need their per-script configs (reph mode and position, `pref`, old-spec tags). The
  `pref` path is not implemented. They currently go through the default shaper, which gives ligatures and marks
  but no reordering. Also missing:
  * the USE shaper (Tibetan, Khmer, Myanmar, Javanese …), Hangul jamo composition, Syriac fin2/fin3/med2
  * Arabic presentation-form fallback for fonts without GSUB
  * Thai PUA fallback for fonts without GSUB
  * `stch`
  * vertical text, AAT/`morx`/`kerx`
  * variable-font `rvrn`/device deltas
* **Bidi.** Line-level L1/L2 is available (`BidiInfo::visual_runs`). `layout_lines` still measures logical
  substrings, so lines are broken first and each line is then shaped with bidi. svg_core applies bidi per shaping
  run, not across tspans in a text chunk. Per-character x/y/dx on RTL runs is approximate.
* **Line breaking.** SA (Thai/Lao/Khmer/Myanmar) resolves by LB1 to AL/CM. No dictionary segmentation, so Thai
  breaks only at spaces, like the conformance file.
* **Normalization.** NFKC/NFKD are not needed by shaping and are not built.
* **Rasters.** Exact mode at 16 px is 90.2 % overall but 82 % for Arabic (see Numbers). `SkiaAaa` is the
  web-identical mode.

## Third-party crates

**None.** font_core has no dependencies and no dev-dependencies. svg_core's only dependency is still font_core.
HarfBuzz (uharfbuzz 0.56.2), fontTools 4.66.1 and Chromium 1194 are **test oracles only**. Scripts under `oracle/`
run them, and they are never linked or vendored. The data tables are Unicode's (and Microsoft's) data files,
transformed by a generator.

## How to continue

* The gate is `cargo test --release -p font_core -p svg_core`. It fetches the UCD conformance files and Noto
  fonts (sha-pinned) or prints SKIP offline.
* After a UCD bump, run `python3 oracle/gen_ucd.py <ucd-dir>` from the crate directory, then update the sha256 and
  URLs in `tests/*.rs` and `oracle/vectors.txt`.
* After a shaper change, rerun `python3 oracle/gen_shape_kat.py <noto-dir> > tests/data/hb_shape_kat.tsv` (needs
  uharfbuzz). For a big sweep, use `FONTBIDI_SEED=n FONTBIDI_SCALE=20 … > sweep.tsv`, then
  `FONTBIDI_HB_KAT=sweep.tsv cargo test --release -p font_core --test complex_shape -- --nocapture`.
* `oracle/run_fontbidi.sh [dir]` reruns Chromium, prints the raster table and writes a fresh
  `fontbidi_chrome.tsv`.
* A new Indic script needs its Indic_Syllabic_Category/Indic_Positional_Category data, which is already generated
  for every script. Add a config (reph mode/position, matra positions) next to the Devanagari one in
  `complex.rs`, map it in `Shaper::for_script`, and add its Noto font to `gen_shape_kat.py`.
