## 2. sdmmcwrite — the first CMD24 on the on-die SDHCI (A23, gap #3)

**Image** `sdmmcwrite-20260906T0137Z-a05c2c8`, kernel.elf sha256
`2b7027883c1e23e2384992b7849606a2f0592470c9e86c58997ebbaac5b4984b`, loader anchor
`KELF min=0x0 max=0x2e6880 pg=743` (matches the MANIFEST's `ELF max_vaddr=0x2e6880`).

**Knob line** (MANIFEST):

```
UNAOS_TEGRA=1 UNAOS_TEGRA_EL0=1 UNAOS_WITNESS=1 UNAOS_ORINRENDER=1 UNAOS_DESKCASCADE=1
UNAOS_ORINRX=1 UNAOS_HOLOCRON=1 UNAOS_ORINCLICK=1 UNAOS_SDMMC=1 UNAOS_SDMMCWRITE=1
```

effective-features `…,deskcascade,sdmmc,sdmmcwrite`.

**Pre-flight safety.** This is the only probe of the four that MUTATES the bench card, so it flew
behind an adjudication of PANEL-REVIEW finding T-1: [`SDMMC-T1.md`](SDMMC-T1.md) —
**VERDICT: SAFE-TO-FLY**, the target sector is provably outside every partition and provably empty
of any embedded boot image on the UNAOS-ORIN card, and two of T-1's premises are factually wrong.
The flight's own wire confirms the adjudication's prediction (`reason=mbr-gap-top`, `prior … = zero`).

**Verdict lines, verbatim** (excerpt lines 177–180):

```
[sdmmc] write probe armed (UNAOS_SDMMCWRITE=1): CMD24 then CMD17 read-back, 1-bit default speed, PIO, vendor block untouched, card_blocks=62333952
[sdmmc] write target=lba 2047 reason=mbr-gap-top layout=MBR (0x55AA boot signature; classic partition table) first_part_lba=2048 card_blocks=62333952
[sdmmc] write prior lba=2047 = zero
[sdmmc] write lba=2047 -> OK (512/512 match, t=78112 ticks = 2499 us @ 31250000 Hz)
```

**Against the design table** ([`../orin14/SDMMCWRITE.md`](../orin14/SDMMCWRITE.md) §Expected wire /
§Scorer). PASS predicate is `[sdmmc] write lba=<n> -> OK (512/512 match` — satisfied. All four
expected lines printed **in the design's order**, including the scratch-sector rule's requirement
that `target=` be printed BEFORE any write. The card matched the design's expected bench branch
exactly: 32 GB card, sector 0 a classic MBR, `card_blocks=62333952`, target `lba 2047`,
`reason=mbr-gap-top`. No `REFUSED`, no `FAIL status=…`, and — the shape the design warned about —
**no EL3 SError**: the standard window is NOT firewalled for writes, so the FWALL conviction is
confined to the vendor pad block. Write + read-back cost 2499 µs at 1-bit default speed, PIO.

**What it decides.** A23 is **flown PASS**: a single-block write to the on-die SDMMC reads back
byte-exact with the vendor pad block disabled. The witness block is deliberately NOT restored, so
**the persistence proof is the NEXT boot of this image**: its `[sdmmc] write prior lba=2047 =
witness(tick=… lba=2047)` line (instead of `= zero`) proves the bytes survived power-off. That
second boot is the one owed item on A23. Downstream — self-update, the flight recorder, an unafs
root (A28's missing backend) — now has a proven write primitive under it.

## 3. net4 — the RX ring below 4 GiB (A12 / NET-4A, gap #2)

**Image** `net4-20260906T0138Z-a05c2c8`, kernel.elf sha256
`b89da04accd604385606b4d3ac963022aeacc68813231acb401c2a96a2698eeb`, loader anchor
`KELF min=0x0 max=0x306ee0 pg=775` (matches the MANIFEST's `ELF max_vaddr=0x306ee0`).

**Knob line** (MANIFEST):

```
UNAOS_TEGRA=1 UNAOS_TEGRA_EL0=1 UNAOS_WITNESS=1 UNAOS_ORINRENDER=1 UNAOS_DESKCASCADE=1
UNAOS_ORINRX=1 UNAOS_HOLOCRON=1 UNAOS_ORINCLICK=1 UNAOS_NET4=1
```

effective-features `…,deskcascade,net4,pcie3,pcie2`.

**Precondition held.** The RJ45 WAS cabled to the bench DHCP segment at power-on, and the link came
up: `PCIe cap @ 0x70: LinkCap max(gen3,x2) LinkStatus cur(gen1,x1) DLL-active=1 => LINK UP`
(excerpt 210), with the chip identified as the expected part —
`[net4F] MAC chip id: TCR=0x57100f00 xid=0x541 … [MATCH]` (RTL8111H class). So this boot is scored,
not `UNDECIDED`.

**Q0/Q1 — the mechanism seated exactly as designed** (excerpt 135, 296, 305–311):

```
:: tegra: [net4A] sub-4GiB Normal-NC DMA window reserved [0x80000000, 0x80200000) (2048 KiB) — lowest clean L2-split block in [0x80000000, 0x100000000); low-DRAM census: 2 Usable region(s) / 1983 MiB usable, 1 carveout(s) below 4 GiB, 2 candidate block(s) scanned (rejected: carveout=0 heap/nc=0 window=0 unsplit=0) ::
:: PCIE4:   [net4F] rx-ring phys=0x80000000 buffers=32 rx-bufs=[0x80010000..0x80020000) tx-ring phys=0x80020000 below4g=1 — every DMA object is < 4 GiB inside the NET-4h identity region: NO inbound-iATU alias in the NIC's write path (a truncated TLP is a no-op truncation) ::
:: PCIE4:   [net4s] all four DMA blocks are identity-covered — no inbound alias needed ::
```

Five `[net4s] … identity-covered, no alias` lines (rx-ring, rx-buffers, tx-ring, tx-buffers,
net4G-decoy), `enabled-index mask = 0x0001` — index 0 is the NET-4h identity region and **no
`[net4r] alias region 1` line exists anywhere in the boot**. NET-4o's "no clean sub-4 GiB span" is
refuted by measurement, as [`../orin14/NET4A.md`](../orin14/NET4A.md) §2 predicted: the scan found
the block on the first two candidates with zero rejections.

**Q2 — THE question, verbatim** (excerpt 341, 346, 353):

```
:: PCIE4:   [net4F] distinct buffers-written(count=2)=[0,17,-1,-1] across the first 4 RX completion(s) at=completion-4 below4g=1 rx-ring=0x80000000 — a single-address latch with NO alias in the path ⇒ NIC/RC-internal, NOT the alias; next question: the RC's inbound iATU region ordering (identity region 0 vs the NIC's TLP path) ::
:: PCIE4:   [net4F] VERDICT tag-proven single-address latch: 4 consecutive completions (through slot 4) wrote ONLY buffer 17 — measured by lost landing tags, not by content match, so the NET-4A artifact cannot produce it. Ring DRAM holds the correct distinct addr for every slot (net4x MATCH) ⇒ the reuse is NIC/RC-internal ::
:: PCIE4:   [net4F] distinct buffers-written(count=2)=[0,17,-1,-1] across the first 4 RX completion(s) at=window-close below4g=1 rx-ring=0x80000000 — …
```

**Against the design table** (NET4A.md §6 Q2). `count=2` with M=4 and `below4g=1` is the design's
**FAIL** arm, stated there as "NIC/RC-internal latch, alias acquitted". Not `PASS` (that needed
`count=4`), not `UNDECIDED` (traffic arrived — five completions popped — and `below4g=1`). The
verdict is reported identically at both sampling points (`at=completion-4` and `at=window-close`),
so it is not a sampling artifact.

**A second hypothesis refuted in the same boot** (excerpt 352):

```
:: PCIE4:   [net4F] RX ring pass verdict: pops=5 NUM_RX=32 wraps=0 RDU-clears=0 RXOVW-clears=0 CR=0x0c RxEnb=1 ISR=0x0084 — one pass only, and RDU NEVER latched: the halt is NOT the un-serviced status latch (REFUTED) — the engine stops without reporting descriptor-unavailable, so it is not re-fetching the recycled descriptors at all ::
```

**Q3 — the lease** (excerpt 355), meaningful only on a Q2 PASS, recorded as a datum:

```
:: PCIE4:   [net4V no-lease verdict] dhcp-tx: discover=1 request=0 | dhcp-rx: offer=0 ack=0 nak=0 | ring: popped=5/32 wraps=0 zero-payload=4 [ring died MID-PASS (window closed before one full pass; wraps=0)] => NO-OFFER: a DISCOVER left the NIC and no OFFER was ever delivered — wire / server / RX filter; the DHCP path above the driver was never exercised ::
```

**What it decides — R19 wording.** The sub-4 GiB placement **failed under these conditions**: with
the ring and all 32 buffers below 4 GiB, inside the NET-4h identity region, with no inbound-iATU
alias ever enabled anywhere in the boot, the buffer-17 single-address latch **still happens**. The
code is **KEPT** — the `net4` window, the placement and the whole `[net4s]`/`[net4F]` witness are
what made this measurement possible, and later rungs need the path open. Nothing is "ruled out".

Two hypotheses are now refuted by measurement, and both refutations are the boot's product:

1. **The inbound-iATU alias is ACQUITTED.** It was never in the path and the latch occurred anyway.
2. **The un-serviced RDU status latch is REFUTED.** `RDU-clears=0` and `RXOVW-clears=0` with
   `RxEnb=1` — the engine halts without ever reporting descriptor-unavailable.

**The manifest's stated next question is now the row's next question:** *the RC's inbound iATU
region ordering — identity region 0 versus the NIC's TLP path.* That is the wire's own wording, and
it is what the next net4 rung must ask.

DHCP is **untested above the driver**: `discover=1 offer=0` with the ring dead mid-pass means no
OFFER ever reached the stack, so the lease logic itself was never exercised. A12's DHCP half stays
open behind the RX half, not beside it.

**Verdict lines, verbatim** (excerpt 123, 125–126, 133, 137, 139, 142–143):

```
[ga10bprobe2] gpu@ node: BAR0=0x17000000 (DTB reg[0], EXT) power-domain-id=35 (DTB power-domains, EXT) clocks=3 (DTB clocks, EXT): 304 41 236 0 0 0 0 0
```

and the boot continued behind it:

```

:: AARCH64 SCHED (virt): boot core 0 at EL1 — running the full M4 CAPSTONE cooperatively ::
```

**Against the design table** ([`../orin14/GA10B-LADDER.md`](../orin14/GA10B-LADDER.md) §Rung 2,
Witness / PASS-FAIL). PASS = `-> POWERED chipset=0x17b` (arch 0x17, impl 0xB) with `pg=0x1` **and**
a desktop line after `rung 2 complete — RETURNING`. Both halves hold, and the implementation field
came back `0xb` — the design's **inferred** GA10B naming, marked UNVERIFIED there, is **confirmed by
the silicon**, so this is a plain PASS and not the PASS-with-datum arm. Every other arm is excluded:
not `UNPOWERED` (`boot0` is neither `0xFFFFFFFF`, nor `0x00000000`, nor a `0xBADxxxxx` PRI pattern),
not `REFUSED reason=pg-*` (BPMP answered `err=0` and the readback was ON), not `FAIL-fatal` (the
`about-to-read pmc_boot_0` announce at excerpt 138 is followed by the result at 139, so the BAR0
read did not kill the boot).

**The three by-products the rung was built to collect:**

1. **The chip id.** `NV_PMC_BOOT_0 = 0xb7b000a1` → chipset `0x17b`, arch `0x17` (Ampere),
   impl `0xb`, rev `0xa1`. First direct GA10B identification from UnaOS on metal.
2. **The clock census.** The DTB `gpu@` node lists 3 clocks: **304, 41, 236** (matching the
   design's expected `GPUSYS 304`, `GPC0CLK 41`, `GPC1CLK 236` — the UNVERIFIED DTB list is now
   verified). **UEFI left all three OFF** (`0 of 3 running before`). This rung enabled 304 and 41
   (`err=0` each); **clock 236 answered `err=-22` (EINVAL) on `IS_ENABLED` both before and after**,
   so it was never enabled and the rung reports `2 of 3`.
3. **BPMP's permission.** BPMP let this kernel read the domain state and drive the clocks it
   accepted, with no `-EACCES`-class refusal anywhere: every `MRQ_PG` err was `0`, every accepted
   `MRQ_CLK` err was `0`. The one negative is `err=-22` on clock 236 — an *argument* rejection, not
   a policy refusal.

**Restore was symmetric.** The rung disabled exactly the two clocks it enabled, in reverse order
(41 then 304), and left the power domain as found (`pg=0x1`, never driven because it was already
ON). `board left as found`.

**What it decides.** A24 rung 2 is **flown PASS**. **Rung 3 is now askable** — the read-only pass
over what the platform firmware left behind. It inherits two concrete inputs from this boot: the
GPU rail is ON with the CCPLEX permitted to drive it, and the GPC clocks were left OFF by UEFI, so
rung 3's reads happen under a clock state this kernel now knows how to establish. The `err=-22` on
clock id 236 is rung 3's first small question: whether that id is wrong in the DTB list this seat
read, or BPMP does not expose `GPC1CLK` to the CCPLEX on this SKU.
