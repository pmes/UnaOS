## 2. Findings
- **HDATONE5 → the DACs are not equal (HDATONE6)**: "hda 1 did a high pitched tone, hda 2 was silent, both = the screech". Wire: the single-member runs print `[hda] amp member=0 dac=0x03 … pin=0x0a … rate=48000 fmt_rd=0x0011` and `[hda] stream-id member=0 dac=0x03 tag=1 chan=0 raw=0x10 (want tag=1 stereo-chan=0) eapd=0x00 pin=0x0a`; `[hda] eapd member=0 pin=0x0a pincap_eapd=0 vendor=1013:4206 cirrus=1 before=0x00 after=0x00 stuck=1`; the pin census: `0x0b type=pin … pincfg=0x90100110 (dev=speaker loc=internal …)`, `0x15 … conns=[20] dev=line-out`, `0x10 spdif-out`. So ONE DAC makes a tone (the pitch is Peter's "high" — 440 Hz is not high; a tone at the wrong pitch, or the wrong rate on that DAC), the OTHER makes nothing, and both together is the screech: the second member is driven into a path that outputs noise, not silence, when both run (one stream tag, two converters, `stereo-chan=0` on both — both DACs taking channel 0 of the same stream?). The cloud reads: which DAC is `hda1` and which pin it reaches; `chan=` per member (left/right split, not both chan 0); whether member 2's path (dac 0x04 → pin 0x0b, the internal speaker per pincfg) is the one that is silent because its pin's `out_en`/amp is really off, or because 0x0b is the speaker that needs the GPIO amp (HDAAMP) — "silent" + "tone" + "screech together" is the shape of two DACs summed into one speaker with one of them unmuted-but-unfed. Headphones were not tried.
- **FILEVIEW2**: "tried to open a txt file but nothing happens". Wire: `[894236ms] [quarry] open TEXT path=/hello.txt -> fileview (latched for the render pass)` and NOTHING after — no window create, no `[fileview]` line; the PNG path at 398 s (`-> facet (latched …)`) DID open. The latch is set, the render pass never consumes it for TEXT (a cfg or a missing arm in the pass).
- **SPLASH2**: "took a while to come up and was only there a sec" — the splash is drawn at 7.6 s (the first 7.6 s of boot have no video: the Kepler takeover) and released at 10.1 s by `store-loaded` (held 2384 ms). By design as written; Peter's reading says the splash should own the glass from the FIRST frame the panel can show — i.e. earlier than the store, right at the takeover — and stay until the setter/login screen is painted (not released on store-loaded). Decision/arc.
- **SDHCMULTI still slow**: `:: SDHCWR: blocks=309 calls=26 multi_calls=5 bytes=158208 ms=70 busy_ms=0 wall_ms=1063 … kbps=148`; later `kbps=101` — 5 multi-block calls of 26, wall 15× the controller time (`ms=70` vs `wall_ms=1063`): the time is NOT in the controller, it is between calls (the FAT layer issuing one cluster at a time, syncs between). "still limited by card" = limited by the write path's call pattern.
- **USBNET4 → the numbers (USBNET5)**: `[usbnet] rx raw len=128 rx_hdr=0x00700002 pkt_cnt=2 hdr_off=112 first_pkt_hdr=0x80008000 reason=pkt-len-bad` — every frame arrives with a per-packet header whose LENGTH field is 0 and bit 31/15 set: the AX88179 reports its packets with the CRC/DROP flags and zero length, which is what the chip does when its RX control (AX_RX_CTL: AB/AM/START, and the checksum-offload / `RX_BULKIN_QCTRL` header mode) is not programmed the way the driver expects, or the header is read at the wrong offset (`hdr_off=112` of 128 = the trailer holds the headers; the first packet header is read from the WRONG word). `rx_short=N` = every frame. DHCP cannot lease → `[sntp] target=0.0.0.0 from=none`.
- **Kepler jitter (KVBLANK6)**: `:: kepler: vblank head=0 count=67359 period_us=16669 jitter_us=16944 … mode=irq vbwaits=748 vbwait_us=5779826 vbgaveup=0 seen=63195 tight=20193` — the mean period is right and the JITTER is a whole period: the vblank interrupt arrives irregularly (missed/doubled), which is "the vugs are roller coastering" (fps 33-59 swinging in the VUGART lines) — the ISR's ack/re-arm (KVBLANK5) delivers, but not every vblank. "a minimized and restored vug runs really high fps for a little bit" — VUGART lines reach `fps=2000`: an occluded-then-restored window composites without the beam wait until the first vblank lands — natural for the first frames, a reading for the restore path (the beam wait should re-engage on the first present).
- **SERIAL**: the kernel's own fixture reads `merged_fixed=187 trunc=4xx deferred=1 defer_lost=0 bypass=29 -> PASS`; the host tool on the capture still counts 1136 merged lines — the two disagree: the kernel fixes 187 merges it sees and the capture still carries merges the kernel did not count (the `bypass=29` path and truncations).
