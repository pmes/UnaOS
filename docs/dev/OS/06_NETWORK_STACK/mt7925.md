# MT7925 — the MediaTek Wi-Fi 7 driver ladder

**Target:** MediaTek MT7925 (`14c3:7925`; linux also binds `14c3:0717` with the same firmware), the Wi-Fi 7 radio of the
ASUS Zenbook S 14 UM5606W (Peter 2026-10-27: "begin support for the um5606w hardware"). PCIe, 802.11be, **SoftMAC
with MCU offloads** (see §2). Ledger: `docs/dev/OS/zenbook-ledger.md` Z5 (ZENBOOKMT7925). Sibling of `bcm4331.md`;
the station layer above both is net.md's (BP-net-15, BP-net-16).

Each stage is one rung with its own serial witness and names what it writes (BP-net-8). S1, S2 (MT7925S2, Z11), S3 (MT7925S3, Z15) and S4 (MT7925S4, Z17) are in the
tree; S5..S10 are owed by name. NO METAL: nothing runs on the Zenbook until the bench's first boot.

Sources: linux v6.11 `drivers/net/wireless/mediatek/mt76` (ISC), read for hardware facts only, no code copied:
`mt7925/{pci.c, mcu.c, mcu.h, init.c, main.c, mt7925.h, regs.h}`, `mt792x_{core.c, dma.c, regs.h}`, `mt792x.h`,
`mt76_connac_mcu.{c,h}`. Line numbers below are v6.11's.

---

## 1. Survey — the facts each rung stands on

**PCI.** One function, BAR0 only (`pcim_iomap_regions(BIT(0))`, pci.c:316). Linux sets `PCI_COMMAND_MEMORY` only when
clear (pci.c:320-324) and bus master after it. The BAR window is 2 MiB: offsets below `0x200000` are used directly
(`__mt7925_reg_addr`, pci.c:160).

**Address map.** The chip's addresses reach BAR0 three ways (pci.c:66-185):
* the fixed map (pci.c:102-157), e.g. `0x7c060000` conn_host_csr_top -> BAR+`0x0e0000`, `0x7c000000` CONN_INFRA ->
  BAR+`0x0f0000`, `0x7c020000` CONN_INFRA wfdma -> BAR+`0x0d0000`, `0x00400000` WF_MCU_SYSRAM -> BAR+`0x080000`;
* WFDMA0 directly at BAR+`0xd4000` (`MT_WFDMA0_BASE`, mt792x_regs.h:260);
* the L1 remap for `0x18000000-0x18c00000`, `0x70000000-0x78000000`, `0x7c000000-0x7c400000` not in the fixed map:
  write `addr >> 16` into bits 31:16 of `MT_HIF_REMAP_L1` (BAR+`0x155024`), read back to push it, then access
  BAR+`0x130000 + (addr & 0xffff)`; the selector is restored on the next access (regs.h:70-74). Anything else goes
  through the L2 remap (`MT_HIF_REMAP_L2` BAR+`0x0120`).

**Ownership.** `MT_CONN_ON_LPCTL` `0x7c060010` (BAR+`0xe0010`): SET_OWN bit 0, CLR_OWN bit 1, OWN_SYNC bit 2
(1 = firmware owns, 0 = driver owns; mt792x_regs.h:469-472). Driver-own = write CLR_OWN, poll OWN_SYNC to 0;
firmware-own = write SET_OWN, poll OWN_SYNC to 1 (mt792x_core.c:810-821, 857-864). Firmware state:
`MT_CONN_ON_MISC` `0x7c0600f0` (BAR+`0xe00f0`) bits 1:0 = FW_PWR_ON | FW_N9_ON, 3 = N9 ready (mt792x_regs.h:474-477).

**Probe order (pci.c:379-407).** fw-own, then driver-own; CHIPID `0x70010200` / REV `0x70010204`
(mt792x_regs.h:394-395, both through the L1 remap); `MT_HW_EMI_CTL` `0x18011100` SLPPROT_EN bit 1; WFSYS reset
(`0x7c000140` = BAR+`0xf0140`: clear bit 0, 50 ms, set it, poll INIT_DONE bit 4 up to 500 ms; mt792x_dma.c:357-367);
then `mt7925_dma_init`.

**WFDMA.** `GLO_CFG` BAR+`0xd4208` (TX_DMA_EN b0, TX_BUSY b1, RX_DMA_EN b2, RX_BUSY b3), `RST` BAR+`0xd4100`.
Disable: clear the EN and OMIT bits, poll both BUSY clear up to 100 ms, `GLO_CFG_EXT0` DMASHDL off and
`MT_DMASHDL_SW_CONTROL` (`0x7c026004`) bypass, then toggle RST's LOGIC and DMASHDL_ALL bits (mt792x_dma.c:253-282).
Rings (mt7925.h:12-17, 90-100; pci.c:208-262): TX band0 = ring 0 (2048), MCU WM = TX ring 15 (256), FWDL = TX ring 16
(128), RX MCU events = RX ring 0 (512), RX data = RX ring 2 (1536). TX ring registers at BAR+`0xd4300`, RX at
BAR+`0xd4500` (16 bytes each: base, count, CPU index, DMA index). `TX_RING0_EXT_CTRL` (BAR+`0xd4600`) = 4. Enable:
prefetch config, `RST_DTX_PTR`/`RST_DRX_PTR` = ~0, delay-int 0, then GLO_CFG feature bits and TX/RX_DMA_EN
(mt792x_dma.c:126-156).

**MCU boot (mt76_connac_mcu.c).** Patch: `PATCH_SEM_CONTROL` get -> `PATCH_IS_DL` (resident, skip) or
`PATCH_NOT_DL_SEM_SUCCESS`; per section of the big-endian patch header, `PATCH_START_REQ` (the 7925's patch addresses
`0x900000` / `0xe0002800`) or `TARGET_ADDRESS_LEN_REQ` {addr, len, mode} then `FW_SCATTER` in 4 KiB chunks on the FWDL
ring; `PATCH_FINISH_REQ`; semaphore release (:3020-3101; :53-78). RAM code: the trailer at the end of the file names
`n_region` regions; per region `TARGET_ADDRESS_LEN_REQ` + `FW_SCATTER`; then `FW_START_REQ` {option, override addr}
(:2869-2923). Then poll `CONN_ON_MISC` for N9_RDY up to 1.5 s (mt792x_core.c:878-912). Corrected by MT7925S4 (measured
against mt7925/pci_mcu.c:8-24 and mcu.c:3135-3211): every command except `FW_SCATTER` is sent on the WM ring (TX ring 15)
behind the legacy connac2 64-byte `mcu_txd` (TXD0 = length | PKT_FMT cmd | Q_IDX 0x20, TXD1 HDR_FORMAT cmd, length at +32,
pq_id 0x8000, cid, pkt_type 0xa0, set_query 3, 4-bit sequence 1..15), not the uni txd; `FW_SCATTER` goes on the FWDL ring
(16) as raw bytes with no TXD and gets no event (linux sends it with wait_resp = false). Only the semaphore, init_download,
`PATCH_FINISH_REQ` and `FW_START_REQ` are answered, on RX ring 0 (event header 32 bytes, length at +32, eid +36, seq +37,
status +40).

**MAC and EEPROM.** `mt7925_run_firmware`: load, then `get_nic_capability` (UNI `CHIP_CONFIG`; the MAC address is the
`MT_NIC_CAP_MAC_ADDR` TLV, mcu.c:769-830, 872-891); efuse buffer mode via UNI `EFUSE_CTRL` (0x2d, mcu.c:1297-1317).

## 2. The seam — one station layer over two radio backends

The MT7925 MCU does **not** run the MLME. Linux drives it as a mac80211 SoftMAC (`.sta_state = mt76_sta_state`,
`.tx = mt792x_tx`, `.hw_scan`, `.mgd_prepare_tx`, `.set_key`; main.c:2079-2135): the host builds authentication and
association frames and sends them on the TX ring behind a connac TXD. The MCU offloads scanning (UNI `SCAN_REQ` 0x16),
keeps per-link state (`DEV_INFO_UPDATE` 0x01, `BSS_INFO_UPDATE` 0x02, `STA_REC_UPDATE` 0x03), holds the keys (set_key
into STA_REC) and can translate received frames to 802.3 (`RX_HDR_TRANS` 0x12).

So `wifi_core::ieee80211`'s frame builders and judges serve both radios. What differs is below them — the S6 trait
(owed, named here, not built):

| call | BCM4331 (`wifi/**`) | MT7925 |
|---|---|---|
| `mac()` | SPROM/OTP read | NIC capability TLV (S5) |
| `tune(ch)` | PHY retune | channel via BSS_INFO / ROC |
| `scan(req)` | dwell + B951's probe | UNI SCAN_REQ, results as beacon/probe-response frames on RX |
| `tx_mgmt(frame)` | TX ring, frame from `wifi_core` | TX ring + connac TXD, frame from `wifi_core` |
| `join(bss)` / `leave()` | MAC registers (BSSID, RX filter) | DEV_INFO / BSS_INFO / STA_REC |
| `tx_data(eth)` / `rx()` | `RxFrame::Dot11` (BP-net-16's codec) | `Dot11` or `Ethernet` (HDR_TRANS) |
| `set_key(...)` | (S10, owed) | STA_REC security TLV |

The data path reaches smoltcp through `RawNic` (BP-net-1), like every NIC.

| **S2** driver-own and the chip id (MT7925S2, Z11) — in the tree, unflown | Zenbook only (`hw::platform()`), the pass after S1: driver-own (LPCTL CLR_OWN, OWN_SYNC polled to 0, 4 tries x 50 ms = 200 ms); CHIPID/REV through the L1 remap with the selector restored; firmware-own given back only when S2 took it | LPCTL CLR_OWN <=4 (none when found driver-owned), HIF_REMAP_L1 x2 (select, restore), LPCTL SET_OWN <=4 (only when S2 took own) | §6 |
| **S3** WFSYS + WFDMA init (MT7925S3, Z15) — in the tree, unflown | the pass after a clean S2 line (selector restored, own given back, CHIPID live); own taken as S2; EMI SLPPROT through the L1 remap; WFSYS reset (RST_B low 50 ms, INIT_DONE polled up to 500 ms); WFDMA0 disabled to idle (BUSY polled up to 100 ms), DMASHDL bypassed, LOGIC/DMASHDL_ALL reset pulsed; ONE TX ring (FWDL, ring 16) and ONE RX ring (MCU events, ring 0), depth 32, zeroed, every ctrl DMA_DONE, no RX buffer handed, no TX posted; prefetch table, DTX/DRX index reset, GLO_CFG features then TX/RX_DMA_EN; own given back only when taken. | **S4** MCU boot (MT7925S4, Z17) — in the tree, unflown | the pass after a clean S3 line; own taken again (linux's fw_pmctrl-then-drv_pmctrl cycle); S3's ring bases read back (`held=`); MT_PCIE_MAC_PM L0S_DIS (BAR0+0x10194 bit 8); patch and RAM code read from the ESP by the S1 reader (`fw_dir` + `fw_read`, pin verdict `ok` required); GLO_CFG disabled, rings 16 and 15 and RX 0 armed (RX 0 with 31 x 2 KiB buffers, CPU index 31), WFDMA0 enabled; PCI COMMAND saved and bus master set (the ONE config write); `PATCH_SEM_CONTROL` get (1 = resident, 2 = go); per patch section init_download + raw FW_SCATTER chunks (each waited on by its TX completion, 100 ms); `PATCH_FINISH_REQ` (status 0); semaphore release (status 3); per RAM region (NON_DL skipped) init_download + scatter; `FW_START_REQ` {option, override}; CONN_ON_MISC polled for N9_RDY up to 2 s; bus master kept only when FW_START was acked AND N9 is ready, else COMMAND restored; own given back only when taken. | S6 radio backend trait (owed) | §2's trait; the BCM4331 path moved under it unchanged | none (refactor) | the BCM4331 wire unchanged |
| S7 scan (owed) | UNI SCAN_REQ from the station task; results into the station layer | WM ring | the station layer's scan line |
| S8 auth/assoc (owed) | DEV_INFO/BSS_INFO, then BP-net-15's frames via `tx_mgmt`, then STA_REC | TX + WM rings | the BP-net-15 judges' lines |

## 5. Wire (S1)

The probe runs from the three storage-ready passes (`main.rs`, beside the Broadcom service call), after
`boot::services_gate("wifi")` and after the program-source volume is up (or 30 s). Once per boot:

```
[mt7925] probe at=<bus>:<dev>.<fn> id=14c3:<7925|0717> rev=<0xNN> bar0=<0x…|unassigned> mem=<on|off> lpctl=<0x…|-> own=<fw|drv|-> fwstate=<0-3|-> fw=<present:2|present:1|absent|no-esp|no-volume> patch_sha=<ok|mismatch|unpinned|-> ram_sha=<ok|mismatch|unpinned|-> -> parked
```

preceded, for a member that is not `ok`, by
`[mt7925] fw <file> role=<patch|ram> bytes=<n> sha256=<hex|-> -> <unpinned|pin-mismatch|too-large|unreadable>`.
A machine without the radio (QEMU, the rMBP) prints nothing. `id=` is the PCI identity; the silicon CHIPID is S2's.

## 6. Wire (S2)

S2 runs once, on the storage-ready pass after the S1 line, only when `hw::platform()` reads the Zenbook UM5606W
(`drivers/mt7925.rs` file tail, `s2`). QEMU and the rMBP print nothing (no `14c3:7925` in the registry). Linux reads
CHIPID/REV right after driver-own and before the WFSYS reset (mt7925/pci.c probe), so the reset stays S3's. Exactly one of:

```
[mt7925] s2 own=<ok|found> chip=<0x7925> rev=<0x…> remap=<restored|stuck> rel=<fw|found|timeout> -> parked
[mt7925] own -> REFUSED lpctl=<0x…> waited=<ms> rel=<fw|timeout>
[mt7925] s2 -> NOT ATTEMPTED why=<platform=<token>|mem-off|unassigned|unmapped|dead>
```

`own=ok rel=fw` is the expected bench line (S1 reads `own=fw`: firmware owns at boot): S2 took own and gave it back.
`own=found rel=found` means the driver already owned the chip and S2 wrote no LPCTL. `chip=` is the raw CHIPID word
(expected `0x7925`), `rev=` the raw REV word (linux keeps its low byte). `remap=stuck` means the selector did not read
back as saved. Device writes are bounded: LPCTL at most 8, HIF_REMAP_L1 exactly 2; no config write, no DMA, nothing
uploaded, nothing transmitted.

**S3** (MT7925S3, Z15; the second file-tail block, `s3`) runs on the pass after an `s2 own=` line that read
`remap=restored`, `rel=` other than `timeout` and a live CHIPID; any other S2 outcome prints no s3 line. Exactly one of:

```
[mt7925] s3 emi=<0x…> remap=<restored|stuck> wfsys reset=<ok|timeout> waited=<ms> rst=<0x…>
  then  [mt7925] s3 wfdma tx=<0x…> rx=<0x…> cnt=32 rb=<ok|bad> glo=<0x…> rel=<fw|found|timeout> -> parked
  or    [mt7925] s3 wfdma -> NOT ATTEMPTED why=<wfsys-timeout|dma-busy glo=0x…|no-memory|dma-high> rel=<fw|found|timeout>
[mt7925] s3 -> NOT ATTEMPTED why=<unmapped|own lpctl=0x… rel=<fw|timeout>>
```

The expected bench pair is `reset=ok` (INIT_DONE, bit 4 of `rst=`, set) then `rb=ok` with `glo=` carrying TX_DMA_EN and
RX_DMA_EN (bits 0 and 2) over the feature bits. `tx=`/`rx=` are the ring physical addresses (the identity map; a ring at
or past 4 GiB is refused as `dma-high` before any ring register is written: one 32-bit base register, linux's 32-bit
DMA mask). `rb=` reads back both rings' base and count. The engines are left enabled over empty rings with bus master
off, so nothing is fetched; S4 sets bus master, re-takes own and checks the state the firmware-own handoff left.

**S4** (MT7925S4, Z17; the third file-tail block, `s4`) runs on the pass after an `s3 wfdma` line with `rb=ok`, `rel=` other
than `timeout` and TX/RX_DMA_EN in `glo=`. QEMU and the rMBP print nothing. Exactly one of:

```
[mt7925] s4 held=<kept|lost> patch=<n|resident> ram=<n> fw_start=<ok|timeout> n9=<ready|timeout> bm=<on|restored> rel=<fw|found|timeout> -> parked
[mt7925] s4 -> NOT ATTEMPTED why=<unmapped|own lpctl=0x…|no-fw|no-memory|dma-high|dma-busy glo=0x…|rb|hdr|sem|dl at=<i>|scatter at=<i>|finish|rx-full> bm=<off|restored> rel=<fw|found|timeout>
```

The expected bench line is `held=kept patch=188192 ram=1390712 fw_start=ok n9=ready bm=on`. `held=` compares the ring-16 and
ring-0 base registers with the addresses S3 printed (own was given back in between). `patch=resident` means the semaphore
answered "already downloaded". `bm=on` is the only state in which PCI bus master stays set; `bm=restored` means the saved
COMMAND word was written back (FW_START not acked or N9 not ready, or a refusal after bus master went on); `bm=off` means
it was never set. A line without `fw_start=` means FW_START was never sent. `rb` is S4's own word for a ring read-back or
GLO_CFG enable that did not hold; `rx-full` means the 31 event buffers were used (no recycling yet). Owed to later rungs:
S3b's remainder (TX ring 0, RX data ring 2, interrupt enables, WFDMA_DUMMY_CR), S4-RECYCLE, S5 (NIC capability, MAC).
