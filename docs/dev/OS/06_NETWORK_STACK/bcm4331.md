# BCM4331 — the native AirPort driver ladder (path A)

**Target:** Broadcom BCM4331 (`14e4:4331`), the AirPort Extreme radio in the 2012 15" Retina
MacBook Pro (MacBookPro10,1). 802.11a/b/g/n, 3x3:3, PCIe, **SoftMAC**.

**Decision on record:** Peter chose **path A — own a native driver**, with the sizing understood
(8,000–15,000 lines, downloadable microcode, HT-PHY register tables). The alternatives (USB
Ethernet, AR9271 with free firmware, a `brcmsmac`-covered card swap) are recorded in
`~/unaos-bench/scratch/gr20/pci-census-report.md` §6.4 and are not re-argued here.

This document is the ladder. Each stage is independently boot-testable, carries its own witness and
its own falsifiable predicate, and names what it writes. The discipline is
`docs/dev/GEMINI/video/iGUI/LADDER-igpu-bringup.md`'s: a stage that cannot be refuted by a serial
line is not a stage.

---

## 0. Ground truth — what we actually know today

Two facts, both from our own kernel, neither assumed.

**From GR20's PCI census (`arch/x86_64/pci.rs::full_census`, `UNAOS_PCICENSUS=1`):** the
class-0x02 device this kernel has named on every rMBP boot —

```
:: x86_64 PCI: Found network controller (class 0x02) vendor 0x14e4 at 3:0.0 ::
:: x86_64 PCI: non-Intel NIC (0x14e4) — no e1000 driver, skipping ::
```

— is matched by `PciScanner::find_device(0x02, 0x00)`, i.e. subclass **0x00 = Ethernet**, and that
helper returns on its first hit. `14e4:16bc` at `3:0.1` is the BCM57765 SDXC reader; `3:0.0` is that
combo chip's Gigabit Ethernet MAC, behind a laptop with **no Ethernet jack**. A BCM4331 reports
subclass **0x80**. It could never have matched. The radio has never been examined by this OS.

**From GR20's BCMA recon (`drivers/bcma.rs`, `UNAOS_BCMARECON=1`):** stage S0 below. Read-only, and
its main structural finding is stated in §1.

**From Boot AJ (metal, first S1 flight) — the chip answers.** One config write to `cfg:0x80` and
ChipCommon reads `chipid=0x13924331`: a BCM4331, chip rev 2, package 9, **socitype 1 (AI/BCMA — it
has an enumeration ROM)**, PMU present, with the EROM at backplane `0x18107000`. The window
hypothesis in §1 is confirmed on metal and the firmware pre-image was restored byte for byte. See
S1/S1b.

**From Boot AF (metal, 2012 rMBP, first S0 flight):**

```
:: bcma: device bdf 4:0.0 14e4:4331 rev=02 ssid=106b:00ef irq=0 pin=A cmd=0x0006 (mem-decode=1 busmaster=1) matches=1 ::
:: bcma: power cap@0x40 pmcsr=0x4008 state=D0 ::
:: bcma: bar0=0xc1900000 raw=0xc1900004 type=mem64 prefetch=0 maplen=0x2000 bar0_win(cfg:0x80)=0x18001000 bar0_win2(cfg:0xac)=0x18101000 ::
:: bcma: REFUSED stage=chipcommon reason=not-decoding chipid=0xffffffff — BAR0 reads all-ones ::
:: bcma: end ok=0 stage=chipcommon elapsed=5ms ::
```

Established, and none of it assumed:

* **The radio exists and is ours to drive.** `14e4:4331` at `4:0.0`, board id `106b:00ef` (Apple),
  behind bridge `0:28.1` (`8086:1e12`, `sec=4 sub=4`, `cmd=0x0007`). One match on the whole machine.
* **It is awake and decoding.** `pmcsr=0x4008` = **D0**, `No_Soft_Reset=1`, `PME_En=0`,
  `PME_Status=0`. `COMMAND=0x0006` = memory decode ON, bus master ON. Neither "asleep" nor
  "decode disabled" is available as an explanation for anything below.
* **BAR0 is `0xc1900000`, 64-bit, non-prefetchable**, high dword zero. The census had predicted
  exactly this.
* **The BAR0 window was NOT on ChipCommon.** `cfg:0x80 = 0x18001000` and `cfg:0xAC = 0x18101000` are
  `BCMA_ADDR_BASE + 1*0x1000` and `BCMA_WRAP_BASE + 1*0x1000` — the (`core->addr`, `core->wrap`)
  pair Linux's `bcma_host_pci_switch_core()` writes for **core index 1**, which on a BCM4331 is the
  d11 802.11 core. Apple's firmware left the selector on the radio core. §1's assumption that
  firmware parks the window at the enumeration base is **false on this machine**.
* **The all-ones was therefore not a verdict about the function**, and reporting it as
  `reason=not-decoding` was a defect in our own instrument: stage 5 tested "all-ones" before it
  tested "is the window even on ChipCommon", so the `window-elsewhere` refusal that existed in the
  file could never fire whenever the off-window core was unreadable. Order corrected (window first).
* **It was not a mapping fault of ours either.** The map wire line
  `:: x86 mmio-map: 0xc1900000..0xc1902000 uc=1 (PAT PA3) wc-kept=0 ::` shows the window retyped in a
  single 2 MiB leaf — the *same* leaf `sdhc`'s BAR at `0xc1820000` lives in, and `sdhc` read its
  registers successfully later in the same boot through that leaf. Same VA range, same PAT typing,
  one works. `translate()` passed, `BAR1` was read and honoured, `maplen=0x2000` is the full
  architecturally-defined extent of BAR0 for this driver model (see §S0).

**What Boot AF could NOT answer, and what was added so Boot AG can.** The census printed `0:28.1`'s
bus-number triple (`pri=0 sec=4 sub=4`) but not its **forwarding windows** — so nothing in the
capture could say whether the bridge above the radio actually forwards `0xc1900000` downstream. A
device whose BAR falls outside its bridge's memory window reads all-ones no matter how correctly the
driver maps it, and that hypothesis was untestable from the evidence we had.
`census_print_bridge_windows()` now prints, for every header-type-1 function, the I/O window
(including the 32-bit upper halves at `0x30`), the non-prefetchable memory window, the prefetchable
memory window (including the 64-bit upper dwords at `0x28`/`0x2C`), and the bridge's **secondary
status** — the ledger where a master-abort on an unclaimed downstream read leaves a mark. `closed`
is rendered explicitly for the architectural `base > limit` encoding rather than as an inverted
range. Read-only, three config reads plus two conditional ones.

Verified under QEMU against a machine whose answer is known independently: with a `pcie-root-port`
inserted, the census prints

```
bdf 0:8.0 1b36:000c … pri=0 sec=1 sub=1 bar0=mem32@0x81285000 io=[0x6000,0x6fff]/16 mem=[0x81000000,0x811fffff] pref=[0xc000000000,0xc01fffffff]/64 secsts=0x0000
bdf 1:0.0 8086:10d3 … bar0=mem32@0x81020000 bar1=mem32@0x81000000 bar2=io@0x6000 bar3=mem32@0x81040000
```

Every downstream BAR falls inside the matching window and the 64-bit prefetchable decode is exercised.

**Prediction for Boot AG:** `0:28.1`'s memory window contains `0xc1900000`. If it does not, that is
the answer and it outranks everything in §1.

Everything else in this document is a plan, and is marked as such.

## 1. The structural finding that shapes the whole ladder

**A BCMA part behind PCIe exposes exactly ONE backplane core through BAR0 at a time, and the
selector is a PCI *config* register.**

BAR0 is a small window. Its first 4 KiB decode to whatever backplane address sits in **PCI config
register `0x80`** (`BCMA_PCI_BAR0_WIN`); the second 4 KiB decode to the address in `0xAC`
(`BCMA_PCI_BAR0_WIN2`, the wrapper window). Linux's `bcma_scan_switch_core()` writes exactly these
two registers and nothing else in order to move from core to core.

**Boot AF corrected the second half of this section.** It used to say "firmware leaves the window
parked at the ChipCommon enumeration base `0x18000000`". It does not. Apple's firmware left
`cfg:0x80 = 0x18001000` — the **d11 802.11 core**, core index 1 — with `cfg:0xAC` on its matching
wrapper. There is therefore **no core at all that is reachable read-only** on this machine, and
Linux agrees this is normal: `bcma_bus_scan()` calls `bcma_scan_switch_core(bus, BCMA_ADDR_BASE)`
*unconditionally* before it reads `BCMA_CC_ID`. It never assumes where firmware left the selector.

The consequences, and they are the entire reason the ladder starts where it does:

| Fact a driver needs | Where it lives | Reachable read-only? |
|---|---|---|
| PCI identity, ssid, D-state, COMMAND, BARs, capabilities | PCI config space | **yes** |
| `BAR0_WIN` / `BAR0_WIN2` — *which core is in the window* | cfg `0x80` / `0xAC` | **yes** |
| the selected core's wrapper: `IOCTL`, `IOST`, `RESET_CTL`, `RESET_ST` | BAR0 `+0x1000` | **yes** — added after Boot AF |
| chip id / rev / package / `ncores` / chip type | ChipCommon `0x00` | **no on this machine — needs cfg `0x80`** |
| capabilities (SPROM present, OTP size, PMU) | ChipCommon `0x04` | **no — same reason** |
| OTP status + which subregions are programmed | ChipCommon `0x10` | **no — same reason** |
| EROM backplane pointer | ChipCommon `0xFC` | **no — same reason** |
| SPROM shadow (MAC, board rev, board flags, PA cal) | ChipCommon `0x800`/`0x830` | **no — same reason**, plus §S2's caveat |
| **the EROM itself — the core inventory** | backplane, ~`0x18010000` | **no — needs cfg `0x80`** |
| **the 802.11 (d11) core registers** | backplane, address from the EROM | **no — needs cfg `0x80`** |
| **PHY type / revision** (`d11 + 0x3E0`) | inside the d11 core | **no — needs cfg `0x80`** |
| OTP *contents* | via a read command written to ChipCommon `0x18` (OTPP) | **no — needs a write** |

So **one 32-bit config write gates the entire backplane** — and after Boot AF that is not a claim
about convenience but the literal state of the machine: the read-only ceiling is PCI config space
plus one core-wrapper's worth of registers, and nothing else. S1 is defined as "make that one write,
and nothing else."

**The exact write, named and not made:**

```
cfg:0x80  (BCMA_PCI_BAR0_WIN, bdf 4:0.0)  <-  0x18000000   (32-bit)
```

Why this one and not another: it is the *smallest* possible unblocking write in the whole ladder. It
touches no backplane register, changes no device state, resets nothing, and is a pure address-decode
selector on the host side of the PCIe function. Linux issues it before it reads anything at all. It
is nevertheless a write, so S0 stops here and reports it.

**One discipline it must carry (S1's, recorded here because Boot AF is why we know it matters):**
the pre-image of `cfg:0x80` on this machine is **not** `0x18000000` — it is `0x18001000`. A stage
that "restores" the window to the enumeration base because that is what it assumed firmware left
would silently change the machine for every later boot stage. The restore must push the value it
actually read.

## 2. The staged ladder

Dependencies are strictly linear: each stage needs every stage above it. Where a stage is
**all-or-nothing** it is marked; those are the stages that cannot be developed incrementally, where
a wrong value gives silence rather than a diagnostic.

| # | Stage | Writes | All-or-nothing? |
|---|---|---|---|
| S0 | Recon | nothing | no — pure evidence |
| S1 | Backplane window + EROM walk (**window CONFIRMED on metal, Boot AJ; walk corrected in S1b**) | 1 config register (cfg:0x80), pre-image saved + restored | no |
| S1c | WIFI-L0: reach the d11 core, read its identity + PHY type (**no new write target — the same cfg:0x80 selector**) | none beyond S1's | no — pure evidence |
| S2r | WIFI-S2: read the board IDENTITY + CAPABILITY from the SPROM shadow (**no new write target — the same cfg:0x80 selector**) | none beyond S1's | no — pure evidence |
| S2 | Board identity: SPROM contents / OTP calibration (the WRITE path) | ChipCommon control | no |
| S3 | Core enable: reset + clocks on the d11 core — **REACHABILITY SATISFIED by the boot state (Boot AO): `bcma_core_enable` is a NO-OP on this part as it arrives. What remains is reset-to-known-state, and it is S4's prologue, not a stage** | **none for reachability**; the reset-to-known-state writes are named in S4 | no |
| S4a | WIFI-S4a: identify the **resident** microcode through the SHM window (**the first MMIO write in this driver — `SHM_CONTROL` only**) | `SHM_CONTROL` (d11+0x160), an address-window register; nothing else | no — pure evidence, with one write to reach it |
| S4 | Firmware (microcode) upload | d11 shared memory | **partly** — the handshake is binary |

| S7 | MAC / station layer (scan, auth, assoc) | templates, SHM, TX rings | no |
| S8 | WPA2-PSK | none new — crypto + EAPOL | no |

### S0 — Reconnaissance (`UNAOS_BCMARECON=1`) — **flown, Boot AF; revised for Boot AG**

**Writes:** none. Config-space reads and BAR0 reads only. Mapping BAR0
(`arch::memory::map_mmio_window`) is a page-table edit; the device sees nothing.

**Does:**
1. Sweeps all buses/devices/functions (MF-gated) for class `0x02` **subclass `0x80`**, counting
   every match. Prints vendor:device, bdf, revision, subsystem id, IRQ/pin, COMMAND, plus the
   existing `[PCI-PROBE]` capability dump.
2. Reads the PM capability's PMCSR and refuses the BAR if the function is not in D0. **Full** PMCSR
   decode (power state, `No_Soft_Reset`, `PME_En`, `PME_Status`, `Data_Select`, `Data_Scale`), so a
   reader can check the D-state claim rather than take it.
3. Refuses the BAR if COMMAND bit 1 (memory decode) is clear.
4. Decodes BAR0 raw (64-bit/prefetchable per the census's prediction, with `BAR1` printed as the
   high dword it actually read), maps `0x2000` of it UC, verifies the mapping with `translate()`.
5. Reads `BAR0_WIN` (cfg `0x80`) and `BAR0_WIN2` (cfg `0xAC`) and **decodes both as core / wrapper
   indices on the standard grid** (`window-decode core-index=… wrap-index=… paired=…
   on-enum-base=…`). A window off the grid is printed `off-grid`, never as an index.
6. **Stage 4b (new):** reads the selected core's wrapper through BAR0`+0x1000` — `IOCTL` (`0x408`),
   `IOST` (`0x500`), `RESET_CTL` (`0x800`), `RESET_ST` (`0x804`) — and applies Linux's
   `bcma_core_is_enabled()` rule (`clk` set, `fgc` clear, not in reset). This is the discriminator
   Boot AF lacked; see the prediction below.
7. **Refuses to decode ChipCommon if the window is not at `0x18000000`, tested BEFORE the all-ones
   test.** That order is the Boot AF fix: "the window is elsewhere" is a fact about `cfg:0x80` that
   needs no MMIO read to be true, whereas "all-ones" only means anything once BAR0+0 is known to be
   ChipCommon. Reversed, an off-window core in reset gets reported as a dead function.
8. With the window on the enumeration base: prints ChipCommon raw first, then decoded — chip
   id/rev/pkg/`ncores`/type, capabilities, capabilities-ext, chip status, EROM pointer.
9. Tests EROM containment in the live window. Walks it if reachable; otherwise emits
   `REFUSED stage=erom reg=cfg:0x80` **with the EROM's address**, which is the value S1 must write.
10. Reports SPROM presence; if present, dumps 220 shadow words and decodes revision + a MAC
    candidate with an explicit `PLAUSIBLE` / `SUSPECT` / `NO-DATA` verdict. Reports OTP size and
    which subregions are programmed; refuses OTP *contents* naming OTPP.
11. Refuses the PHY version read, naming cfg `0x80` and `d11+0x3E0`.

**On `maplen=0x2000`.** Not a guess and not a BAR size. On a BCMA PCIe host BAR0 is exactly two
4 KiB apertures and Linux's own accessors say which is which: `bcma_host_pci_read32` reads
`mmio + offset` (the core window, cfg `0x80`) and `bcma_host_pci_aread32` reads
`mmio + 1*BCMA_CORE_SIZE + offset` (the wrapper window, cfg `0xAC`). No bcma accessor indexes past
`2*BCMA_CORE_SIZE`, so `0x2000` is the whole extent this driver model defines. The BAR's **physical**
size remains unknown — reading it needs the write-all-ones/read-mask/restore sizing dance, which
this arc does not perform — but the inequality runs the safe way: both windows exist and are used,
so the true size is at least `0x2000` and mapping `0x2000` cannot map past the BAR.

**Also fixed after Boot AF:** the `core_name()` table used by the EROM walker was wrong on nearly
every id past ChipCommon (it named `0x812` "mips-33" and `0x820` "d11(802.11)"; Linux's
`bcma.h` has `BCMA_CORE_80211 = 0x812` and `BCMA_CORE_PCIE = 0x820`). Nothing had run the walk yet,
so no capture could have caught it — and it would have sent S3 at the PCIe core while calling it
the radio. Retranscribed in full.

**Proves it took:** `:: bcma: end ok=1 stage=chipcommon chip=0x4331 … ::`.

**Failure on serial:** every stage has a `REFUSED`/`no-device` line naming its reason; the closing
`ok=0 stage=<name>` says which one stopped it. `no-device` is the expected QEMU reading and is also
the reading that would refute the whole premise on metal.

**Falsifiable prediction for the next metal boot (Boot AG), stated before it flies.** With the
window still at `0x18001000`, S0 must now print `REFUSED … reason=window-elsewhere` and **not**
`reason=not-decoding` — anything else convicts the reorder. And stage 4b splits the two live
explanations of Boot AF's all-ones:

| Boot AG wrapper reading | What it establishes | What S1 becomes |
|---|---|---|
| wrapper answers (not all-ones), `in-reset=1` or `clk=0` | The function decodes; BAR0+0 read all-ones because the window sits on a d11 core that is held in reset / clock-gated. Nothing upstream is wrong. | The single `cfg:0x80 <- 0x18000000` write, as planned. S3's job (releasing d11 reset) is already half-mapped by this wrapper. |
| wrapper answers, `core-enabled=1` | The function decodes *and* the core is running, so all-ones at BAR0+0 is a property of that core's register 0, not of reachability. | Same write; but re-examine what core index 1 actually is before trusting the grid. |
| wrapper ALSO all-ones | The block that survives reset is silent too, so "core in reset" is refuted. Blame moves upstream: the PCIe link, or `0:28.1` not forwarding `0xc1900000`. | Blocked on the bridge-window census line for `0:28.1` (§0), not on `cfg:0x80`. |

**Bounds:** structural entry cap on the EROM walk (`EROM_MAX_ENTRIES = 512`), plus a TSC deadline
(`now_cycles()` / `hw_wait_budget()`) on the walk and the SPROM dump. Never `arch::ms()` — the APIC
tick does not advance with interrupts masked, and this runs inside `pci::init`.

### S1 — Backplane window + EROM walk — **FLOWN, Boot AJ: window CONFIRMED, walk fixed in S1b**

**Boot AJ result, in one line.** The window hypothesis is **confirmed** and the unwind held:

```text
:: bcma-s1: WROTE cfg:0x80 old=0x18001000 new=0x18000000 readback=0x18000000 took=1 ::
:: bcma-s1: cc-raw chipid=0x13924331 cap=0x58500000 cap_ext=0x00000001 chipstatus=0x00000002 erom=0x18107000 ::
:: bcma-s1: RESTORE cfg:0x80 <- pre-image 0x18001000 readback=0x18001000 restored=MATCH ::
:: bcma-s1: end ok=1 stage=window chip=0x4331 window-hypothesis=CONFIRMED restore=MATCH wrote-cfg80=1 ::
```

One 32-bit config write turned a function that had read `0xffffffff` for the life of the project
into a chip that answers with its own identity, and the recorded pre-image went back byte for byte.
The EROM pointer — `0x18107000`, the address the whole rest of the ladder hangs off — is now a
measured value rather than an assumption.

**The one thing that did not work:** the EROM walk found zero cores. That is S1b, below; the
walk's defect was entirely in this file's transcription of the entry format, and Boot AJ's own
abort line was enough to convict it.

**Status.** Written in `drivers/bcma.rs` as `s1_window_walk()`, gated by the `bcmaS1` cargo feature
(`UNAOS_BCMAS1=1`). The `bcmaS1` feature **implies `bcmarecon`**, so S1 rides on top of S0: `recon()`
runs the read-only pass first (its `REFUSED … window-elsewhere` line is unchanged and remains S0's
deliverable), then — only when the knob is armed — the S1 block, prefixed `:: bcma-s1: … ::`. Riding
on `bcmarecon` is also what lets S1 reuse S0's `find_wifi()`/`find_cap()`/BAR-map helpers and share
the existing x86-only module gate and the single call site in `arch/x86_64/pci.rs` (untouched by this
arc). Gate green (11 cfg legs, both arches); QEMU exercises only the `no-device` refusal (it models no
BCM4331), so the write path's first execution is on metal. Default OFF ⇒ no S1 code and zero
`bcma-s1` witness strings; media byte-identical.

**The implemented sequence** (each step a witness that can say NO; no early return between the first
window move and the restore):

1. **Guard, then record the pre-image.** The window write is issued ONLY when both the Broadcom
   vendor id (`0x14e4`) **and** the 4331 device id (`0x4331`) read back — a stray class-0x02/sub-0x80
   function, or a future QEMU model, is refused with no write. Then cfg `0x80` and cfg `0xAC` are read
   and **stored**; the `0x80` value is the sole restore target. `0x18000000` is never used as a
   restore value anywhere in the stage.
2. **Prove the unwind before moving anything.** The pre-image is written *back to itself* (a no-op:
   the value cfg `0x80` already holds, so the window does not move and the device sees no state
   change) and read back. This exercises the exact write+readback the final restore depends on; a
   mismatch aborts with the window still on the firmware value (`REFUSED stage=unwind-selftest`). This
   is the igpu-lane discipline: a self-test, not a bare write.
3. **The write.** `cfg:0x80 <- 0x18000000` — Linux's `bcma_scan_switch_core(BCMA_ADDR_BASE)`.
   Witnessed with old, new, and readback.
4. **Read ChipCommon** through BAR0+0: `chipid` (low 16 = `0x4331` expected), rev/pkg/`ncores`/type,
   capabilities, cap-ext, chip status, the EROM pointer. If `chipid` is **still `0xFFFFFFFF`** after
   the window move, that **REFUTES** the window hypothesis (the move was not the blocker; blame is
   upstream — link or the `0:28.1` bridge window) and is printed as a finding, never a silent pass.
5. **Walk the EROM.** A second window write points cfg `0x80` at the (page-aligned) EROM base; the
   recon's `walk_erom()` is reused verbatim; the walk's core count is cross-checked against
   ChipCommon's `ncores`.
6. **Restore.** `cfg:0x80 <- pre_win` (the **stored** value), read back, and witnessed
   `restored=MATCH`/`FAILED` by comparing to the stored pre-image — **not** to `0x18000000`. A failed
   restore is a hard finding (the radio's window is left moved for the next stage to misread).

The rest of this section is the design as specified before implementation; the code follows it, with
the one deviation that S1 writes **only** cfg `0x80` (not `0xAC`) — the wrapper-window write is
deferred to the stage that actually needs wrapper state, keeping S1's write surface at the single
selector.

**Depends on — REVISED after Boot AF.** The old dependency was "S0 reporting `ok=1` and an EROM
pointer". That is now unreachable: on this machine S0 cannot report `ok=1`, because the window
firmware left behind does not contain ChipCommon and no read-only path exists to move it. S1's real
dependency is therefore weaker and already satisfied: **S0 reporting a Broadcom function in D0 with
memory decode on and a mapped BAR0** — Boot AF gave all three. S1 now owns the ChipCommon read as
well as the EROM walk.

**Writes:** **exactly one register to start.** PCI config `0x80` (`BCMA_PCI_BAR0_WIN`), 32 bits,
set FIRST to `0x18000000` (`BCMA_ADDR_BASE`) to bring ChipCommon into the window — this is
`bcma_scan_switch_core(bus, BCMA_ADDR_BASE)`, exactly what Linux does before its first `BCMA_CC_ID`
read — then to the EROM base ChipCommon reports, then once per core to read wrapper state. Nothing
on the backplane is written. `0xAC` (`WIN2`) may be written to reach wrapper windows; it is the same
class of write and should land in the same stage, not a later one.

**Restore discipline — and Boot AF is the reason it is not a formality.** The pre-image of `0x80` is
read and pushed before the first write and restored at the end of the stage, in the `igpu`
unwind-stack spirit. On this machine that pre-image is **`0x18001000`, not `0x18000000`**. A stage
that "restores" to the enumeration base because that is what it assumed firmware left would silently
change the machine for every later boot stage — and would look like a successful restore in every
log line. Push the value read; never the value expected.

**First falsifiable predicate, before the walk even starts:** after writing `0x18000000` to
`cfg:0x80`, ChipCommon `0x00` must read a chip id of `0x4331` in its low 16 bits. If it still reads
`0xFFFFFFFF`, the window register is not the blocker and S1 stops there rather than proceeding to
walk a dead window.

**Proves it took:** the walker already written in `drivers/bcma.rs` (`walk_erom`) starts printing:

```
:: bcma: core[0] id=0x800 (chipcommon) rev=… mfg=0x4bf class=0 base=0x18000000 wrap=0x18100000(swrap) …
:: bcma: core[1] id=0x812 (d11(802.11)) rev=… base=0x18001000 wrap=0x18101000 …
:: bcma: core[2] id=0x820 (pcie) …
:: bcma: erom-walk cores=N entries=… stop=end-tag elapsed=…ms
```

**Falsifiable predicate — WITHDRAWN, see S1b §"the ncores trap".** This section previously claimed
`cores == ncores` as a predicate. It is not one: `ncores` is `BCMA_CC_ID_NRCORES`, the Sonics-era
CoreCount field, and on a socitype=1 (EROM) part the EROM is the only authority. Linux's bcma never
reads it. The surviving predicate: exactly one core with `id=0x812` (`BCMA_CORE_80211`) must be
present, and its `base` must be 4 KiB-aligned and inside `0x18000000`'s region.

**Third predicate, and it is free — Boot AF already paid for it.** Firmware left `cfg:0x80` at
`0x18001000` and `cfg:0xAC` at `0x18101000`. If the grid reading is right, the walk must return a
core whose `base` is **exactly** `0x18001000` and whose `wrap` is **exactly** `0x18101000`, and that
core must be the d11. This is a cross-check between two entirely independent sources — a config
register firmware wrote, and an on-chip ROM we walked — and a mismatch means the grid arithmetic in
`grid_index()` is a coincidence rather than a layout.

**Failure on serial:** `stop=all-ones` (window did not move / device stopped decoding),
`stop=cib-malformed` / `mp-malformed` / `addr-malformed` (the walk desynchronised — the one failure
mode that would otherwise produce plausible-looking nonsense, which is why the tags are checked and
not assumed), `stop=entry-cap` or `stop=tsc-deadline` (unbounded EROM).

**Not all-or-nothing.** Every line stands alone; a partial walk is still evidence.

### S1b — the EROM walk, corrected — **IMPLEMENTED, awaiting metal**

Same knob (`UNAOS_BCMAS1=1`), same three cfg:0x80 writes and the same restore. Read-only otherwise;
S1b adds no write target. The whole arc is decode.

**What Boot AJ printed, and why it is a complete diagnosis:**

```text
:: bcma: erom-abort at entry 4 while consuming 2 master ports of core id=0xf80 ::
:: bcma: erom-walk cores=0 entries=4 stop=mp-malformed elapsed=0ms ::
```

The first EROM dword on any BCMA part is ChipCommon's CIA. `id=0xf80` is that word read through the
wrong mask. One word, `0x4BF80001`, two decodes:

| mask set | manuf | id | class |
|---|---|---|---|
| as shipped (`mfg[11:0]`, `id[23:12]`, `class[27:24]`) | `0x001` | `0xf80` | `0xb` |
| corrected (`mfg[31:20]`, `id[19:8]`, `class[7:4]`) | `0x4bf` (BCM) | `0x800` (chipcommon) | `0` |

The shipped masks put the manufacturer field on top of the 4-bit tag/valid nibble — which no EROM
layout can do, because the tag has to live somewhere. The corrected layout is Linux
`drivers/bcma/scan.h` (`SCAN_CIA_*`, `SCAN_CIB_*`) / Broadcom `siutils_priv.h` (`CIA_*`, `CIB_*`).

The same line convicts the CIB masks at the bit level. `nmp=2` came out of `(cib >> 13) & 0xF`, so
ChipCommon's real CIB has bits 16:13 = `0b0010` — bit 14 set — and bit 14 is the low bit of the
corrected `CIB_NMW` (18:14). "Entry 4" is arithmetic: CIA at 0, CIB at 1, two entries consumed
before the tag check failed, so entry 2 really did carry the master-port tag and entry 3 —
ChipCommon's **first address descriptor**, its base — was eaten as a second master port.

**Three defects, one arc:**

1. **CIA/CIB field positions** (above). Anchored to the metal word, not to memory.
2. **Address descriptors were classified with the wrong tag mask.** Bit 3 of an address descriptor is
   `AD_AG32` ("a high address dword follows"), not tag. Linux masks address entries with
   `SCAN_ER_TAGX = 0x6`; the code used the full `0xE`. Worse, `ADDR_AS_64` was `0x04` — bit 2, a tag
   bit *set on every address descriptor* — so the walk would have read a phantom high dword for every
   address on the chip and desynchronised immediately. `AD_SZ`/`SZD` were shifted a bit as well.
3. **Fixed arity.** The walk consumed exactly `nsp + nmw + nsw` address descriptors. An EROM declares
   PORTS, not descriptors; a port carries one or more, and the list ends only when the next entry
   fails to match that port *and* type. The walk is now `bcma_get_next_core` step for step, over a
   **pushback cursor** (`Erom::peek` never advances; every accessor advances only on a match) — plus
   the not-a-core filters Linux applies (ARM `0xFFF` placeholder, no slave port, wrapper-less unless
   PMU/GCI/CC-B/4706-gbit-common, bridge), each of which is now *printed* as an `erom-skip` line
   rather than silently folded into the count.

**The `ncores` trap.** `chipid = 0x13924331` decodes, field by field, with Linux's own masks:

| field | mask | bits | value |
|---|---|---|---|
| `ID` | `0x0000FFFF` | 15:0 | `0x4331` |
| `REV` | `0x000F0000` | 19:16 | `2` |
| `PKG` | `0x00F00000` | 23:20 | `9` |
| `NRCORES` | `0x0F000000` | 27:24 | `3` |
| `TYPE` | `0xF0000000` | 31:28 | `1` = AI/BCMA, has an EROM |

Our decode was already right; the *use* was wrong. `NRCORES` is the Sonics-backplane CoreCount that
`sb_numcores()` reads. On a socitype=1 part the EROM is authoritative and Linux's bcma sets
`nr_cores` from the walk without ever looking at `NRCORES`. So `walk-cores != 3` is expected, not a
fault. The witness now says exactly that, and its verdict is `WALK-FAILED` iff `cores == 0`. GR20's
"6-10 cores" estimate was never contradicted by `ncores=3`.

**The sharp prediction.** Firmware left `cfg:0x80 = 0x18001000` and `cfg:0xAC = 0x18101000`. If the
corrected walk is right, it must independently report the d11 core (`id=0x812`) at **exactly**
`base=0x18001000` and `swrap=0x18101000` — a config register Apple wrote, versus an on-chip ROM we
walked, agreeing to the bit. That pair, on the new `erom-d11 FOUND` line, is the arc's deliverable
and the input to S3.

**New witness lines:** `erom-skip …`, `erom-walk cores=N skipped=K entries=E stop=…`,
`erom-d11 FOUND|ABSENT …`, and the cross-check reworded to advisory. `core[i]` now carries `mfg` and
`swrap`/`mwrap` separately — they are not interchangeable, and a bring-up stage handed a *master*
wrapper looks exactly like a core that will not come out of reset.

### S1c — WIFI-L0: the d11 core's first reach — **IMPLEMENTED, awaiting metal**

Same knob (`UNAOS_BCMAS1=1`), same block, and **no new write target**. L0 moves `cfg:0x80` — the one
selector S1 already writes twice and restores — onto the d11 core's backplane base and reads. It
writes no core register, no wrapper register, and no second config register. Its witnesses carry the
`wifi-l0:` prefix.

**What Boots AL/AM/AN handed this stage.** The S1b walk landed clean and identically on three boots:

```text
:: bcma: core[1] id=0x812 (d11(802.11)) rev=29 mfg=0x4bf(bcm) class=0 base=0x18001000 wrap=0x18101000(mwrap) mwrap=0x18101000 swrap=0x0 nsp=1 nmp=1 nsw=0 nmw=1 extra-slave-addr=0 ::
:: bcma: wrapper win2=0x18101000 at bar0+0x1000: ioctl=0x00002055 iost=0x0000100c resetctl=0x00000000 resetst=0x00000000 ::
:: bcma: wrapper-verdict answering clk=1 fgc=0 gated-clk=0 in-reset=0 core-enabled=1 ::
```

Two consequences, and they are why L0 exists as a stage at all rather than as part of S3:

* **The d11 core arrives out of reset and clocked.** `resetctl=0` and `ioctl` with `CLK` set, `FGC`
  clear. So its register window can be *read* without the `bcma_core_enable` sequence S3 owns —
  which means the PHY identity, the predicate §S3 was written to prove, is reachable one stage early
  and with zero writes beyond the selector.
* **The wrapper needs no `cfg:0xAC` write.** Firmware left `cfg:0xAC = 0x18101000` and the EROM
  independently reports the d11's master wrapper at `0x18101000`. L0 *checks* that equality and only
  then reads the agent registers at `bar0+0x1000`; when they differ it prints
  `REFUSED stage=wrapper reason=cfg0xac-elsewhere` and reads no AGENT register (the core window is still read, with a NOTE that reset-state is UNKNOWN), because pointing that aperture
  at the radio would be a second config write this arc does not make.

**A defect S1b's own deliverable line carried, fixed here.** `erom-d11 FOUND` advised
`cfg:0xac <- 0x00000000`, because it took the wrapper address from `swrap` and this core declares
`nsw=0 nmw=1` — its wrapper is a *master* wrapper. Following that advice would have pointed the
wrapper aperture at the bottom of the backplane. The line now carries Linux's `core->wrap` choice
(master wrapper when the core has one, else slave) alongside both raw values, and the address it
advises is the one firmware itself independently used.

**What L0 reads.** All of it status or identity, none of it read-to-clear:

| where | registers | what it settles |
|---|---|---|
| ChipCommon window (S1 step 3a) | `OTPS`/`OTPC`/`OTPL` + capabilities bit 30 | whether this board's calibration lives in SPROM, OTP, or both — **presence only** |
| d11 agent, `bar0+0x1000` | `IOCTL`/`IOST`/`RESET_CTL`/`RESET_ST` | the radio core's reset and clock state, for this specific core |
| d11 agent, `+0xFD0..0xFFC` | ARM PeripheralID/ComponentID block (Broadcom `aidmp.h`) | an **independent** part number and revision to cross-check the EROM against |
| d11 core window | `MACCTL` (0x120), `GEN_IRQ_MASK` (0x12C), `RADIO_HWENABLED_HI/LO` (0x158/0x49A) | is the MAC enabled, is the PSM running, is the radio hard-killed |
| d11 core window | `TSF_LOW`/`TSF_HIGH` (0x180/0x184), sampled twice | **clock liveness** — a counter that advances means the TSF counter is clocked and advancing; it carries no claim about the PSM |
| d11 core window | `PHY_VER` (0x3E0) | the crux: analog / **PHY type** / PHY rev |

Deliberately **not** read: `GEN_IRQ_REASON` (0x128) and the DMA `*_REASON` words are read-to-clear
and would destroy state S4/S6 need; `RADIO_CONTROL` (0x3E2) and `SHM_CONTROL` (0x160) are indirect
ports whose read requires first *writing* an index, so the radio's own id and the SHM contents are
not read-only facts and are not claimed as any.

**The REACH predicate.** Three facts, each on its own line, never averaged into one bit:

1. `cfg:0x80` reads back the d11 base (the selector took);
2. the agent answers with a valid ARM component-id preamble, and its part number is compared against
   the EROM's `id=0x812`;
3. `PHY_VER` decodes, and its type is **7 (HT-PHY)**.

`verdict=REACHED` requires (1) and (3). (2) is reported but is deliberately *not* part of the
verdict: the `aidmp.h` offsets are transcribed and unverified against this part, and Broadcom is
under no obligation to program the DMP part-number field with the BCMA core id — so a mismatch there
indicts the transcription, not the walk, and the witness says so.

**Refutes.** `raw@+0x000` and every other core read at `0xFFFFFFFF` with the selector confirmed = the
core window is dark despite the agent saying enabled (a finding that would move blame back to the
window or the link). `phy_type != 7` = the part is not what four boots have called it — `4` (N-PHY)
would mean a BCM4322-class card, `11` (AC) an 11ac upgrade; either redirects the project. A
`cfg:0x80` readback that is not the d11 base = the selector did not take, and every core read below
it is refused rather than reported.

**What the d11 core revision decides.** `rev=29` is the number that picks the driver lineage, and it
is worth stating plainly because it is the roadmap fact this stage exists to nail down:

* **`brcmsmac` does not claim the BCM4331.** Its PHY support is N-PHY and LCN-PHY (BCM4313,
  43224/43225-class parts). A d11 rev of 29 with an HT-PHY is outside it.
* **`b43` is the lineage that reaches this part**, through `phy_ht.c` — and upstream that support is
  partial: the HT-PHY init tables and calibration are incomplete. This is the §5 risk-1 wall,
  restated with a part number attached rather than an assumption.
* Either way the next gate is **not** more register reading, it is **microcode** — see S4, whose
  decision box is unchanged by this stage.

**The firmware boundary, named here so no later stage discovers it.** A d11 MAC does not execute
anything until tens of KB of Broadcom microcode are uploaded into it. That blob is proprietary,
non-redistributable, and has no free replacement for an HT-PHY part (OpenFWWF's only microcode
source is `ucode5.asm`, `%arch 5` — the rev 5–10 mapping; a free *assembler* for the arch-15 family
this part belongs to does exist, but no free *image* for rev 29 does). Under `docs/MANIFESTO/CLEAN_ROOM_POLICY.md` §4 — *"unaOS does not distribute
proprietary software. All proprietary assets … must be provided by the user at runtime."* — **the
public tree never carries the blob, in source or in any media image it builds.** The only shape that
is both legal and workable is a runtime load from the ESP, with the extraction done by the user on
their own machine; anything that stages, caches, or vendors the microcode belongs in the private
bunker repository and not here. S4's decision box is where that choice is made; L0's job is only to
make sure it is made with the part's real revision on the table.

**Knob wiring:** none new. `bcmaS1` already implies `bcmarecon`, is already on the `x86-all` cfg leg,
and is already stripped from `arm_features`. L0 adds no feature, no call site, and no aarch64 byte.

### S2r — WIFI-S2: the board's identity + capability, read-only — **IMPLEMENTED, awaiting metal**

Same knob (`UNAOS_BCMAS1=1`), same block as S1/L0, and **no new write target**. S2 moves cfg:0x80 —
the one selector S1 already writes and restores at Step 4 — back onto ChipCommon (`0x18000000`, where
the SPROM shadow lives), reads, and lets S1's Step 4 restore the window. It writes no ChipCommon
register, no core register and no second config register. Its witnesses carry the `wifi-s2:` prefix.
It runs in `s1_window_walk` **after** the EROM walk (so it has the ChipCommon CORE rev the walk
captured) and after L0, immediately before the Step 4 restore.

**What Boot AO handed this stage.** L0's `cc-identity` line already read, with the window on
ChipCommon: `sprom=present (cap bit30) otp=present-programmed otp_words=128 gup(ci=1)`. So the board
advertises an SPROM **and** a programmed OTP chip-info region — on an Apple board the SPROM shadow may
be OTP-backed. The EROM walk reported ChipCommon **core[0] rev=37**. That number does NOT select the shadow
offset — the first cut of this stage claimed it did, and review refuted it (see the offset paragraph
below: the BCM4331 is the one chip Linux names as excluded from `0x830`, and the `rev >= 31` test
belongs to `bcma_sprom_ext_available`, i.e. SPROM PRESENCE, not offset selection). The core rev is
carried because it decides whether `SROM_CONTROL`'s PRESENT bit is AUTHORITATIVE for presence.

**What S2 reads** (every read an `r16` of a status/identity word, no side effect):

| where | field | what it settles |
|---|---|---|
| ChipCommon `+0x190` | `SROM_CONTROL.PRESENT` | whether an external SPROM is **attached at all** — the presence determination, not a guess |
| shadow, last word | SROM revision (low byte) | which SROM layout this is; a 4331 is rev 8/9 |
| shadow `+0x8C` | `SSB_SPROM8_IL0MAC`, 3 BE words | the station **MAC** — the WiFi twin of BT's BD_ADDR |
| shadow `+0x9C` | `SSB_SPROM8_ANTAVAIL` | the **band capability**: lo byte = 2.4GHz antenna mask, hi byte = 5GHz — a nonzero 5GHz mask is the SPROM's statement that the board is dual-band |
| shadow `+0x04` | `board_type` (`SSB_SPROM1_SPID`) | the **board id**; the SPROM normally programs the PCI ssid device, so a match corroborates the offset |
| shadow `+0x82`/`+0x84..0x8A` | `board_rev`, `boardflags`/`boardflags2` | the rest of the board identity (UNVERIFIED decode, RAW dumped) |

**The SPROM offset: `0x800`, and the 4331 is the part explicitly excluded from the alternative.**
This paragraph previously stated the rule backwards, so the sourcing is recorded rather than
asserted:

* current Linux `drivers/bcma/sprom.c` sets `u16 offset = BCMA_CC_SPROM` (`0x800`) on the
  external-SPROM path and never moves it — `BCMA_CC_SPROM_PCIE6` does not appear in that file at all;
* the historical (v3.2-era) code that ever used `0x830` reads
  `offset = (chipinfo.id == 0x4331) ? BCMA_CC_SPROM : BCMA_CC_SPROM_PCIE6;` — the **BCM4331 is the one
  chip named as the exception**, and the rule it stands in for is **PCIe-core rev >= 6**, not a
  ChipCommon revision;
* the `rev >= 31` test appears exactly once in `sprom.c`, inside `bcma_sprom_ext_available()`, where it
  selects `SROM_CONTROL` over `CHIPSTATUS` for **presence detection**. It has nothing to do with the
  shadow's address.

The first cut of S2 conflated those two functions and moved the offset to `0x830`, replacing a right
answer (S0's `0x800`, reached for the wrong reason — it keyed on the chip rev) with a wrong one. Both
the offset **and its reason** are now printed, one shared `sprom_offset_for()` serves S0 and S2 so the
rule cannot diverge between them, and S2 **dumps the shadow at both `0x800` and `0x830`** so a single
metal boot settles the question either way.

**Two field offsets were also wrong, and independently fatal.** `il0macaddr` was read at `0x4A`,
which is not the rev-8 MAC and not even the rev-4 MAC — it is `SSB_SPROM4_BFL2HI`/`SSB_SPROM5_BFLLO`,
a **boardflags** word. Reading it and calling it a station MAC yields six plausible bytes that are not
an address. `ANTAVAIL` was at `0x5C`, the *rev-4* antavail. Both are corrected (`0x8C`, `0x9C`), and
the structural check is that the MAC now sits immediately after this revision's boardflags block
(`BOARDREV 0x82`, `BFL* 0x84..0x8A`). The same `0x4A` literal in the S0 path is gone — S0 and S2 share
the constant.

**Where read-only stops, and the write S2 names instead.** On the 4331 the external power-amplifier
control lines are muxed onto the SPROM pins; Linux calls `bcma_chipco_bcm4331_ext_pa_lines_ctl(cc,
false)` — a ChipCommon chip-control WRITE — before reading the shadow. That write is past the
read-only ceiling. If the shadow reads all-`0xFFFF` (or all-zero), S2 prints `BLOCKED`, **names that
write** (the way L0 names the cfg:0x80 write it declines), and notes the identity may instead live in
OTP, whose contents need a read command written to OTPP — also a write, also refused. Only a
non-degenerate shadow is decoded.

**And the BLOCKED branch is now a determination, not an inference.** S2 reads
`BCMA_CC_SROM_CONTROL` (`cc+0x190`) — the other half of `bcma_sprom_ext_available()`. On a ChipCommon
CORE rev >= 31 (here 37) its `PRESENT` bit says whether an external SPROM is physically attached, so an
empty shadow splits cleanly: `PRESENT=1` ⇒ a real SPROM is there and the emptiness points at the PA
mux; `PRESENT=0` ⇒ there is no external SPROM and the empty shadow is simply the truth. Below rev 31
the authority is `CHIPSTATUS` instead, so the line is printed but marked non-authoritative.

**The REACH-equivalent for S2 — facts that can each fail on their own, never averaged into one bit:**

1. the selector took (`cfg:0x80` reads back `0x18000000`) — else nothing below is trusted;
2. the dump is **complete** (`words_read == 220`) — a run cut short by the TSC deadline cannot support
   any verdict about the contents, least of all `all-ff`, which a zero-word read would satisfy
   vacuously;
3. the shadow is not degenerate — else `BLOCKED`, with the `SROM_CONTROL` determination above;
4. **the MAC leg and the shadow leg, independently.** `mac-credible` = non-degenerate **and** unicast
   **and** a recognised OUI; `shadow-credible` = SROM rev in `[8,11]` **and** `board_type == ssid`.
   `PLAUSIBLE` requires both.

That last split is the correction that matters. `unicast` alone is a coin flip — bit 0 of any
arbitrary byte is clear half the time — and `board_type`/`board_rev` sit at offsets that were correct
even while the MAC's was wrong, so they corroborate **the shadow, never the MAC's own offset** and
cannot stand in for it. Without the OUI condition the verdict could not fail on its own headline
claim. The OUI table is deliberately **non-exhaustive** (Apple holds hundreds of OUIs): an
unrecognised prefix downgrades to `SUSPECT` rather than convicting the address, which understates a
genuine MAC instead of overstating a false one, and the raw bytes are always on the line.

**Refutes.** shadow all-`0xFFFF` = window not on ChipCommon, PA-mux blocking, or offset wrong (and
`SROM_CONTROL.PRESENT` now says which); MAC all-FF/all-00 = SPROM not populated or offset wrong;
`board_type != ssid device` = the offset **or** the board (the SPROM programming the subsystem id is
the normal case, not a law); SROM rev outside `[8,11]` = offset wrong / unpopulated; structure in the
**alt-offset** dump while the chosen offset is degenerate = the offset rule itself is refuted, and one
capture is enough to say so. Predictions: `~/unaos-bench/scratch/gr22/wifis2-predictions.md`.

**Still transcribed, not corroborated.** The MAC offset and the offset rule are both read out of
headers; nothing on metal has confirmed either, because S0 has never once reached ChipCommon on this
machine (it refuses at `window-elsewhere`), so there is no prior capture to check them against. The
alt-offset dump exists precisely so the first metal boot can settle them.

**The CRC is deliberately not computed** — the SPROM CRC-8 polynomial is not transcribed in this tree,
and a wrong table would lie `BAD` on a good SPROM. Transcribing it is an S2-contents (write-path)
deliverable, below.

**Knob wiring:** none new. `bcmaS1` already implies `bcmarecon`, is already on the `x86-all` cfg leg,
and is already stripped from `arm_features`. S2 adds no feature, no call site and no aarch64 byte.

### S2 — Board identity: SPROM contents / OTP

**Depends on:** S1 (the ChipCommon core address, and — for OTP — its wrapper), and S2r (which reads
the shadow read-only and names the PA-line write when it is blocked).

**Writes:** on BCM4331 specifically, Linux calls `bcma_chipco_bcm4331_ext_pa_lines_ctl(cc, false)`
**before** reading the SPROM shadow, because the external power-amplifier control lines are muxed
onto the SPROM pins. That is a ChipCommon control write and it is why S0's SPROM dump is reported
with a plausibility verdict rather than asserted valid. For OTP: a read command written to
ChipCommon `0x18` (OTPP) per word, polled through OTPS.

**Proves it took:** a MAC address with a unicast OUI and an SPROM revision in `[8, 11]`; and — the
stronger predicate — **the SPROM CRC-8 validates**. The CRC is deliberately *not* computed in S0
(the polynomial is not transcribed in this tree and a wrong table would produce a lying `BAD` on a
good SPROM); transcribing `bcma`'s 256-entry table is an S2 deliverable and turns "we read 220 words
of something" into "this is the board's calibration".

**Falsifiable predicate:** the MAC read from SPROM/OTP must match the one Apple's firmware knows —
compare against the `ssid=` subsystem id and, better, against a MAC observed on the air from another
machine. Also: `board_type` should equal the PCI subsystem device id (that is where Linux takes it
from), so the two must agree.

**Failure on serial:** `NO-DATA` (all-`0xFFFF` or all-zero shadow — the mux, or genuinely blank),
`SUSPECT` (multicast bit set in byte 0, or an unsupported revision), CRC mismatch.

**Apple boards commonly use OTP rather than SPROM.** S0 reports which by reading ChipCommon
capabilities bit 30 and the OTP GUP bits; S2 must handle whichever S0 found, and the two paths are
different enough that discovering it in S0 is what stops S2 being written twice.

**Not all-or-nothing** — but note that **without correct calibration the PHY cannot be brought up
and TX is out of regulatory spec.** S2 is a hard prerequisite for S5, not an optimisation.

### S3 — Core enable — **SETTLED FROM EVIDENCE: reachability is a NO-OP; ownership is S4's prologue** (`wifi-s3:`)

**Depends on:** S1 (the d11 core's base and wrapper addresses). **Writes: none, and none proposed
for this stage.** The witness is pure decode over words L0 already read — it performs zero device
access, deliberately, so that the arc which *decides* whether S3 is needed cannot be the arc which
touches the registers S3 would write.

**S3 was written expecting to have to bring the radio out of reset. It does not.** WIFI-L0 reported
the core arrives enabled; this stage checks that reading against Linux's rule rather than accepting
it, and the reading survives.

#### The verdict, and the arithmetic behind it

Linux's `bcma_core_is_enabled()` (`drivers/bcma/core.c`) is **exactly two tests and inspects no
other bit**:

```c
(bcma_aread32(core, BCMA_IOCTL) & (BCMA_IOCTL_CLK | BCMA_IOCTL_FGC)) == BCMA_IOCTL_CLK
&& !(bcma_aread32(core, BCMA_RESET_CTL) & BCMA_RESET_CTL_RESET)
```

Boot AO, in its own words:

```text
:: bcma: wrapper win2=0x18101000 at bar0+0x1000: ioctl=0x00002055 iost=0x0000100c resetctl=0x00000000 resetst=0x00000000 ::
```

* `ioctl & (CLK|FGC)` = `0x2055 & 0x3` = **`0x1`** = `BCMA_IOCTL_CLK`. First test **passes**.
* `resetctl & RESET` = `0x0 & 0x1` = **`0`**. Second test **passes**.

**L0's reading is correct.** `bcma_core_is_enabled` already returns true for these words, so S3's
goal — make the core answer — is met with zero writes. Everything L0 and S2r read (PHY identity,
d11 rev, TSF, MACCTL, the SPROM shadow) was read **without** it, which is the strongest possible
corroboration: the stage that was supposed to unblock those reads was skipped and the reads still
worked.

Note what this does **not** mean: `bcma_core_enable` itself is **not inert**. It opens with
`bcma_core_disable`, which asserts `RESET_CTL.RESET`; running it here would reset the core and
discard the firmware's configuration. That is precisely the reset S4's prologue needs, which is why
the sequence is not deleted but relocated.

**So S3 as "make the core answer" is discharged with no write, as a measured fact rather than an
assumed one, and the witness re-measures it every boot** (see the standing check below).

#### What the same registers say that the enable rule does not — and why S3 is not simply gone

`bcma_core_is_enabled` looks at two bits out of thirty-two. The rest of `IOCTL` is
`BCMA_IOCTL_CORE_BITS` (0x3FFC) — defined by the core, and for a d11 those are b43's
`B43_BCMA_IOCTL_*`. Decoding `ioctl=0x00002055` against them:

| bit | b43 name | value |
|---|---|---|
| 0 | `BCMA_IOCTL_CLK` | 1 |
| 1 | `BCMA_IOCTL_FGC` | 0 |
| 2 | `B43_BCMA_IOCTL_PHY_CLKEN` | **1** |
| 3 | `B43_BCMA_IOCTL_PHY_RESET` | 0 |
| 4 | `B43_BCMA_IOCTL_MACPHYCLKEN` | **1** |
| 5 | `B43_BCMA_IOCTL_PLLREFSEL` | 0 |
| 6:7 | `B43_BCMA_IOCTL_PHY_BW` | **`0x40` = 20 MHz** |
| 13 | `B43_BCMA_IOCTL_GMODE` | **1** |

That is not a power-on state. `PHY_BW` is a **two-bit field whose all-zero encoding decodes as
10 MHz**, so "power-on does not choose a bandwidth" would overstate it: the field reads **`0x40`
(20 MHz)** rather than the all-zero reset encoding, and `0x40` is precisely the value
`b43_wireless_core_reset` writes — so the field **was written**, by something shaped like b43.
`CLK` +
`PHY_CLKEN` + `MACPHYCLKEN` set, with `FGC` and `PHY_RESET` clear and a bandwidth chosen, is the
state a *completed* b43-shaped bring-up leaves behind — `b43_wireless_core_reset` (GMODE, PHY_CLKEN,
PHY_BW_20MHZ), then `b43_bcma_phy_reset` / `b43_phy_take_out_of_reset` (PHY_RESET asserted then
cleared, FGC raised then lowered), then `b43_mac_phy_clock_set` (MACPHYCLKEN).

Three further readings from the same capture point the same way:

* `macctl=0xc0020403` decodes to `ENABLED | PSM_RUN | IHR_ENABLED | INFRA | DISCTXSTAT | GMODE`.
  **`PSM_RUN=1` means the d11's microcode processor is executing right now**, and `INFRA` /
  `DISCTXSTAT` are operating-mode *policy* that no reset leaves set.
* `tsf sample0=0x00000000:0x009054b2` = **9,458,866 µs ≈ 9.46 s** on a counter that ticks at 1 MHz
  by 802.11 — read at kernel timestamp **1,986 ms**. The counter reads ~7.5 s more than this
  kernel's uptime. What started it is UNKNOWN — see the caveat below.
* `iost=0x0000100c` carries `BCMA_IOST_DMA64` and `B43_BCMA_IOST_DUALB_PHY`. **Caveat on the
  dual-band reading:** the per-band `B43_BCMA_IOST_2G_PHY` and `B43_BCMA_IOST_5G_PHY` status bits
  both read **0** in that same word, so the dual-band statement rests on `DUALB_PHY` alone and not
  on a per-band confirmation.

**Conclusion: the radio arrives configured, clocked, and running someone else's microcode — the
platform firmware's.** (A 2012 rMBP EFI brings the AirPort up for wireless NetBoot / Internet
Recovery; that is a plausible mechanism, and it is offered as a mechanism, not as the evidence. The
evidence is `PSM_RUN` and the selected 20 MHz bandwidth. The TSF reading is recorded alongside but
is NOT load-bearing: whether the d11 TSF free-runs with the PSM halted is undocumented in both
directions, so a TSF larger than our uptime is also consistent with a counter running since chip
power-on.)

**Which is why S3 does not vanish, it changes job.** "Enabled" and "in a state we chose" are
different claims. b43's own upload path asserts the second:

```c
/* b43_wireless_core_reset(), before a single ucode word is written */
B43_WARN_ON(macctl & B43_MACCTL_PSM_RUN);
macctl |= B43_MACCTL_PSM_JMP0;
```

b43 reaches that assertion only *after* `bcma_core_enable` (reached during wireless-core bring-up),
whose reset pulse is what clears `PSM_RUN` — *inferred from core-reset semantics; b43 does not state
it*. On this machine `PSM_RUN` is set at UnaOS boot, so **S4 cannot begin from the state the
machine hands us** — its first act must be the core reset S3 was going to own. That work is real,
but it is one sequence with S4's upload and has no predicate of its own (the "proves it took" for a
reset whose only purpose is to precede an upload *is* the upload's handshake). Folding it into S4 as
a prologue is therefore the honest structure; leaving it as a stage would create a stage that cannot
be refuted on its own, which this ladder's discipline forbids.

**The writes that prologue will need, named and not made** (against `bcma_core_enable` +
`b43_wireless_core_reset`, so a later arc starts from a list rather than a memory):

| # | register | write | why |
|---|---|---|---|
| 1 | wrapper `RESET_CTL` (`+0x800`) | set `RESET` (bit 0), read back, `udelay(1)` | assert reset — the step that clears `PSM_RUN` and voids the firmware's configuration |
| 2 | wrapper `IOCTL` (`+0x408`) | `CLK | FGC | GMODE | PHY_CLKEN | PHY_BW_20MHZ` | our flags, chosen by us, while the core is held in reset |
| 3 | wrapper `RESET_CTL` | clear `RESET`, read back, `udelay(1)` | deassert |
| 4 | wrapper `IOCTL` | clear `FGC` | leave forced clock gating off |
| 5 | wrapper `IOCTL` | set `PHY_RESET`, `udelay(2)`, then clear it with `FGC` raised and lowered around the clear | `b43_bcma_phy_reset` / `b43_phy_take_out_of_reset` — the PHY's own reset, separate from the core's |
| 6 | core `MACCTL` (`+0x120`) | set `PSM_JMP0`, `PSM_RUN` already clear | the state b43 asserts before upload |

**This table is the SHAPE of the prologue, not a transcription of b43's path.** b43's own sequence
also includes `bcma_core_set_clockmode(FAST)` and `bcma_core_pll_ctl`; step 5's
`b43_phy_take_out_of_reset` clears `PHY_CLKEN` while `FGC` is raised and re-sets it as `FGC` drops;
and `bcma_core_disable` writes `IOCTL` = flags *before* asserting reset. The arc that makes these
writes must work from the source, not from this table.

**Each of those is a first write to the radio's silicon and belongs to the arc that also carries the
upload it exists to enable, with its own review.** This arc makes none of them.

#### The standing check (`wifi-s3: VERDICT`)

That S3 owes no write is recorded as a *measurement that is re-taken every boot*, never as a fact
the tree may assume. `d11_s3_witness()` prints, from words L0 already read and with no device access of its own:

```text
:: wifi-s3: enable-rule ioctl=… (ioctl&(CLK|FGC))=… want=0x0001 match=… resetctl=… (resetctl&RESET)=… => bcma_core_is_enabled=… ::
:: wifi-s3: ioctl-decode clk=… fgc=… phy-clken=… phy-reset=… macphyclken=… pllrefsel=… phy-bw=… gmode=… ::
:: wifi-s3: iost-decode … dma64=… dualb-phy=… ::
:: wifi-s3: macctl-ownership … psm-run=… infra=… disctxstat=… ::
:: wifi-s3: tsf-provenance tsf=…us uptime=…us predates-us=… delta=…us ::
:: wifi-s3: VERDICT reachability=SATISFIED(no-write)|REQUIRED enable-writes-needed=… ownership=FOREIGN|OURS-OR-IDLE|UNREAD reset-to-known-state-writes-needed=… wrote-anything=0 ::
```

**`reachability=REQUIRED` is the alarm.** A different card, a cold power cycle that skips the EFI
AirPort init, or a firmware revision that leaves the radio down, all print it — and it puts
`bcma_core_enable` back and makes S3 a stage again. Nothing downstream may assume the core arrives
enabled; it must read this line.

`tsf-provenance` is **corroboration only, never the ownership verdict** — that verdict is
`PSM_RUN`'s alone. It samples this kernel's uptime *after* the TSF, which can only overstate the
uptime, so the comparison errs toward **not** claiming a predating counter. When the bootpace TSC
rate is not yet calibrated, or the bootpace origin has not been set, it prints `UNAVAILABLE` with
the reason rather than inventing a microsecond from a guessed frequency or an unset origin.

#### Two facts this stage harvested for later stages, free

* **`BCMA_IOST_DMA64` is set.** The d11's DMA engine is the 64-bit one, so **S6 programs 64-bit
  descriptor rings**, and that is now the core's own statement rather than an inference from the
  part number.
* **`B43_BCMA_IOST_DUALB_PHY` is set.** An independent second source for the dual-band claim S2r
  reads out of the SPROM antenna masks — a core status bit versus a board EEPROM, agreeing. **The
  caveat travels with it:** the per-band `2G_PHY` and `5G_PHY` status bits both read 0 in the same
  `iost` word, so this second source is `DUALB_PHY` alone and is not corroborated per band.

#### The predicate S3 was created to prove is already discharged

`phy_type == 7` was S3's falsifiable predicate. L0 read it one stage early, without S3's writes:
`phy-ver raw=0x9701 analog=9 type=7 (HT) rev=1 type-match=1`. It stays S3's predicate on any boot
that prints `reachability=REQUIRED`, because such a boot would have to reach it the original way.

### S4 — Firmware (microcode) upload — **the wall, now pinned exactly**

**Depends on:** S1c (the d11 base/wrapper, both measured) and **S3's reset-to-known-state prologue,
which is now part of this stage** (§S3). Nothing else in S3 is outstanding.

Everything in this section is transcribed from the b43 reference implementation's *interface* — file
names, register offsets, sequence, handshake — and is **UNVERIFIED against this part**; no boot has
executed any of it. The offsets that this tree already carries as constants (`SHM_CONTROL` 0x160,
`SHM_DATA` 0x164, `MACCTL` 0x120) are the ones L0 deliberately declines to touch.

#### What exactly the d11 needs

| what | file (b43 naming) | why this one |
|---|---|---|
| **microcode** | `b43/ucode29_mimo.fw` | b43 selects on the **d11 core revision**, and rev 29 with an HT-PHY maps to `ucode29_mimo`. Our core is `rev=29`, `phy type=7 (HT)` — measured, three boots. The ucode is core-revision-specific; a rev-26 or rev-30 image is the wrong blob and the handshake is what says so. |
| **initvals** | `b43/ht0initvals29.fw` | register init table, selected by PHY type **and** core rev (`B43_PHYTYPE_HT` + rev 29). |
| **band-switch initvals** | `b43/ht0bsinitvals29.fw` | the per-band retune table, same selection. |
| **PCM** | *none* | b43 loads a PCM image only for the old low-rev cores; rev 29 does not use one. |

**Size:** tens of KB for the ucode, a few KB for the initvals — but the band-switch initvals run
much smaller than "a few KB": the real `ht0bsinitvals29.fw` measured **178 bytes** on metal (GR27,
2026-08; it was rejected by the loader's original 256-byte floor, staging 2/3 — the floor is now
128). The exact byte count is a property of the user's extraction and **must be taken from the file
header, never from a constant in this tree**.

**Container header — W3, ANSWERED ON METAL (rmbp1-boot1, 2026-08).** An earlier draft here recorded
"a 4-byte header (`type`, `ver`, reserved, big-endian `size`)" with a uniformly word-stream payload;
that record was internally inconsistent (four fields cannot fit in four bytes) and the word-stream
claim was wrong for two of the three files. The measured truth:

* Every file carries the same **8-byte header**: `type` u8, `ver` u8, 2 reserved bytes, `be32 size`.
* **`type` 0x75 — the microcode**: `size` is the payload **byte** count (`size == len − 8`) and the
  payload is a stream of big-endian 32-bit words (39760-byte file, `size`=39752, whole words).
* **`type` 0x69 — both initvals files**: `size` is the payload **record** count, and the payload is
  a stream of variable-length records: `be16 offset` (bit 15 flags a 32-bit value) followed by a
  `be16` or `be32` value — 4 or 6 bytes per record. Measured: `ht0initvals29.fw` `size`=477 walks as
  exactly 477 records consuming its 2712-byte payload exactly; `ht0bsinitvals29.fw` `size`=35
  likewise (170-byte payload) — the same 178-byte file that falsified both earlier candidate
  layouts.

Provenance: the record framing was pinned by hypothesis-falsification against the user's own
extracted set on this bench (the framing above is the one reading under which both record walks
match their declared counts while consuming their payloads exactly); no driver source was read. The
walk pins the **framing** — what the `offset` field means to the d11 core is upload-time evidence.
The upload consequence: step 2 below (the be32 word-stream into `SHM_DATA`) is the **ucode's** path;
the initvals are **not** streamed through it — they are per-register writes applied by their own
consumer, which is S5's business.

**Provenance:** extracted from Broadcom's own binary driver, `broadcom-wl-5.100.138`, with
`b43-fwcutter`. That is the same extraction every Linux distribution asks its users to perform for
this card. See the clean-room boundary below.

#### The upload path, and the handshake

The upload does **not** use a dedicated aperture — it goes through the **SHM indirect window** the
d11 core already exposes, which is exactly the port L0 refuses to touch because opening it requires
a write:

1. **Prologue (the old S3):** core reset with our IOCTL flags, then `MACCTL |= PSM_JMP0` with
   `PSM_RUN` clear. b43 `B43_WARN_ON`s if `PSM_RUN` is set here — and on this machine it *is* set at
   boot, which is the whole reason the prologue is mandatory (§S3).
2. **Stream the ucode:** write `(B43_SHM_UCODE << 16) | 0` to `SHM_CONTROL` (`d11+0x160`), then
   write each big-endian-decoded 32-bit word to `SHM_DATA` (`d11+0x164`). The window
   **auto-increments**; there is no per-word address. b43 spaces the writes by ~10 µs.
3. **Clear pending interrupt state**, then **start the PSM:** `MACCTL |= PSM_RUN`, `&= ~PSM_JMP0`.
4. **Wait for the microcode to announce itself:** poll `GEN_IRQ_REASON` (`d11+0x128` —
   read-to-clear, which is why L0 will not read it) for `B43_IRQ_MAC_SUSPENDED`, budget ~21 × 50 ms.
   Silence here is "microcode not responding" and is the binary failure.
5. **Read the handshake out of shared memory:** `SHM_CONTROL` ← `(B43_SHM_SHARED << 16) | offset`,
   then read `SHM_DATA` — `UCODEREV` at shared offset `0x00`, `UCODEPATCH` `0x02`, `UCODEDATE`
   `0x04`, `UCODETIME` `0x06`.

**Proves it took:** the ucode publishes its own revision, patch level and build date/time in shared
memory *after it starts executing*. Note what this is and is not: it is an **integrity echo from a
processor that is running our bytes**, not an authentication of them. b43's one hard rejection is
`fwrev <= 0x128` (296) — "firmware from binary drivers older than version 4.x". **The 351/410/598
numbers are NOT rejection thresholds**, as an earlier draft of this section said: they are
`B43_FW_HDR_351`/`_410`/`_598`, which select the RX/TX frame-header layout a microcode generation
uses. §S4a's interpretation table carries both, separately.

**Falsifiable predicate:** `UCODEREV` read from SHM equals the revision the extracted image declares,
`UCODEDATE`/`UCODETIME` decode to a plausible build stamp, and `MACCTL` shows `PSM_RUN` set with
`PSM_JMP0` clear.

**Failure on serial:** `GEN_IRQ_REASON` never reaches `MAC_SUSPENDED` (the PSM did not start — wrong
image, bad upload, or the prologue's reset did not take); `UCODEREV` reads `0` or `0xFFFF` (ucode not
running); a revision mismatch (wrong blob for core rev 29).

**Partly all-or-nothing:** the *mechanism* (SHM window, autoincrement, word order) is incrementally
verifiable by reading back what was written, before the PSM is ever started. The *handshake* is
binary.

#### A finding from §S3 that S4 must not misuse

The d11 is **already executing microcode at UnaOS boot** (`PSM_RUN=1`; the TSF reading is
corroborative at best and is not relied on). Somebody's image is resident in that PSM right now.

This is **not** a route around S4 and must not be treated as one: we cannot identify it, cannot
version it read-only (`UCODEREV` lives behind the SHM window, whose read requires a write, so it is
an S4-class probe and not a read-only fact), cannot rely on any particular firmware revision leaving
it there, and cannot reach a known state without a reset that destroys it. It is recorded because it
is true and because it makes one cheap thing available early: **the first write-bearing probe worth
making is `SHM_CONTROL`/`SHM_DATA` reading `UCODEREV` on the resident image** — four writes of two
distinct select values, no
reset, no upload, and it exercises the exact indirect-window mechanism S4 depends on against a PSM
that is known to be alive. That is a much smaller first write than a full upload, and it is the
natural first arc after this one. **That arc is written — see §S4a below**, which makes exactly that
probe and nothing else.

#### Signed or unsigned — and how that compares to the GPU

**The d11 microcode is UNSIGNED.** There is no signature, no hash, and no key anywhere in the path
above: b43 streams raw words into the PSM's instruction memory through an autoincrementing window,
and the only "verification" is a revision word the ucode publishes about *itself* after it starts —
which any image that runs can publish, and which therefore authenticates nothing. The BCM4331's PSM
has no secure-boot gate.

That matters because it is the same posture as the Kepler falcons on this machine, where **our own
hand-authored FECS image already executes**. So the honest statement, which corrects an implication
this document previously left standing:

> **Clean-room authoring of WiFi microcode is not barred by cryptography.** Option 3 in the decision
> box below is not blocked the way it would be on a signed part. It is blocked by three other things,
> and they should be argued on their own merits rather than hidden behind "proprietary".

| | Kepler falcon (GK107, this machine) | d11 PSM rev 29 (BCM4331, this machine) |
|---|---|---|
| signature check in hardware | **none** on Kepler (secure-boot falcons arrive with later parts) | **none** |
| our status | **ucode we authored executes on metal** | nothing attempted |
| ISA documentation | falcon v3/v4 documented by envytools/rnndb — a Group-A-legal source, and this tree authors instructions from `const fn` constructors | **partial, and not for this rev.** OpenFWWF ships exactly one microcode source, `ucode5.asm` (`%arch 5`); b43 maps core revs 5–10 to that image, so its free ucode is the arch-5 family only. A free assembler does exist and does cover this part's ISA family — `b43-asm`/`b43-dasm` implement arch 5 and arch 15, and core rev ≥ 15 (rev 29 included) is arch 15; Nexmon v3 / SEEMOO D11emu decode rev 15–54. What is missing is a rev-29-specific ISA document, any validated evidence that arch-15 fidelity holds on an HT-PHY part, and a free image for rev 29 — of which there is none |
| what the ucode must *do* | a bounded, purpose-built sequence that has to satisfy one handshake | a full real-time MAC: ACK/CTS inside SIFS (10 µs), backoff, NAV, aggregation, rate-control hooks. **There is no minimal "echo" image that reaches S6**, because the RX path's timing is ucode-driven |
| what remains after the ucode | nothing — the ucode *was* the wall | **S5.** Free microcode moves the wall from S4 to S5 (the undocumented HT-PHY tables, §5 risk 1) and removes nothing |

**So the comparison cuts the other way from what "both are unsigned" suggests.** On the GPU, writing
our own microcode was tractable *and* decisive. On the radio it is neither: no documented ISA, a far
larger and harder real-time program, and a wall behind it that the effort would not touch. Option 3
below stays rejected — but on effort and on the S5 wall, not on signing, and the ledger should say so.

**The clean-room boundary is unchanged and is not what is in question here.**
`docs/MANIFESTO/CLEAN_ROOM_POLICY.md` §4 — *"unaOS does not distribute proprietary software. All
proprietary assets … must be provided by the user at runtime."* — **the public tree never carries the
blob, in source or in any media image it builds**, and §2's two-team rule governs anyone who
disassembles it. Option 1 below is the only shape that satisfies both.

### S4-W5 — the SHM/ucode routing, PINNED (W5 research pass, 2026-08-19) — **the wall is down**

The one named unknown gate 3 refused on — the numeric routing selector for microcode memory — is
settled from a source legal for `src/wifi/`: the **b43 open specification wikis**, the
reverse-engineered *hardware documentation* the community wrote for clean-room reimplementation
(what wireless.wiki.kernel.org/en/users/drivers/b43/developers points at). Two generations, both
live and fetched during the pass:

* **[SPEC-V3]** `bcm-specs.sipsolutions.net` (the original bcm-specs wiki)
* **[SPEC-V4]** `bcm-v4.sipsolutions.net` (the 4.xx-series spec)

No Linux driver source was read. These tags are Group-A-legal pins; `[METAL]`/`[LEDGER]` keep their
existing meanings. The numbered facts below are what `bringup.rs`'s `wifi3` upload rung cites.

**Fact 1 — the routing.** `[SPEC-V3 SHM]` routing table: `0x0001` Shared Memory (byte-addressed),
`0x0002` 802.11 Settings, `0x0003` PCM Data, `0x0004` Security HW MAC list, **`0x0300`
"Microcode"**, `0x0301` "Initial Value Microcode(?)". `[SPEC-V3 MicrocodeUpload]`: "The microcode
is written to the SHM, **control word 0x03000000, 32 bits at a time**" — `(0x0300 << 16) | 0`
verbatim. Discriminating cross-check: the same table carries `0x0001`, the value S4a already
proved on metal. Mapped constant: `SHM_ROUTE_UCODE = 0x0300`. (PCM routing 0x0003 unused — rev 29
loads no PCM, corroborated by [SPEC-V4]'s Init/Firmware rev→file tables; 0x0301 unused — see
fact 6.)

**Fact 2 — the window mechanism, and the MACCTL upgrade.** `[SPEC-V3 SHM]`: control word = routing
(high 16) | offset (low 16); non-shared routings take 32-bit word pointers, shared (0x0001) takes
BYTE addresses (`>> 2`); data at 0x164 (aligned) / 0x166 (odd half); the internal pointer
**auto-increments 32 bits per access**, read and write alike. `[SPEC-V4 802.11/Registers]`
corroborates the map (SHM Control 0x160, SHM Data 0x164) and pins the MACCTL bit values this tree
carried as EXT-CORROBORATION-WEAK: MAC Enabled 0x1, PSM Run 0x2, PSM Jump-0 0x4, SHM Enabled
0x100, SHM Upper 0x200, Big Endian 0x10000, Infra 0x20000 — every MACCTL constant in `bringup.rs`
is re-tagged `[SPEC-V4 802.11/Registers]`, values unchanged.

**Fact 3 — the word-stream.** Select `0x0300_0000`, stream the payload "32 bits at a time" into
0x164. What a word is on disk is the tree's own `[METAL W3]` pin: 8-byte container header, ucode
type 0x75 ⇒ size = payload BYTES, be32 words (the staged `ucode29_mimo.fw`: declared 39752 = 9938
words). The spec does not state file endianness; the fact-5 handshake is the backstop if the
decode direction were wrong. (3.4) Inter-word pacing appears in NEITHER spec generation — the
implementation's ~10 µs/word settle is engineering margin, tagged as such, ~100 ms total. (3.5)
Before the PSM ever starts, re-select `0x0300_0000` and read the stream back through the same
auto-incrementing window — the "incrementally verifiable" leg §S4 promised, now with a citable
mechanism.

**Fact 4 — starting the PSM, the citable ladder.** `[SPEC-V3 ChipInit]` steps 1–6: (1) write
**0x404** to 0x120 (PSM_JMP0 + 0x400 — the spec pins the WHOLE WORD; RUN clear, JMP0 set, exactly
§S4 step 1's required state); (2) the upload (facts 1–3); (3) write **0xFFFFFFFF** to **0x128**;
(4) write **0x20402** to 0x120 (Infra + 0x400 + PSM Run, JMP0 dropped); (5) spinwait the
**Ready** bit in 0x128, up to **10 s**, polling every **10 µs**; (6) dummy read of 0x128
(read-to-clear). Ready pinned twice independently: `[SPEC-V3 Interrupts]` 0x00000001 "Ready" ∧
`[SPEC-V4 Registers]` 0x00000001 "MAC Suspended" — same bit, both generations. Sequence-shape
note, deliberate: §S4's prose phrased steps 1/4 as RMW; the spec's citable facts are ABSOLUTE
words (0x404, 0x20402) and the implementation writes them absolutely, printing the displaced
pre-image beside each write — the displaced bits belong to the image the prologue already
destroyed. Budget: the implementation caps the spinwait at min(spec 10 s, `hw_wait_budget()`) and
prints elapsed.

**Fact 5 — the handshake.** `[SPEC-V3 SHM]` shared layout: 0x0000 "uCode Revision High 16 bits",
0x0002 "uCode Revision Low 16 bits" (also 0x0016 Core Revision, 0x0050 PHY Revision). NAME
MISMATCH, flagged: the tree's b43-lineage constants read the four words at 0,2,4,6 as
rev/patch/date/time; V3 reads 0/2 as one 32-bit revision and does not document 4/6. Mechanics
identical (four 16-bit shared reads through routing 0x0001 — S4a's metal-proven path); the witness
prints all four RAW plus BOTH decodes and gates only on what both agree on: 0/0xFFFF means "not
running", and the one hard floor is rev > 0x128 (296). Falsifiable predicate: Ready fires;
UCODEREV ∉ {0, 0xFFFF}, > 296; MACCTL shows PSM_RUN=1, PSM_JMP0=0.

**Fact 6 — initvals are NOT this arc.** `[SPEC-V3 InitialValues]`: initvals records are
per-register **MMIO** writes, not an SHM stream; `[SPEC-V3 ChipInit]` orders them at **step 8,
after Ready** — so M2/M3 is complete without touching them; they stay staged and gate-2-validated
for the S5-side arc. Routing 0x0301 is recorded, uncertain in the spec itself ("?"), and unused.

**Fact 7 — the prologue's residual, and the mitigation.** The wrapper-level reset
(RESET_CTL/IOCTL at +0x800/+0x408) is an AI/AXI-wrapper sequence documented in NEITHER spec
generation (both document only the SSB-era backplane) — those register facts stay **Group-B,
recorded**, the same class R6 already writes under. The unpinned IOCTL FLAG VALUES are sidestepped
entirely: metal (Boots AO+, four boots) measures `ioctl=0x00002055` = the completed-bring-up word
(S3's own decode), so the prologue **preserves the measured word** across the reset — read
`ioctl_found`; `IOCTL <- found|FGC|CLK`; `RESET_CTL <- RESET` (the destructive step); `RESET_CTL
<- 0`; `IOCTL <- found` — only pinned bits added, no PHY_RESET pulse (the PHY arrives out of reset
and is never put into it). Fallback, enforced in code: if `ioctl` at prologue time is not the
S3-shape word (CLK set, FGC + PHY_RESET clear), the prologue REFUSES — the preserve-the-word
argument holds only for the word four boots measured.

**Fact 8 — the sequence end to end** is implemented as `upload_ucode()` in `bringup.rs`, feature
`wifi3` (`UNAOS_WIFI3=1`, implies `wifi2`): prologue guard → preserve-word reset → MACCTL 0x404 →
`SHM_CONTROL <- 0x03000000` → 9938-word stream → readback verify (FNV, first/last) → `0x128 <-
0xFFFFFFFF` → MACCTL 0x20402 → Ready spinwait → dummy read → shared-memory handshake → verdict.
Failure past the prologue has NO unwind (§5 risk 4: the resident image is gone; stated on the wire
at BEGIN) — the verdict names the first failed leg and `bringup_once`'s R8 window-restore still
runs. The default build's gate-3 refusal SURVIVES, its reason renamed
`shm-ucode-routing-UNPINNED` → **`wifi3-not-armed`** — the unknown is settled and the line must
stop claiming otherwise.

Residuals, open and non-blocking: (1) AI-wrapper facts stay Group-B (recorded since GR25); (2) the
~10 µs pacing is margin, not spec; (3) rev-low-16 vs patch at 0x0002 is interpretive only; (4) the
expected revision NUMBER for broadcom-wl-5.100.138's ucode29 is pinned by no legal source — the
witness prints what the PSM publishes and gates only on the >296 floor. QEMU note: QEMU models no
BCM4331, so the upload is unreachable there; the QEMU gate for `wifi3` is compile + `strings`
tokens only, and the first armed boot is metal, destructive, and Peter's to schedule.

### S4a — WIFI-S4a: identify the RESIDENT microcode — **IMPLEMENTED, awaiting metal**

Same knob (`UNAOS_BCMAS1=1`), same block as S1/L0/S2r, and it runs inside `d11_l0` immediately after
S3's verdict — deliberately, because `PSM_RUN` is the context that decides whether an identity word
means anything, so it must already be on the wire when this stage's lines are read. Its witnesses
carry the `wifi-s4a:` prefix.

**This is the first MMIO write in `drivers/bcma.rs`.** Every stage above it writes exactly one *PCI
config* register (`cfg:0x80`, the BAR0 core selector) and restores it; none of them writes a device
register. S4a writes one, and the whole stage exists to make that write as small as a write can be.

#### What it settles, and why it could not be settled read-only

§S3 established that the d11 arrives with `MACCTL.PSM_RUN` set: **somebody's microcode is executing in
that processor right now**, and the `IOCTL` bits say it was put there by something shaped like b43.
WIFI-L0 could not name it. A running d11 microcode publishes its own revision, patch level and build
stamp into shared memory — but shared memory is behind an indirect window whose *read* requires first
*writing* the address, so L0 explicitly declined it (`SHM_CONTROL` is on L0's "deliberately not read"
list for exactly this reason). S4a is that write and nothing more.

#### The mechanism, and where every offset came from

| constant | value | provenance |
|---|---|---|
| `SHM_CONTROL` | `d11+0x160` | `B43_MMIO_SHM_CONTROL`. **Already in this tree** — named in `bcma.rs`'s "deliberately not read" comment block since L0 (that block now carries "…until S4a, which does open it", so it no longer contradicts the stage that cites it), and in §S4 above |
| `SHM_DATA` | `d11+0x164` | `B43_MMIO_SHM_DATA`. Already in this tree, same places |
| `SHM_DATA_UNALIGNED` | `d11+0x166` | `B43_MMIO_SHM_DATA_UNALIGNED`. **New in this arc**, transcribed from b43 `b43.h`; used for the odd 2-byte half of a dword |
| routing `B43_SHM_SHARED` | `0x0001` | b43 `b43.h` shared-memory routing enum |
| `UCODEREV` / `UCODEPATCH` / `UCODEDATE` / `UCODETIME` | shared byte offsets `0x00` / `0x02` / `0x04` / `0x06` | `B43_SHM_SH_UCODE*`, b43 `b43.h`. **Already named in §S4 above**, which is where this arc took them from |

**The access rule, `b43_shm_read16` step for step.** For `B43_SHM_SHARED` the caller's BYTE offset is
converted to a DWORD index (`offset >> 2`) and written as `(routing << 16) | index`; the data port then
depends on the offset's low bits — a 4-aligned word comes out of `SHM_DATA`, the odd 2-byte half out of
`SHM_DATA_UNALIGNED`. **The control word is identical for both halves of a dword; only the port
differs.** So the four identity words need exactly **two distinct window SELECT VALUES** (`0x00010000`
for `UCODEREV`/`UCODEPATCH`, `0x00010001` for `UCODEDATE`/`UCODETIME`).

**The stage nevertheless issues FOUR writes**, re-writing the select before every read, and the `end`
line reports the count it actually made (`wrote-shm-control=4`), not the number of distinct values.
Two distinct select values, four writes; the two numbers are different things and the witness says
which is which.

The justification is *not* "nothing establishes whether the window auto-increments". Something does,
on the write side, and this document has said so since before S4a existed: §S4 above describes b43
streaming ucode "through an autoincrementing window", and `b43_upload_microcode` writes the control
word **once** and then loops on `SHM_DATA` — which only works because **a data-port access advances
the index**. What b43 does not establish is whether a *read* of the data port advances it the same way
a write does; b43's own read helper re-writes the control word every time, so the question never
arises there either.

That makes the re-write load-bearing rather than merely cautious: **a data-port access moves the
index, so the four reads are independent ONLY because the select is rewritten in front of each one.**
Collapsing four writes to two would make read #2's word depend on whether read #1 advanced the index —
folding the exact unknown this stage exists to remove into the measurement instead of measuring it.

#### The safety argument, and it is on the wire

The probe writes **one register: `SHM_CONTROL`**, an address-window select on the read path. On the
`begin` line, in full:

* **not `SHM_DATA`** — no shared-memory word and no PSM instruction is modified. The upload path S4
  owns (stream words into `SHM_DATA` with the window on `B43_SHM_UCODE`) is precisely what this does
  not do;
* **not `MACCTL`** — `PSM_RUN` and `PSM_JMP0` are exactly as the machine handed them over;
* **not the wrapper `RESET_CTL`/`IOCTL`** — nothing is reset or re-clocked;
* **not `RADIO_CONTROL`** — no radio-silicon register is even addressed.

The resident image keeps running, unaltered, for the whole stage. That is the point: an image that had
to be disturbed to be identified could not be identified.

**The guard on that write is re-read LIVE, immediately before it.** `d11_l0` verified `cfg:0x80` at
its step 1 — before the wrapper walk, the DMP identification block, the core register reads, the TSF
pair and §S3's verdict — and handing that stale boolean down to guard an MMIO *write* would be the
same mistake this file already refuses for a config *read* ("a witness that says 'live' should not be
quoting a value captured several stages earlier"). So S4a reads `cfg:0x80` again and gates on that,
printing `selector LIVE re-read cfg:0x80=… == d11 base …` or refusing with
`REFUSED stage=selector reason=drifted-since-l0`. The failure it prevents is concrete: any stage
inserted between L0 step 1 and S4a that moves the window leaves this probe writing `0x00010000` into
offset `0x160` of whatever core is selected — plausibly ChipCommon, where `+0x160` is not an
address-window register and the "garbage in, garbage out" argument evaporates entirely. The safety
case above is a statement about `SHM_CONTROL` specifically; it does not survive the window moving.

**The control readback is downstream of the measurement, not between the select and it.** b43 never
reads `SHM_CONTROL`, so that readback is an access with no upstream precedent — and on a window whose
data-port accesses are known to advance an index, an untested access sitting between the select and
the data read is exactly the shape of thing that would corrupt the number it was added to
corroborate. `shm_read16_shared` therefore reads the DATA port first and the control readback second.

**Odd byte offsets are refused, as b43 refuses them.** `b43_shm_read16` carries
`B43_WARN_ON(offset & 1)`; without that check an odd offset routes to `SHM_DATA_UNALIGNED` and returns
a *different* word with nothing on the wire to say so. The guard is in `shm_read16_shared`. Like
b43's, it compiles out at the current call sites (all four offsets are even `const`s), so its witness
is deliberately **not** among the reachable `wifi-s4a` strings — it is a source-level invariant that
becomes a runtime witness the moment an offset stops being a constant.

**Worst case if an offset here is wrong: a wrong routing value or dword index reads a *different*
shared-memory word.** Garbage in, garbage out — a misleading number on the wire, not damage. There is
no write-side consequence because there is no write to the data port. That asymmetry is why this probe
is worth making before the upload path exists, and it is stated rather than assumed.

b43 uses this same window, with the PSM running, for every runtime shared-memory access it makes; the
operation is ordinary. The `end` line carries the audited zeros: `wrote-shm-control=4` (a *derived*
count, not a hard-coded one), `wrote-shm-data=0(audited)`, `wrote-macctl=0(audited)`,
`wrote-wrapper=0(audited)`, `wrote-radio=0(audited)`, `uploaded-bytes=0(audited)`.

**And L0's own `end` line no longer claims a zero S4a violates.** `d11_s4a_shm_probe` is called from
*inside* `d11_l0`, eleven lines before that line prints, and `SHM_CONTROL` *is* a d11 core register —
so `wrote-core-regs=0(audited)` was false on any boot that reached S4a. It now reads
`wrote-core-regs=0-by-L0-ITSELF(audited; …)` and points at the `wifi-s4a: end` line where S4a's writes
are counted. An audited zero that the same call frame violates is the one thing this driver's witness
discipline exists to make impossible.

#### The witness

```text
:: wifi-s4a: begin — SHM probe of the RESIDENT microcode. WRITES: SHM_CONTROL (d11+0x160) ONLY … macctl=… psm-run=… shm-enabled=… shm-upper=… big-endian=… ::
:: wifi-s4a: selector LIVE re-read cfg:0x80=… == d11 base … — checked HERE, immediately before the write ::
:: wifi-s4a: shm-raw sel=[…] sel-readback=[…] select=… ucoderev=…@+0x00(port 0x164) patch=…@+0x02(port 0x166) date=… time=… ::
:: wifi-s4a: shm-decode rev=… patch=… build=YYYY-MM-DD HH:MM:SS stamp-plausible=… opensource=… b43-too-old=… hdr-format=… big-endian=… ::
:: wifi-s4a: SHM probe UCODEREV=… PATCH=… DATE=…(YYYY-MM-DD) TIME=…(HH:MM:SS) (via SHM_CONTROL d11+0x160 sel=…) — resident ucode IDENTIFIED|IDENTIFIED-SUSPECT|NOT-DECODABLE ::
:: wifi-s4a: IDENTIFIED-SUSPECT reason=… — do NOT plan S4 against this UCODEREV ::   (only when suspect)
:: wifi-s4a: end ok=… suspect=… rev=… psm-run=… shm-upper=… big-endian=… select=… wrote-shm-control=4 … ::
```

**`DATE`/`TIME` are rendered the way b43 renders them**: year `2000 + ((date >> 12) & 0xF)`, month
`(date >> 8) & 0xF`, day `date & 0xFF`; hour `(time >> 11) & 0x1F`, minute `(time >> 5) & 0x3F`, second
`time & 0x1F`.

**Every read that can fail says so distinctly, and none is folded into another:**

| name | condition | what it means |
|---|---|---|
| `REFUSED stage=selector` | `cfg:0x80` (as verified by L0) does not read back the d11 base | BAR0+0 is not the radio's window, so `d11+0x160` would be some other core's register. **Nothing is written** |
| `REFUSED stage=selector reason=drifted-since-l0` | the LIVE `cfg:0x80` re-read, taken immediately before the write, disagrees with the d11 base | the window moved between L0 step 1 and here. **Nothing is written** |
| `REFUSED stage=core reason=core-window-unread` | L0 declined the core reads | `MACCTL` is UNKNOWN; the stage will not write into a window it has not established is answering. **Nothing is written** |
| `REFUSED stage=core reason=macctl-all-ones` | the core window is dark | writing into it would prove nothing. **Nothing is written** |
| `all-ff` | all four words `0xFFFF` | the **read path** is dead. Not a statement about the microcode |
| `all-zero` | all four words `0` | **three** explanations, in the order to check them: `MACCTL.SHM_ENABLED=0` (the host SHM aperture is switched off at the MAC, so no select could have had any effect — it is on the `begin` line, it costs nothing, and it is the most likely of the three); **or** the select had no effect for a transcription reason; **or** nothing ever published an identity. The `select=` leg is the tie-breaker between the last two |
| `stuck-data-port` | all four equal, non-degenerate | the data port ignores the select. These four words have no reason to be equal, which is what makes the test sharp |
| `no-ucoderev` | structure elsewhere, `UCODEREV` is `0`/`0xFFFF` | the window works; the revision word specifically is not published (or not at this offset on this image) |

**And one state that is not a failure and is not a success:** `IDENTIFIED-SUSPECT`. Every test above
asks "are the four words uniform?" — so a window honoured against the **wrong bank**, a **big-endian**
MAC, or a build stamp that does not decode as a date all sail through them, producing four varying,
non-degenerate words. Rendering that as a flat `IDENTIFIED` would put a fabricated `UCODEREV` on the
wire and S4 would be planned against it, which is the failure this stage exists to prevent rather than
to commit. `stamp_plausible` used to be computed, printed, and then ignored by the verdict; it is a
consequence now.

| suspect reason | condition | what it means |
|---|---|---|
| `macctl-shm-upper` | `MACCTL.SHM_UPPER=1` (`0x0000_0200`) | the word index resolved against the **upper** shared-memory bank. Four real, varying words — just not the ones b43 reads at index 0/1 with the bit clear. A genuine reading of the wrong location |
| `macctl-be` | `MACCTL.BE=1` | the 16-bit words are byte-swapped relative to every decode in the file. `rev`/`patch`/`date`/`time` and all derived fields are wrong by a swap and must not be quoted until it is undone |
| `implausible-build-stamp` | words vary, `UCODEREV` non-degenerate, but `UCODEDATE`/`UCODETIME` do not decode to a real date/time and the OpenFWWF `0xFFFF` discriminator does not fire | a real b43-lineage image stamps a real build time. Four varying words that fail this are evidence the window is not landing where this file thinks it is, not an identity |

`SHM_UPPER` costs **zero** device accesses to check — `MACCTL` is already in hand from L0 — which is
why it is decoded on L0's core line, printed on S4a's `begin` and `end` lines, and consequential in
the verdict.

**The `select=` leg is advisory and says so.** b43 never reads `SHM_CONTROL`, so whether it is readable
at all is UNKNOWN on this part. The line reports three states: `CONFIRMED(readback == written)`,
`DEAD(all-ones — the MMIO path, not just the window)`, and
`NOT-READABLE(advisory — a non-echoing select is not by itself a fault)`. Only `DEAD` is load-bearing,
and it is load-bearing about the MMIO path rather than about SHM.

#### Interpretation table — what a `UCODEREV` value means for the ladder

| `UCODEREV` | reading | what it implies |
|---|---|---|
| `0x0000` / `0xFFFF` | no identity | Not decodable. See the failure table above; the mechanism is in question, not the ladder |
| `1 .. 0x128` (≤ 296) | a pre-4.x binary-driver image | b43 **rejects this band outright** (`"YOUR FIRMWARE IS TOO OLD"`). Would mean the resident image is far older than this board's generation — surprising enough to be worth chasing. The *mechanism* would be confirmed working either way |
| `0x129 .. 409` | post-rejection, `B43_FW_HDR_351` RX/TX header layout | b43 would work with it. **b43 cuts at 410 and 598 only** — its `else` branch assigns `B43_FW_HDR_351` to *every* revision below 410, including revisions below 351, so `0x129..350` and `351..409` are the **same** header bucket. There is no "pre-351" layout; an earlier draft of this section invented one |
| `410 .. 597` | `B43_FW_HDR_410` layout | b43-lineage, the middle generation |
| **`598 +`** | `B43_FW_HDR_598` layout | b43-lineage, the newest generation. **The `broadcom-wl-5.100.138` extraction `ucode29_mimo` comes from is in the upper part of this range**, so a value here is the strongest "the EFI loaded a Broadcom image of the same family `b43-fwcutter` extracts" reading available |
| any of the above with `UCODEDATE == 0xFFFF` | **open-source firmware** | b43's own discriminator (`fw.opensource = (fwdate == 0xFFFF)`); OpenFWWF stamps the date `0xFFFF` and puts its patch level in `UCODETIME`. On a 2012 rMBP's EFI this would be extraordinary — but a discriminator that cannot fire is not a discriminator, so it is decoded |

**The three names are generation markers, not gates — and there are only TWO cut points.**
`B43_FW_HDR_351` / `_410` / `_598` name which RX/TX frame-header layout a microcode generation uses,
and b43 selects between them with `if (rev >= 598) … else if (rev >= 410) … else B43_FW_HDR_351`. So
`351` is the *name* of the else-branch's layout, not a boundary anything is compared against: a
revision of 200 gets `B43_FW_HDR_351` just as a revision of 400 does. The one true rejection threshold
is `rev <= 0x128`. §S4 above previously said b43 "rejects `ucode_rev < 351` outright"; that conflated a
header-format name with the rejection, and the witness prints both separately for that reason.

#### Platform CtrlFW vs a b43-style ucode — the distinction this stage exists to make

Two shapes of resident image are consistent with everything observed so far, and they lead to different
places:

* **A b43-lineage Broadcom d11 microcode.** Publishes `UCODEREV`/`PATCH`/`DATE`/`TIME` at the b43
  offsets, because that is what those offsets *are* — part of the image's own shared-memory layout. A
  plausible revision therefore both identifies the image **and** verifies our transcription of the SHM
  mechanism on this silicon, which is the input S4 needs.
* **A platform control firmware** loaded by EFI to hold the radio in a known state for wireless
  NetBoot / Internet Recovery, without being a full b43-shaped MAC image. Such an image need not
  populate `SHM_SH_UCODE*` at all. It would read `all-zero` with `select=CONFIRMED` — the window
  working and the contents genuinely empty.

**Neither outcome is a route around S4**, and this section must not be read as one. The image cannot be
authenticated (the revision is an echo from a processor running those bytes, not a signature); we have
no file for it; we cannot rely on any firmware revision leaving it there; and S4's prologue resets the
core, which destroys it. What S4a buys is (a) an identity for the thing `PSM_RUN` has been pointing at
since Boot AL, and (b) the SHM mechanism S4 depends on, tested where a failure is a serial line rather
than a silent handshake timeout.

### S5 — PHY and radio initialisation — **the crux**

**Depends on:** S2 (calibration) and S4 (ucode).

**Writes:** thousands of PHY and radio registers, from tables. HT-PHY init tables, 2059 radio init
tables, RF calibration loops, TX power control, per-band retune.

**Proves it took:** nothing short of S6's first received frame. That is the problem.

**This stage is ALL-OR-NOTHING and it is where the project stalls or dies.** Three reasons, and they
compound:

1. **The tables are undocumented.** Every value is reverse-engineered from Broadcom's binary driver
   by the bcm-specs/b43 project. They cannot be derived, checked, or reasoned about — only
   transcribed.
2. **A wrong table gives silence, not a diagnostic.** There is no intermediate register that says
   "the PHY is 80% up". This is the opposite of every other stage in this ladder.
3. **b43's HT-PHY support is the least complete PHY in that driver.** BCM4331 has spent most of its
   Linux life marked experimental/partial. We would be transcribing the weakest target of the
   weakest part of the reference implementation.

**The only honest sub-division available** is to split by band and by function: (a) radio powered and
its ID register reading the expected 2059 id; (b) PHY reset sequence completing without the MAC
hanging; (c) channel tune to one 2.4 GHz channel; (d) RX chain enabled. (a) and (b) have read-back
predicates. (c) and (d) do not, until S6.

**Falsifiable predicate available before S6:** the radio ID register must read the 2059's id. That
is the one cheap check in this stage and it should be the first thing written.

**Stop rule:** **if S6 cannot receive a single beacon, stop the project.** Everything after S6 is
unreachable, and continuing to write S7 against a dead PHY is how months disappear.

### S6 — DMA rings and monitor-mode RX

**Depends on:** S5.

**Writes:** the 64-bit DMA engine's ring base/index registers, RX descriptor rings, RX filter and
MAC control for promiscuous/monitor operation.

**Proves it took:** **one decoded beacon frame with a real SSID printed on serial.** Not a
descriptor advancing, not an interrupt firing — a beacon whose SSID matches a network we know is in
the room. That is the project's single most important line and everything above it is scaffolding
for it.

**Falsifiable predicate:** the SSID string in the decoded beacon equals a network Peter can name,
and the frame's RSSI and channel are plausible. A garbage SSID means the PHY RX header decode is
wrong, which is S5 feedback, not S6 feedback — and distinguishing those two is why the raw RX header
bytes must be printed alongside the decode.

**Failure on serial:** descriptors never advance (DMA not running / rings mis-programmed — an S6
bug); descriptors advance but every frame fails FCS (PHY not tuned — an S5 bug). Those two lines are
the whole diagnostic value of this stage, so both must be counted separately.

**Not all-or-nothing** — but it is the **stop gate**. See S5.

### S7 — MAC / station layer

**Depends on:** S6.

**Writes:** TX DMA rings, SHM frame templates (probe request, auth, assoc), MAC control, rate
tables.

**Proves it took:** an association state reached against an **open** network — beacon seen, probe
request sent, probe response received, auth exchange completed, assoc response with a status of
success and an AID assigned.

**Falsifiable predicate:** the AP's own client list shows us. A driver that believes it associated
while the AP has never heard of it is the failure mode to design against, so the predicate must be
external to us.

**Failure on serial:** probe requests sent but no response (TX not reaching the air — check TX power
and the PHY TX chain, i.e. S5 again); response received but auth times out (frame templates or
sequence numbers wrong).

**Not all-or-nothing.** Each of scan / probe / auth / assoc has its own observable.

---

### S8 — WPA2-PSK

**Depends on:** S7.

**Writes:** nothing new in hardware terms beyond the CCMP key slots (or software CCMP).

**Needs:** PBKDF2-SHA1 (key derivation), HMAC-SHA1 (the EAPOL MIC), AES-CCMP. **This tree has no
crypto library.** That is its own sub-arc and should be sized separately; it is arch-neutral, host-
testable, and — unlike everything from S4 down — it can be developed and unit-tested with zero
hardware.

**Proves it took:** a DHCP lease over the radio. `smolnet` (smoltcp 0.13.1, DHCPv4, the default x86
net stack since 2026-07-17) does the rest unchanged the instant frames flow: ARP, IPv4, ICMP, UDP,
TCP, DNS, SNTP are all already proven.

**Falsifiable predicate:** `ping` from the UnaOS shell to the gateway, over WiFi, answered.

## 3. What this OS already has, and what it does not

**Has:** the entire stack from Layer 2 upward. `drivers/e1000.rs` (~1,300 lines) is a working DMA
ring driver with MSI delivery; `smolnet` carries the shell's `ping`/`arp`/`netinfo`, the socket
syscalls, DNS and SNTP. Hand this OS a device that produces and consumes Ethernet-shaped frames and
everything above the wire works today.

**Does not have:** anything at all below that line for radio. smoltcp has no 802.11 notion — no
scanning, no association, no WPA, no 802.11 headers, no rate control. The e1000 is a wired MAC whose
link is simply up or down and it shares essentially nothing with a SoftMAC radio beyond "DMA rings
exist".

**So: 100% of S3–S8 is work we have never done, and 0% of it is work we have.** The existing stack
does not shorten the driver; it means that *if* the radio ever delivers a frame, everything after
that already works. That is worth a great deal — but it is worth it only at S6 and later.

## 4. Knob wiring

| Place | Entry |
|---|---|
| `unaos/crates/kernel/Cargo.toml` | `bcmarecon = []` |
| `unaos/crates/kernel/src/drivers/mod.rs` | `#[cfg(all(target_arch = "x86_64", feature = "bcmarecon"))] pub mod bcma;` |
| `unaos/crates/kernel/src/arch/x86_64/pci.rs` | call site, after `full_census()`, before the GPACE anchor |
| `unaos/arroyo` (feature mapping) | `UNAOS_BCMARECON=1` → `bcmarecon` |
| `unaos/arroyo` (`arm_features`) | stripped for aarch64 — x86-only code, so leaving it enabled would shift aarch64 media hashes for zero observable change (the `sdw`/`kbdwit`/`pcicensus` argument) |
| `unaos/arroyo` (`KERNEL_CFG_MATRIX`) | appended to the `x86-all` leg; the `x86-mix-*` legs derive from that union, so the pairwise mix enrolled it automatically |
| `unaos/builder/src/main.rs` | `UNAOS_BCMARECON` → `bcmarecon` |

The builder wiring is not optional. The builder rebuilds the x86 kernel from its **own** env-derived
feature list, so a knob wired only in `arroyo` ships the feature disabled while the banner claims it
is on (s42/INSTGUI, WXN-M3b). This arc is as exposed to that bug as the census was and in the same
direction: **a recon that silently did not run is indistinguishable on the wire from a machine with
no radio in it** — and that is precisely the conclusion the path-A decision would then rest on.

Each later stage gets its own knob (`UNAOS_BCMA_S1`, …) rather than escalating `bcmarecon`, so that
"the read-only recon" and "the stage that writes the backplane window" can never be armed by the
same variable.

## 5. Risks, ranked

1. **S5 (HT-PHY) never comes up.** Highest-probability project-ending outcome. Mitigation: none
   available; the mitigation is the S6 stop rule.
2. **The firmware licensing decision is deferred rather than made**, and S4 gets written against an
   assumption. Mitigation: §S4's decision box, answered before S4 starts.
3. **The part is not a BCM4331.** Cheap to refute — S0 says so on the first boot, and S3's
   `phy_type` says so again by a different route.
4. **A backplane write wedges the bus.** S1 writes one config register and restores it, and S1c/S2r
   add no write target. **S3 turned out to need no write at all** (§S3). **S4a is the first MMIO
   write in the driver** — one address-window register (`SHM_CONTROL`) on the read path, no device
   state changed and nothing to unwind (§S4a). So the first stage that
   resets silicon is still **S4's prologue** — and it is the first stage that needs an unwind path. Its
   unwind is not free the way S3's would have been: the reset destroys the firmware-resident
   microcode the radio arrives running, and only a successful upload restores a working state.
5. **The SPROM/OTP calibration is unreadable** (the 4331 PA-line mux). Refutable at S2 and it has a
   documented workaround; it is a delay, not a wall.
