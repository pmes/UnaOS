# BCM4331 — the native AirPort driver ladder (path A)

**Target:** Broadcom BCM4331 (`14e4:4331`), the AirPort Extreme radio in the 2012 15" Retina
MacBook Pro (MacBookPro10,1). 802.11a/b/g/n, 3x3:3, PCIe, **SoftMAC**.

**Decision on record:** Peter chose **path A — own a native driver**, with the sizing understood
(8,000–15,000 lines, downloadable microcode, HT-PHY register tables). The alternatives (USB
Ethernet, AR9271 with free firmware, a `brcmsmac`-covered card swap) are recorded in
`~/unaos-bench/scratch/gr20/pci-census-report.md` §6.4 and are not re-argued here.

This document is the ladder. Each stage is independently boot-testable, carries its own witness and
its own falsifiable predicate, and names what it writes. The discipline is
`docs/dev/GEMINI/video/iGUI/LADDER-igpu-bringup.md`'s: a stage that cannot be refuted by a serial
line is not a stage.

---

## 0. Ground truth — what we actually know today

Two facts, both from our own kernel, neither assumed.

**From GR20's PCI census (`arch/x86_64/pci.rs::full_census`, `UNAOS_PCICENSUS=1`):** the
class-0x02 device this kernel has named on every rMBP boot —

```
:: x86_64 PCI: Found network controller (class 0x02) vendor 0x14e4 at 3:0.0 ::
:: x86_64 PCI: non-Intel NIC (0x14e4) — no e1000 driver, skipping ::
```

— is matched by `PciScanner::find_device(0x02, 0x00)`, i.e. subclass **0x00 = Ethernet**, and that
helper returns on its first hit. `14e4:16bc` at `3:0.1` is the BCM57765 SDXC reader; `3:0.0` is that
combo chip's Gigabit Ethernet MAC, behind a laptop with **no Ethernet jack**. A BCM4331 reports
subclass **0x80**. It could never have matched. The radio has never been examined by this OS.

**From GR20's BCMA recon (`drivers/bcma.rs`, `UNAOS_BCMARECON=1`):** stage S0 below. Read-only, and
its main structural finding is stated in §1.

**From Boot AJ (metal, first S1 flight) — the chip answers.** One config write to `cfg:0x80` and
ChipCommon reads `chipid=0x13924331`: a BCM4331, chip rev 2, package 9, **socitype 1 (AI/BCMA — it
has an enumeration ROM)**, PMU present, with the EROM at backplane `0x18107000`. The window
hypothesis in §1 is confirmed on metal and the firmware pre-image was restored byte for byte. See
S1/S1b.

**From Boot AF (metal, 2012 rMBP, first S0 flight):**

```
:: bcma: device bdf 4:0.0 14e4:4331 rev=02 ssid=106b:00ef irq=0 pin=A cmd=0x0006 (mem-decode=1 busmaster=1) matches=1 ::
:: bcma: power cap@0x40 pmcsr=0x4008 state=D0 ::
:: bcma: bar0=0xc1900000 raw=0xc1900004 type=mem64 prefetch=0 maplen=0x2000 bar0_win(cfg:0x80)=0x18001000 bar0_win2(cfg:0xac)=0x18101000 ::
:: bcma: REFUSED stage=chipcommon reason=not-decoding chipid=0xffffffff — BAR0 reads all-ones ::
:: bcma: end ok=0 stage=chipcommon elapsed=5ms ::
```

Established, and none of it assumed:

* **The radio exists and is ours to drive.** `14e4:4331` at `4:0.0`, board id `106b:00ef` (Apple),
  behind bridge `0:28.1` (`8086:1e12`, `sec=4 sub=4`, `cmd=0x0007`). One match on the whole machine.
* **It is awake and decoding.** `pmcsr=0x4008` = **D0**, `No_Soft_Reset=1`, `PME_En=0`,
  `PME_Status=0`. `COMMAND=0x0006` = memory decode ON, bus master ON. Neither "asleep" nor
  "decode disabled" is available as an explanation for anything below.
* **BAR0 is `0xc1900000`, 64-bit, non-prefetchable**, high dword zero. The census had predicted
  exactly this.
* **The BAR0 window was NOT on ChipCommon.** `cfg:0x80 = 0x18001000` and `cfg:0xAC = 0x18101000` are
  `BCMA_ADDR_BASE + 1*0x1000` and `BCMA_WRAP_BASE + 1*0x1000` — the (`core->addr`, `core->wrap`)
  pair Linux's `bcma_host_pci_switch_core()` writes for **core index 1**, which on a BCM4331 is the
  d11 802.11 core. Apple's firmware left the selector on the radio core. §1's assumption that
  firmware parks the window at the enumeration base is **false on this machine**.
* **The all-ones was therefore not a verdict about the function**, and reporting it as
  `reason=not-decoding` was a defect in our own instrument: stage 5 tested "all-ones" before it
  tested "is the window even on ChipCommon", so the `window-elsewhere` refusal that existed in the
  file could never fire whenever the off-window core was unreadable. Order corrected (window first).
* **It was not a mapping fault of ours either.** The map wire line
  `:: x86 mmio-map: 0xc1900000..0xc1902000 uc=1 (PAT PA3) wc-kept=0 ::` shows the window retyped in a
  single 2 MiB leaf — the *same* leaf `sdhc`'s BAR at `0xc1820000` lives in, and `sdhc` read its
  registers successfully later in the same boot through that leaf. Same VA range, same PAT typing,
  one works. `translate()` passed, `BAR1` was read and honoured, `maplen=0x2000` is the full
  architecturally-defined extent of BAR0 for this driver model (see §S0).

**What Boot AF could NOT answer, and what was added so Boot AG can.** The census printed `0:28.1`'s
bus-number triple (`pri=0 sec=4 sub=4`) but not its **forwarding windows** — so nothing in the
capture could say whether the bridge above the radio actually forwards `0xc1900000` downstream. A
device whose BAR falls outside its bridge's memory window reads all-ones no matter how correctly the
driver maps it, and that hypothesis was untestable from the evidence we had.
`census_print_bridge_windows()` now prints, for every header-type-1 function, the I/O window
(including the 32-bit upper halves at `0x30`), the non-prefetchable memory window, the prefetchable
memory window (including the 64-bit upper dwords at `0x28`/`0x2C`), and the bridge's **secondary
status** — the ledger where a master-abort on an unclaimed downstream read leaves a mark. `closed`
is rendered explicitly for the architectural `base > limit` encoding rather than as an inverted
range. Read-only, three config reads plus two conditional ones.

Verified under QEMU against a machine whose answer is known independently: with a `pcie-root-port`
inserted, the census prints

```
bdf 0:8.0 1b36:000c … pri=0 sec=1 sub=1 bar0=mem32@0x81285000 io=[0x6000,0x6fff]/16 mem=[0x81000000,0x811fffff] pref=[0xc000000000,0xc01fffffff]/64 secsts=0x0000
bdf 1:0.0 8086:10d3 … bar0=mem32@0x81020000 bar1=mem32@0x81000000 bar2=io@0x6000 bar3=mem32@0x81040000
```

Every downstream BAR falls inside the matching window and the 64-bit prefetchable decode is exercised.

**Prediction for Boot AG:** `0:28.1`'s memory window contains `0xc1900000`. If it does not, that is
the answer and it outranks everything in §1.

Everything else in this document is a plan, and is marked as such.

## 1. The structural finding that shapes the whole ladder

**A BCMA part behind PCIe exposes exactly ONE backplane core through BAR0 at a time, and the
selector is a PCI *config* register.**

BAR0 is a small window. Its first 4 KiB decode to whatever backplane address sits in **PCI config
register `0x80`** (`BCMA_PCI_BAR0_WIN`); the second 4 KiB decode to the address in `0xAC`
(`BCMA_PCI_BAR0_WIN2`, the wrapper window). Linux's `bcma_scan_switch_core()` writes exactly these
two registers and nothing else in order to move from core to core.

**Boot AF corrected the second half of this section.** It used to say "firmware leaves the window
parked at the ChipCommon enumeration base `0x18000000`". It does not. Apple's firmware left
`cfg:0x80 = 0x18001000` — the **d11 802.11 core**, core index 1 — with `cfg:0xAC` on its matching
wrapper. There is therefore **no core at all that is reachable read-only** on this machine, and
Linux agrees this is normal: `bcma_bus_scan()` calls `bcma_scan_switch_core(bus, BCMA_ADDR_BASE)`
*unconditionally* before it reads `BCMA_CC_ID`. It never assumes where firmware left the selector.

The consequences, and they are the entire reason the ladder starts where it does:

| Fact a driver needs | Where it lives | Reachable read-only? |
|---|---|---|
| PCI identity, ssid, D-state, COMMAND, BARs, capabilities | PCI config space | **yes** |
| `BAR0_WIN` / `BAR0_WIN2` — *which core is in the window* | cfg `0x80` / `0xAC` | **yes** |
| the selected core's wrapper: `IOCTL`, `IOST`, `RESET_CTL`, `RESET_ST` | BAR0 `+0x1000` | **yes** — added after Boot AF |
| chip id / rev / package / `ncores` / chip type | ChipCommon `0x00` | **no on this machine — needs cfg `0x80`** |
| capabilities (SPROM present, OTP size, PMU) | ChipCommon `0x04` | **no — same reason** |
| OTP status + which subregions are programmed | ChipCommon `0x10` | **no — same reason** |
| EROM backplane pointer | ChipCommon `0xFC` | **no — same reason** |
| SPROM shadow (MAC, board rev, board flags, PA cal) | ChipCommon `0x800`/`0x830` | **no — same reason**, plus §S2's caveat |
| **the EROM itself — the core inventory** | backplane, ~`0x18010000` | **no — needs cfg `0x80`** |
| **the 802.11 (d11) core registers** | backplane, address from the EROM | **no — needs cfg `0x80`** |
| **PHY type / revision** (`d11 + 0x3E0`) | inside the d11 core | **no — needs cfg `0x80`** |
| OTP *contents* | via a read command written to ChipCommon `0x18` (OTPP) | **no — needs a write** |

So **one 32-bit config write gates the entire backplane** — and after Boot AF that is not a claim
about convenience but the literal state of the machine: the read-only ceiling is PCI config space
plus one core-wrapper's worth of registers, and nothing else. S1 is defined as "make that one write,
and nothing else."

**The exact write, named and not made:**

```
cfg:0x80  (BCMA_PCI_BAR0_WIN, bdf 4:0.0)  <-  0x18000000   (32-bit)
```

Why this one and not another: it is the *smallest* possible unblocking write in the whole ladder. It
touches no backplane register, changes no device state, resets nothing, and is a pure address-decode
selector on the host side of the PCIe function. Linux issues it before it reads anything at all. It
is nevertheless a write, so S0 stops here and reports it.

**One discipline it must carry (S1's, recorded here because Boot AF is why we know it matters):**
the pre-image of `cfg:0x80` on this machine is **not** `0x18000000` — it is `0x18001000`. A stage
that "restores" the window to the enumeration base because that is what it assumed firmware left
would silently change the machine for every later boot stage. The restore must push the value it
actually read.

## 2. The staged ladder

Dependencies are strictly linear: each stage needs every stage above it. Where a stage is
**all-or-nothing** it is marked; those are the stages that cannot be developed incrementally, where
a wrong value gives silence rather than a diagnostic.

| # | Stage | Writes | All-or-nothing? |
|---|---|---|---|
| S0 | Recon | nothing | no — pure evidence |
| S1 | Backplane window + EROM walk (**window CONFIRMED on metal, Boot AJ; walk corrected in S1b**) | 1 config register (cfg:0x80), pre-image saved + restored | no |
| S2 | Board identity: SPROM / OTP calibration | ChipCommon control | no |
| S3 | Core enable: reset + clocks on the d11 core | core wrappers | no |
| S4 | Firmware (microcode) upload | d11 shared memory | **partly** — the handshake is binary |
| S5 | PHY + radio init | thousands of PHY/radio regs | **YES — the project's crux** |
| S6 | DMA rings + monitor RX | DMA engine registers | no |
| S7 | MAC / station layer (scan, auth, assoc) | templates, SHM, TX rings | no |
| S8 | WPA2-PSK | none new — crypto + EAPOL | no |

### S0 — Reconnaissance (`UNAOS_BCMARECON=1`) — **flown, Boot AF; revised for Boot AG**

**Writes:** none. Config-space reads and BAR0 reads only. Mapping BAR0
(`arch::memory::map_mmio_window`) is a page-table edit; the device sees nothing.

**Does:**
1. Sweeps all buses/devices/functions (MF-gated) for class `0x02` **subclass `0x80`**, counting
   every match. Prints vendor:device, bdf, revision, subsystem id, IRQ/pin, COMMAND, plus the
   existing `[PCI-PROBE]` capability dump.
2. Reads the PM capability's PMCSR and refuses the BAR if the function is not in D0. **Full** PMCSR
   decode (power state, `No_Soft_Reset`, `PME_En`, `PME_Status`, `Data_Select`, `Data_Scale`), so a
   reader can check the D-state claim rather than take it.
3. Refuses the BAR if COMMAND bit 1 (memory decode) is clear.
4. Decodes BAR0 raw (64-bit/prefetchable per the census's prediction, with `BAR1` printed as the
   high dword it actually read), maps `0x2000` of it UC, verifies the mapping with `translate()`.
5. Reads `BAR0_WIN` (cfg `0x80`) and `BAR0_WIN2` (cfg `0xAC`) and **decodes both as core / wrapper
   indices on the standard grid** (`window-decode core-index=… wrap-index=… paired=…
   on-enum-base=…`). A window off the grid is printed `off-grid`, never as an index.
6. **Stage 4b (new):** reads the selected core's wrapper through BAR0`+0x1000` — `IOCTL` (`0x408`),
   `IOST` (`0x500`), `RESET_CTL` (`0x800`), `RESET_ST` (`0x804`) — and applies Linux's
   `bcma_core_is_enabled()` rule (`clk` set, `fgc` clear, not in reset). This is the discriminator
   Boot AF lacked; see the prediction below.
7. **Refuses to decode ChipCommon if the window is not at `0x18000000`, tested BEFORE the all-ones
   test.** That order is the Boot AF fix: "the window is elsewhere" is a fact about `cfg:0x80` that
   needs no MMIO read to be true, whereas "all-ones" only means anything once BAR0+0 is known to be
   ChipCommon. Reversed, an off-window core in reset gets reported as a dead function.
8. With the window on the enumeration base: prints ChipCommon raw first, then decoded — chip
   id/rev/pkg/`ncores`/type, capabilities, capabilities-ext, chip status, EROM pointer.
9. Tests EROM containment in the live window. Walks it if reachable; otherwise emits
   `REFUSED stage=erom reg=cfg:0x80` **with the EROM's address**, which is the value S1 must write.
10. Reports SPROM presence; if present, dumps 220 shadow words and decodes revision + a MAC
    candidate with an explicit `PLAUSIBLE` / `SUSPECT` / `NO-DATA` verdict. Reports OTP size and
    which subregions are programmed; refuses OTP *contents* naming OTPP.
11. Refuses the PHY version read, naming cfg `0x80` and `d11+0x3E0`.

**On `maplen=0x2000`.** Not a guess and not a BAR size. On a BCMA PCIe host BAR0 is exactly two
4 KiB apertures and Linux's own accessors say which is which: `bcma_host_pci_read32` reads
`mmio + offset` (the core window, cfg `0x80`) and `bcma_host_pci_aread32` reads
`mmio + 1*BCMA_CORE_SIZE + offset` (the wrapper window, cfg `0xAC`). No bcma accessor indexes past
`2*BCMA_CORE_SIZE`, so `0x2000` is the whole extent this driver model defines. The BAR's **physical**
size remains unknown — reading it needs the write-all-ones/read-mask/restore sizing dance, which
this arc does not perform — but the inequality runs the safe way: both windows exist and are used,
so the true size is at least `0x2000` and mapping `0x2000` cannot map past the BAR.

**Also fixed after Boot AF:** the `core_name()` table used by the EROM walker was wrong on nearly
every id past ChipCommon (it named `0x812` "mips-33" and `0x820` "d11(802.11)"; Linux's
`bcma.h` has `BCMA_CORE_80211 = 0x812` and `BCMA_CORE_PCIE = 0x820`). Nothing had run the walk yet,
so no capture could have caught it — and it would have sent S3 at the PCIe core while calling it
the radio. Retranscribed in full.

**Proves it took:** `:: bcma: end ok=1 stage=chipcommon chip=0x4331 … ::`.

**Failure on serial:** every stage has a `REFUSED`/`no-device` line naming its reason; the closing
`ok=0 stage=<name>` says which one stopped it. `no-device` is the expected QEMU reading and is also
the reading that would refute the whole premise on metal.

**Falsifiable prediction for the next metal boot (Boot AG), stated before it flies.** With the
window still at `0x18001000`, S0 must now print `REFUSED … reason=window-elsewhere` and **not**
`reason=not-decoding` — anything else convicts the reorder. And stage 4b splits the two live
explanations of Boot AF's all-ones:

| Boot AG wrapper reading | What it establishes | What S1 becomes |
|---|---|---|
| wrapper answers (not all-ones), `in-reset=1` or `clk=0` | The function decodes; BAR0+0 read all-ones because the window sits on a d11 core that is held in reset / clock-gated. Nothing upstream is wrong. | The single `cfg:0x80 <- 0x18000000` write, as planned. S3's job (releasing d11 reset) is already half-mapped by this wrapper. |
| wrapper answers, `core-enabled=1` | The function decodes *and* the core is running, so all-ones at BAR0+0 is a property of that core's register 0, not of reachability. | Same write; but re-examine what core index 1 actually is before trusting the grid. |
| wrapper ALSO all-ones | The block that survives reset is silent too, so "core in reset" is refuted. Blame moves upstream: the PCIe link, or `0:28.1` not forwarding `0xc1900000`. | Blocked on the bridge-window census line for `0:28.1` (§0), not on `cfg:0x80`. |

**Bounds:** structural entry cap on the EROM walk (`EROM_MAX_ENTRIES = 512`), plus a TSC deadline
(`now_cycles()` / `hw_wait_budget()`) on the walk and the SPROM dump. Never `arch::ms()` — the APIC
tick does not advance with interrupts masked, and this runs inside `pci::init`.

### S1 — Backplane window + EROM walk — **FLOWN, Boot AJ: window CONFIRMED, walk fixed in S1b**

**Boot AJ result, in one line.** The window hypothesis is **confirmed** and the unwind held:

```text
:: bcma-s1: WROTE cfg:0x80 old=0x18001000 new=0x18000000 readback=0x18000000 took=1 ::
:: bcma-s1: cc-raw chipid=0x13924331 cap=0x58500000 cap_ext=0x00000001 chipstatus=0x00000002 erom=0x18107000 ::
:: bcma-s1: RESTORE cfg:0x80 <- pre-image 0x18001000 readback=0x18001000 restored=MATCH ::
:: bcma-s1: end ok=1 stage=window chip=0x4331 window-hypothesis=CONFIRMED restore=MATCH wrote-cfg80=1 ::
```

One 32-bit config write turned a function that had read `0xffffffff` for the life of the project
into a chip that answers with its own identity, and the recorded pre-image went back byte for byte.
The EROM pointer — `0x18107000`, the address the whole rest of the ladder hangs off — is now a
measured value rather than an assumption.

**The one thing that did not work:** the EROM walk found zero cores. That is S1b, below; the
walk's defect was entirely in this file's transcription of the entry format, and Boot AJ's own
abort line was enough to convict it.

**Status.** Written in `drivers/bcma.rs` as `s1_window_walk()`, gated by the `bcmaS1` cargo feature
(`UNAOS_BCMAS1=1`). The `bcmaS1` feature **implies `bcmarecon`**, so S1 rides on top of S0: `recon()`
runs the read-only pass first (its `REFUSED … window-elsewhere` line is unchanged and remains S0's
deliverable), then — only when the knob is armed — the S1 block, prefixed `:: bcma-s1: … ::`. Riding
on `bcmarecon` is also what lets S1 reuse S0's `find_wifi()`/`find_cap()`/BAR-map helpers and share
the existing x86-only module gate and the single call site in `arch/x86_64/pci.rs` (untouched by this
arc). Gate green (11 cfg legs, both arches); QEMU exercises only the `no-device` refusal (it models no
BCM4331), so the write path's first execution is on metal. Default OFF ⇒ no S1 code and zero
`bcma-s1` witness strings; media byte-identical.

**The implemented sequence** (each step a witness that can say NO; no early return between the first
window move and the restore):

1. **Guard, then record the pre-image.** The window write is issued ONLY when both the Broadcom
   vendor id (`0x14e4`) **and** the 4331 device id (`0x4331`) read back — a stray class-0x02/sub-0x80
   function, or a future QEMU model, is refused with no write. Then cfg `0x80` and cfg `0xAC` are read
   and **stored**; the `0x80` value is the sole restore target. `0x18000000` is never used as a
   restore value anywhere in the stage.
2. **Prove the unwind before moving anything.** The pre-image is written *back to itself* (a no-op:
   the value cfg `0x80` already holds, so the window does not move and the device sees no state
   change) and read back. This exercises the exact write+readback the final restore depends on; a
   mismatch aborts with the window still on the firmware value (`REFUSED stage=unwind-selftest`). This
   is the igpu-lane discipline: a self-test, not a bare write.
3. **The write.** `cfg:0x80 <- 0x18000000` — Linux's `bcma_scan_switch_core(BCMA_ADDR_BASE)`.
   Witnessed with old, new, and readback.
4. **Read ChipCommon** through BAR0+0: `chipid` (low 16 = `0x4331` expected), rev/pkg/`ncores`/type,
   capabilities, cap-ext, chip status, the EROM pointer. If `chipid` is **still `0xFFFFFFFF`** after
   the window move, that **REFUTES** the window hypothesis (the move was not the blocker; blame is
   upstream — link or the `0:28.1` bridge window) and is printed as a finding, never a silent pass.
5. **Walk the EROM.** A second window write points cfg `0x80` at the (page-aligned) EROM base; the
   recon's `walk_erom()` is reused verbatim; the walk's core count is cross-checked against
   ChipCommon's `ncores`.
6. **Restore.** `cfg:0x80 <- pre_win` (the **stored** value), read back, and witnessed
   `restored=MATCH`/`FAILED` by comparing to the stored pre-image — **not** to `0x18000000`. A failed
   restore is a hard finding (the radio's window is left moved for the next stage to misread).

The rest of this section is the design as specified before implementation; the code follows it, with
the one deviation that S1 writes **only** cfg `0x80` (not `0xAC`) — the wrapper-window write is
deferred to the stage that actually needs wrapper state, keeping S1's write surface at the single
selector.

**Depends on — REVISED after Boot AF.** The old dependency was "S0 reporting `ok=1` and an EROM
pointer". That is now unreachable: on this machine S0 cannot report `ok=1`, because the window
firmware left behind does not contain ChipCommon and no read-only path exists to move it. S1's real
dependency is therefore weaker and already satisfied: **S0 reporting a Broadcom function in D0 with
memory decode on and a mapped BAR0** — Boot AF gave all three. S1 now owns the ChipCommon read as
well as the EROM walk.

**Writes:** **exactly one register to start.** PCI config `0x80` (`BCMA_PCI_BAR0_WIN`), 32 bits,
set FIRST to `0x18000000` (`BCMA_ADDR_BASE`) to bring ChipCommon into the window — this is
`bcma_scan_switch_core(bus, BCMA_ADDR_BASE)`, exactly what Linux does before its first `BCMA_CC_ID`
read — then to the EROM base ChipCommon reports, then once per core to read wrapper state. Nothing
on the backplane is written. `0xAC` (`WIN2`) may be written to reach wrapper windows; it is the same
class of write and should land in the same stage, not a later one.

**Restore discipline — and Boot AF is the reason it is not a formality.** The pre-image of `0x80` is
read and pushed before the first write and restored at the end of the stage, in the `igpu`
unwind-stack spirit. On this machine that pre-image is **`0x18001000`, not `0x18000000`**. A stage
that "restores" to the enumeration base because that is what it assumed firmware left would silently
change the machine for every later boot stage — and would look like a successful restore in every
log line. Push the value read; never the value expected.

**First falsifiable predicate, before the walk even starts:** after writing `0x18000000` to
`cfg:0x80`, ChipCommon `0x00` must read a chip id of `0x4331` in its low 16 bits. If it still reads
`0xFFFFFFFF`, the window register is not the blocker and S1 stops there rather than proceeding to
walk a dead window.

**Proves it took:** the walker already written in `drivers/bcma.rs` (`walk_erom`) starts printing:

```
:: bcma: core[0] id=0x800 (chipcommon) rev=… mfg=0x4bf class=0 base=0x18000000 wrap=0x18100000(swrap) …
:: bcma: core[1] id=0x812 (d11(802.11)) rev=… base=0x18001000 wrap=0x18101000 …
:: bcma: core[2] id=0x820 (pcie) …
:: bcma: erom-walk cores=N entries=… stop=end-tag elapsed=…ms
```

**Falsifiable predicate — WITHDRAWN, see S1b §"the ncores trap".** This section previously claimed
`cores == ncores` as a predicate. It is not one: `ncores` is `BCMA_CC_ID_NRCORES`, the Sonics-era
CoreCount field, and on a socitype=1 (EROM) part the EROM is the only authority. Linux's bcma never
reads it. The surviving predicate: exactly one core with `id=0x812` (`BCMA_CORE_80211`) must be
present, and its `base` must be 4 KiB-aligned and inside `0x18000000`'s region.

**Third predicate, and it is free — Boot AF already paid for it.** Firmware left `cfg:0x80` at
`0x18001000` and `cfg:0xAC` at `0x18101000`. If the grid reading is right, the walk must return a
core whose `base` is **exactly** `0x18001000` and whose `wrap` is **exactly** `0x18101000`, and that
core must be the d11. This is a cross-check between two entirely independent sources — a config
register firmware wrote, and an on-chip ROM we walked — and a mismatch means the grid arithmetic in
`grid_index()` is a coincidence rather than a layout.

**Failure on serial:** `stop=all-ones` (window did not move / device stopped decoding),
`stop=cib-malformed` / `mp-malformed` / `addr-malformed` (the walk desynchronised — the one failure
mode that would otherwise produce plausible-looking nonsense, which is why the tags are checked and
not assumed), `stop=entry-cap` or `stop=tsc-deadline` (unbounded EROM).

**Not all-or-nothing.** Every line stands alone; a partial walk is still evidence.

### S1b — the EROM walk, corrected — **IMPLEMENTED, awaiting metal**

Same knob (`UNAOS_BCMAS1=1`), same three cfg:0x80 writes and the same restore. Read-only otherwise;
S1b adds no write target. The whole arc is decode.

**What Boot AJ printed, and why it is a complete diagnosis:**

```text
:: bcma: erom-abort at entry 4 while consuming 2 master ports of core id=0xf80 ::
:: bcma: erom-walk cores=0 entries=4 stop=mp-malformed elapsed=0ms ::
```

The first EROM dword on any BCMA part is ChipCommon's CIA. `id=0xf80` is that word read through the
wrong mask. One word, `0x4BF80001`, two decodes:

| mask set | manuf | id | class |
|---|---|---|---|
| as shipped (`mfg[11:0]`, `id[23:12]`, `class[27:24]`) | `0x001` | `0xf80` | `0xb` |
| corrected (`mfg[31:20]`, `id[19:8]`, `class[7:4]`) | `0x4bf` (BCM) | `0x800` (chipcommon) | `0` |

The shipped masks put the manufacturer field on top of the 4-bit tag/valid nibble — which no EROM
layout can do, because the tag has to live somewhere. The corrected layout is Linux
`drivers/bcma/scan.h` (`SCAN_CIA_*`, `SCAN_CIB_*`) / Broadcom `siutils_priv.h` (`CIA_*`, `CIB_*`).

The same line convicts the CIB masks at the bit level. `nmp=2` came out of `(cib >> 13) & 0xF`, so
ChipCommon's real CIB has bits 16:13 = `0b0010` — bit 14 set — and bit 14 is the low bit of the
corrected `CIB_NMW` (18:14). "Entry 4" is arithmetic: CIA at 0, CIB at 1, two entries consumed
before the tag check failed, so entry 2 really did carry the master-port tag and entry 3 —
ChipCommon's **first address descriptor**, its base — was eaten as a second master port.

**Three defects, one arc:**

1. **CIA/CIB field positions** (above). Anchored to the metal word, not to memory.
2. **Address descriptors were classified with the wrong tag mask.** Bit 3 of an address descriptor is
   `AD_AG32` ("a high address dword follows"), not tag. Linux masks address entries with
   `SCAN_ER_TAGX = 0x6`; the code used the full `0xE`. Worse, `ADDR_AS_64` was `0x04` — bit 2, a tag
   bit *set on every address descriptor* — so the walk would have read a phantom high dword for every
   address on the chip and desynchronised immediately. `AD_SZ`/`SZD` were shifted a bit as well.
3. **Fixed arity.** The walk consumed exactly `nsp + nmw + nsw` address descriptors. An EROM declares
   PORTS, not descriptors; a port carries one or more, and the list ends only when the next entry
   fails to match that port *and* type. The walk is now `bcma_get_next_core` step for step, over a
   **pushback cursor** (`Erom::peek` never advances; every accessor advances only on a match) — plus
   the not-a-core filters Linux applies (ARM `0xFFF` placeholder, no slave port, wrapper-less unless
   PMU/GCI/CC-B/4706-gbit-common, bridge), each of which is now *printed* as an `erom-skip` line
   rather than silently folded into the count.

**The `ncores` trap.** `chipid = 0x13924331` decodes, field by field, with Linux's own masks:

| field | mask | bits | value |
|---|---|---|---|
| `ID` | `0x0000FFFF` | 15:0 | `0x4331` |
| `REV` | `0x000F0000` | 19:16 | `2` |
| `PKG` | `0x00F00000` | 23:20 | `9` |
| `NRCORES` | `0x0F000000` | 27:24 | `3` |
| `TYPE` | `0xF0000000` | 31:28 | `1` = AI/BCMA, has an EROM |

Our decode was already right; the *use* was wrong. `NRCORES` is the Sonics-backplane CoreCount that
`sb_numcores()` reads. On a socitype=1 part the EROM is authoritative and Linux's bcma sets
`nr_cores` from the walk without ever looking at `NRCORES`. So `walk-cores != 3` is expected, not a
fault. The witness now says exactly that, and its verdict is `WALK-FAILED` iff `cores == 0`. GR20's
"6-10 cores" estimate was never contradicted by `ncores=3`.

**The sharp prediction.** Firmware left `cfg:0x80 = 0x18001000` and `cfg:0xAC = 0x18101000`. If the
corrected walk is right, it must independently report the d11 core (`id=0x812`) at **exactly**
`base=0x18001000` and `swrap=0x18101000` — a config register Apple wrote, versus an on-chip ROM we
walked, agreeing to the bit. That pair, on the new `erom-d11 FOUND` line, is the arc's deliverable
and the input to S3.

**New witness lines:** `erom-skip …`, `erom-walk cores=N skipped=K entries=E stop=…`,
`erom-d11 FOUND|ABSENT …`, and the cross-check reworded to advisory. `core[i]` now carries `mfg` and
`swrap`/`mwrap` separately — they are not interchangeable, and a bring-up stage handed a *master*
wrapper looks exactly like a core that will not come out of reset.

### S2 — Board identity: SPROM or OTP

**Depends on:** S1 (the ChipCommon core address, and — for OTP — its wrapper).

**Writes:** on BCM4331 specifically, Linux calls `bcma_chipco_bcm4331_ext_pa_lines_ctl(cc, false)`
**before** reading the SPROM shadow, because the external power-amplifier control lines are muxed
onto the SPROM pins. That is a ChipCommon control write and it is why S0's SPROM dump is reported
with a plausibility verdict rather than asserted valid. For OTP: a read command written to
ChipCommon `0x18` (OTPP) per word, polled through OTPS.

**Proves it took:** a MAC address with a unicast OUI and an SPROM revision in `[8, 11]`; and — the
stronger predicate — **the SPROM CRC-8 validates**. The CRC is deliberately *not* computed in S0
(the polynomial is not transcribed in this tree and a wrong table would produce a lying `BAD` on a
good SPROM); transcribing `bcma`'s 256-entry table is an S2 deliverable and turns "we read 220 words
of something" into "this is the board's calibration".

**Falsifiable predicate:** the MAC read from SPROM/OTP must match the one Apple's firmware knows —
compare against the `ssid=` subsystem id and, better, against a MAC observed on the air from another
machine. Also: `board_type` should equal the PCI subsystem device id (that is where Linux takes it
from), so the two must agree.

**Failure on serial:** `NO-DATA` (all-`0xFFFF` or all-zero shadow — the mux, or genuinely blank),
`SUSPECT` (multicast bit set in byte 0, or an unsupported revision), CRC mismatch.

**Apple boards commonly use OTP rather than SPROM.** S0 reports which by reading ChipCommon
capabilities bit 30 and the OTP GUP bits; S2 must handle whichever S0 found, and the two paths are
different enough that discovering it in S0 is what stops S2 being written twice.

**Not all-or-nothing** — but note that **without correct calibration the PHY cannot be brought up
and TX is out of regulatory spec.** S2 is a hard prerequisite for S5, not an optimisation.

### S3 — Core enable: reset and clocks on the d11 core

**Depends on:** S1 (the d11 core's base and wrapper addresses).

**Boot AF gave this stage a free head start.** Firmware left `cfg:0x80`/`cfg:0xAC` pointed at the
d11 core *and its wrapper*, so S0's stage 4b reads the exact `IOCTL`/`IOST`/`RESET_CTL`/`RESET_ST`
values S3 will have to write — for the right core, without S1 having run. Boot AG's
`wrapper-verdict` line is therefore also S3's **pre-image**: it says whether the radio arrives held
in reset (in which case S3's job is the standard `bcma_core_enable` sequence) or already enabled (in
which case S3 has a different question to answer before it writes anything).

**Writes:** the d11 core's **wrapper** registers — `IOCTL`/`RESETCTL` (`bcma_core_enable` /
`bcma_core_disable` in Linux): assert reset, set the clock-enable and FGC bits, deassert reset,
clear FGC. Also the PMU/PLL setup ChipCommon owns for this chip.

**Proves it took:** the d11 core's own registers stop reading `0xFFFFFFFF` and start returning
sensible values — specifically `d11 + 0x3E0` (`B43_MMIO_PHY_VER`) decodes to
`analog=<n> type=7 (HT) rev=<n>`. **PHY type 7 = HT-PHY is the expected reading for BCM4331.**

**Falsifiable predicate:** `phy_type == 7`. Anything else means the part is not what the census
said. `type=4` (N-PHY) would mean a BCM4322-class part; `type=11` (AC) an 11ac card
(`43a0`/`43ba` — a MacBookPro11,x part or an after-market upgrade). Either would redirect the whole
project, and this is the cheapest stage that can tell us.

**Failure on serial:** the core window still all-ones after reset deassert (reset did not take, or
the wrapper address is wrong — which points back at S1), or a `PHY_VER` of `0x0000`.

**Not all-or-nothing.** This stage has a clean binary verdict and a cheap unwind (re-assert reset).

### S4 — Firmware (microcode) upload

**Depends on:** S3.

**Writes:** the d11 core's shared memory and the microcode upload window — tens of KB of ucode plus
initvals plus PCM data, written through the SHM autoincrement path, then the MAC brought out of
suspend to run it.

**Proves it took:** the ucode revision handshake. After upload and start, the ucode publishes its
revision + patch level in shared memory; the driver reads it back and it must equal what the blob's
header claims. That is a genuine end-to-end proof that the CPU inside the radio is executing our
bytes.

**Falsifiable predicate:** `ucode_rev` read from SHM == the revision the blob declares, and the MAC
control register shows the ucode running rather than suspended.

**Failure on serial:** revision reads `0` or `0xFFFF` (ucode not running), or a mismatch (wrong blob
for this core revision — the ucode is core-revision specific).

**Partly all-or-nothing:** the *mechanism* (SHM writes, upload window) is incrementally verifiable
by reading back what was written. The *handshake* is binary.

> #### ⚠ DECISION POINT FOR PETER — the firmware blob is not redistributable
>
> This stage cannot be completed with free software, and that is a licensing decision, not an
> engineering one.
>
> * **The BCM4331 microcode is proprietary.** On Linux it is not shipped; it is *extracted* from
>   Broadcom's own binary driver at install time with `b43-fwcutter`. There is no Broadcom-granted
>   redistribution licence.
> * **OpenFWWF, the free replacement, does not cover this part.** It targets the old LP/G-PHY cores
>   only. There is no free microcode for an HT-PHY 4331.
> * **UnaOS is GPLv3.** A non-free blob may not be linked into the kernel image. The workable shape
>   is a runtime load from media — the blob sits on the ESP as a file, the driver reads it through
>   the FAT reader we already have, and the kernel binary itself remains free. The blob must never
>   be committed to this repository and must never be baked into a media image we distribute.
>
> **The three options, stated plainly:**
>
> 1. **Runtime load from the ESP, blob never in the repo.** The user extracts it themselves from
>    Broadcom's driver, exactly as Linux users do. Legally the same posture Debian's `non-free`
>    takes. This is the only option that both works and keeps the tree clean.
> 2. **Abandon path A at S4** and take the AR9271 USB route, whose firmware
>    (open-ath9k-htc-firmware) is genuinely free. S5's reverse-engineered PHY problem disappears
>    with it; S7/S8 remain.
> 3. **Write free microcode.** Not realistic. OpenFWWF took years for a far simpler PHY.
>
> **Nothing in S4 or below should be written until Peter has picked one.** S0–S3 are unaffected by
> the choice and are worth doing regardless: they are read-mostly, cheap, and they tell us whether
> the part is even the one we think it is.

### S5 — PHY and radio initialisation — **the crux**

**Depends on:** S2 (calibration) and S4 (ucode).

**Writes:** thousands of PHY and radio registers, from tables. HT-PHY init tables, 2059 radio init
tables, RF calibration loops, TX power control, per-band retune.

**Proves it took:** nothing short of S6's first received frame. That is the problem.

**This stage is ALL-OR-NOTHING and it is where the project stalls or dies.** Three reasons, and they
compound:

1. **The tables are undocumented.** Every value is reverse-engineered from Broadcom's binary driver
   by the bcm-specs/b43 project. They cannot be derived, checked, or reasoned about — only
   transcribed.
2. **A wrong table gives silence, not a diagnostic.** There is no intermediate register that says
   "the PHY is 80% up". This is the opposite of every other stage in this ladder.
3. **b43's HT-PHY support is the least complete PHY in that driver.** BCM4331 has spent most of its
   Linux life marked experimental/partial. We would be transcribing the weakest target of the
   weakest part of the reference implementation.

**The only honest sub-division available** is to split by band and by function: (a) radio powered and
its ID register reading the expected 2059 id; (b) PHY reset sequence completing without the MAC
hanging; (c) channel tune to one 2.4 GHz channel; (d) RX chain enabled. (a) and (b) have read-back
predicates. (c) and (d) do not, until S6.

**Falsifiable predicate available before S6:** the radio ID register must read the 2059's id. That
is the one cheap check in this stage and it should be the first thing written.

**Stop rule:** **if S6 cannot receive a single beacon, stop the project.** Everything after S6 is
unreachable, and continuing to write S7 against a dead PHY is how months disappear.

---

### S6 — DMA rings and monitor-mode RX

**Depends on:** S5.

**Writes:** the 64-bit DMA engine's ring base/index registers, RX descriptor rings, RX filter and
MAC control for promiscuous/monitor operation.

**Proves it took:** **one decoded beacon frame with a real SSID printed on serial.** Not a
descriptor advancing, not an interrupt firing — a beacon whose SSID matches a network we know is in
the room. That is the project's single most important line and everything above it is scaffolding
for it.

**Falsifiable predicate:** the SSID string in the decoded beacon equals a network Peter can name,
and the frame's RSSI and channel are plausible. A garbage SSID means the PHY RX header decode is
wrong, which is S5 feedback, not S6 feedback — and distinguishing those two is why the raw RX header
bytes must be printed alongside the decode.

**Failure on serial:** descriptors never advance (DMA not running / rings mis-programmed — an S6
bug); descriptors advance but every frame fails FCS (PHY not tuned — an S5 bug). Those two lines are
the whole diagnostic value of this stage, so both must be counted separately.

**Not all-or-nothing** — but it is the **stop gate**. See S5.

---

### S7 — MAC / station layer

**Depends on:** S6.

**Writes:** TX DMA rings, SHM frame templates (probe request, auth, assoc), MAC control, rate
tables.

**Proves it took:** an association state reached against an **open** network — beacon seen, probe
request sent, probe response received, auth exchange completed, assoc response with a status of
success and an AID assigned.

**Falsifiable predicate:** the AP's own client list shows us. A driver that believes it associated
while the AP has never heard of it is the failure mode to design against, so the predicate must be
external to us.

**Failure on serial:** probe requests sent but no response (TX not reaching the air — check TX power
and the PHY TX chain, i.e. S5 again); response received but auth times out (frame templates or
sequence numbers wrong).

**Not all-or-nothing.** Each of scan / probe / auth / assoc has its own observable.

---

### S8 — WPA2-PSK

**Depends on:** S7.

**Writes:** nothing new in hardware terms beyond the CCMP key slots (or software CCMP).

**Needs:** PBKDF2-SHA1 (key derivation), HMAC-SHA1 (the EAPOL MIC), AES-CCMP. **This tree has no
crypto library.** That is its own sub-arc and should be sized separately; it is arch-neutral, host-
testable, and — unlike everything from S4 down — it can be developed and unit-tested with zero
hardware.

**Proves it took:** a DHCP lease over the radio. `smolnet` (smoltcp 0.13.1, DHCPv4, the default x86
net stack since 2026-07-17) does the rest unchanged the instant frames flow: ARP, IPv4, ICMP, UDP,
TCP, DNS, SNTP are all already proven.

**Falsifiable predicate:** `ping` from the UnaOS shell to the gateway, over WiFi, answered.

## 3. What this OS already has, and what it does not

**Has:** the entire stack from Layer 2 upward. `drivers/e1000.rs` (~1,300 lines) is a working DMA
ring driver with MSI delivery; `smolnet` carries the shell's `ping`/`arp`/`netinfo`, the socket
syscalls, DNS and SNTP. Hand this OS a device that produces and consumes Ethernet-shaped frames and
everything above the wire works today.

**Does not have:** anything at all below that line for radio. smoltcp has no 802.11 notion — no
scanning, no association, no WPA, no 802.11 headers, no rate control. The e1000 is a wired MAC whose
link is simply up or down and it shares essentially nothing with a SoftMAC radio beyond "DMA rings
exist".

**So: 100% of S3–S8 is work we have never done, and 0% of it is work we have.** The existing stack
does not shorten the driver; it means that *if* the radio ever delivers a frame, everything after
that already works. That is worth a great deal — but it is worth it only at S6 and later.

## 4. Knob wiring

| Place | Entry |
|---|---|
| `unaos/crates/kernel/Cargo.toml` | `bcmarecon = []` |
| `unaos/crates/kernel/src/drivers/mod.rs` | `#[cfg(all(target_arch = "x86_64", feature = "bcmarecon"))] pub mod bcma;` |
| `unaos/crates/kernel/src/arch/x86_64/pci.rs` | call site, after `full_census()`, before the GPACE anchor |
| `unaos/arroyo` (feature mapping) | `UNAOS_BCMARECON=1` → `bcmarecon` |
| `unaos/arroyo` (`arm_features`) | stripped for aarch64 — x86-only code, so leaving it enabled would shift aarch64 media hashes for zero observable change (the `sdw`/`kbdwit`/`pcicensus` argument) |
| `unaos/arroyo` (`KERNEL_CFG_MATRIX`) | appended to the `x86-all` leg; the `x86-mix-*` legs derive from that union, so the pairwise mix enrolled it automatically |
| `unaos/builder/src/main.rs` | `UNAOS_BCMARECON` → `bcmarecon` |

The builder wiring is not optional. The builder rebuilds the x86 kernel from its **own** env-derived
feature list, so a knob wired only in `arroyo` ships the feature disabled while the banner claims it
is on (s42/INSTGUI, WXN-M3b). This arc is as exposed to that bug as the census was and in the same
direction: **a recon that silently did not run is indistinguishable on the wire from a machine with
no radio in it** — and that is precisely the conclusion the path-A decision would then rest on.

Each later stage gets its own knob (`UNAOS_BCMA_S1`, …) rather than escalating `bcmarecon`, so that
"the read-only recon" and "the stage that writes the backplane window" can never be armed by the
same variable.

## 5. Risks, ranked

1. **S5 (HT-PHY) never comes up.** Highest-probability project-ending outcome. Mitigation: none
   available; the mitigation is the S6 stop rule.
2. **The firmware licensing decision is deferred rather than made**, and S4 gets written against an
   assumption. Mitigation: §S4's decision box, answered before S4 starts.
3. **The part is not a BCM4331.** Cheap to refute — S0 says so on the first boot, and S3's
   `phy_type` says so again by a different route.
4. **A backplane write wedges the bus.** S1 writes one config register and restores it; S3 is the
   first stage that resets silicon, and it is the first stage that needs an unwind path.
5. **The SPROM/OTP calibration is unreadable** (the 4331 PA-line mux). Refutable at S2 and it has a
   documented workaround; it is a delay, not a wall.
