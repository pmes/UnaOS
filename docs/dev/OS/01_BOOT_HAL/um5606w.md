Created 2026-10-27 by ZENBOOKSURVEY (zenbook-ledger Z1). Queue: `docs/dev/OS/zenbook-queue.md`. Code read at `281b09c3e`.

## 3. The boot path

UEFI (Secure Boot OFF) → `EFI/BOOT/BOOTX64.EFI` (`unaos/crates/bootloader`, the same loader as the rMBP; no Apple EFI
quirk is load-bearing: the loader's one Mac-only step is the `unaos_ivb` entry trace, ZENBOOK-LOADERTRACE) → the GOP
framebuffer → the config-table reads (ACPI RSDP, and since Z1 the SMBIOS entry point: SMBIOS 3.0 first, 2.x fallback,
`[loader]`-side line `SMBIOS ep at 0x… (smbios3)`) → `exit_boot_services` → `kernel_main` with `BootInfo` (identity map,
`physical_memory_offset` 0) → BPACE rungs → `arch::acpi::init` (MADT: 24 logical CPUs) → `arch::pci::init`, whose FIRST
act is `hw::platform_say()`: `[hw] platform=zenbook_um5606w dmi="<product>" vendor="ASUSTeK COMPUTER INC." src=smbios3`.

## 4. The glass: GOP on the external monitor

The rule today: the loader takes the GOP mode the firmware lit (bootloader_spec.md); the rule ZENBOOK-GOP builds: the
loader picks the native mode of the CONNECTED output. Two cases the plan names, both unmeasured:
- the firmware still enumerates the dead internal eDP panel (its EDID answers, the panel shows nothing): GOP may light
  the internal panel's 2880x1800 and leave the external monitor dark, or mirror. The operator's fallback: the firmware's
  own display setting, or the lid closed; ZENBOOK-GOP picks the output by EDID presence + hot-plug, not by index.
- the firmware does not enumerate the internal panel: GOP lights the external monitor at its preferred mode, as on QEMU.
The kernel draws only the GOP framebuffer until ZENBOOK-RADEON; no mode set happens after `exit_boot_services`.

## 6. The first-boot recipe (ZENBOOK-FIRSTBOOT, the bench's)

1. Build: `cd unaos && ./arroyo esp-x86` with the ZENBOOK-IMAGELINE knobs; write the card image to a USB stick.
2. External monitor on the USB-C (DP alt mode) or HDMI port; the FTDI FT232 serial adapter (0403:6001) on a USB port;
   the stick on another.
3. Power on, F2 (or Esc) into the firmware: Secure Boot OFF; boot the stick.
4. Expected, in order (unmeasured): the loader's `CON cur=` and `ACPI RSDP at`, `SMBIOS ep at 0x… (smbios3)`,
   `[loader] kelf slot=A hash=ok`, `KELF min= max=`; on the glass `:: SPLASH: stage=gop`; then
   `[hw] platform=zenbook_um5606w dmi="…UM5606…" vendor="ASUSTeK COMPUTER INC." src=smbios3`,
   `:: x86_64 PCI Init: Found xHCI at 0x… ::` (the serial door opens here if the FTDI is on that controller), the
   `[hw] skip …` lines for each gated probe the image carries, `[hda] absent` when the service pass reaches HDA, and the
   root stage waiting for a volume (no NVMe driver yet).
5. Serial: everything before the xHCI is up exists only on the glass (and in the bootlog ring); photograph it.

## 7. The serial door

The bench's door on the rMBP is the kernel driving an FTDI FT232 (0403:6001) as USB HOST over xHCI
(`drivers/xhci/ftdi.rs`: TX, plus FTDIRX's receive); there is no CDC-ACM serial driver. The Zenbook has xHCI only, so the
door is FEASIBLE as built — on the condition that the adapter sits on a port of the ONE xHCI the kernel brings up (the
first class 0C/03/30 function in walk order, `unaos/crates/kernel/src/arch/x86_64/pci.rs:895`), which of the four Strix
controllers that is, and which physical ports it serves, is unmeasured (ZENBOOK-XHCIPICK). The xHCI bring-up has no
Intel-only step besides PORTSW, which is inert on AMD.

## 8. Risks

| risk | what happens | mitigation |
|---|---|---|
| the FTDI is on a controller the kernel does not bring up | no serial after the loader | try each port; ZENBOOK-XHCIPICK |
| GOP lights the dead internal panel | dark external monitor | firmware display setting / lid closed; ZENBOOK-GOP |
| AMD xHCI quirks the Intel-tested driver never met | enumeration stalls | the wire's bounded waits name the step; a row per finding |
| no root volume (NVMe only) | stage-resolve waits, no desktop from disk | ZENBOOK-NVME; boot from the stick's FAT meanwhile |
| no keyboard (8042) / touchpad (I2C-HID) | no input except a USB keyboard | a USB keyboard on the walked xHCI; ZENBOOK-I8042, -TOUCHPAD |
| the loader's IVB trace on an image carrying UNAOS_IVB | port I/O at 0x7D0/0x7D4 and a config-space BAR read at 0:2.0 on AMD, before the kernel | the Zenbook line carries no IVB; ZENBOOK-LOADERTRACE |
| an SMBIOS product without `UM5606` (a firmware string we have not seen) | `platform=unknown`; the ASUS vendor still makes `gate` skip the Apple probes | the first boot's `[hw] platform` line settles the string |
| Secure Boot left on | the firmware refuses the unsigned loader | step 3 of §6 |
