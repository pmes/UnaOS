## Threat framing

UnaOS is being built to hold *direct authority over physical hardware*:
G-code streams to a 3-D printer, PWM to a vehicle's throttle, GPIO, SDR. A
compromise is not just data loss — it has physical consequences. Security is
therefore foundation work, not a retrofit (BeOS deferred multi-user and paid
for it; we won't repeat that).

Exposure classes, honestly stated:

1. **Ring-0-resident parsers.** The network stack (Ethernet/ARP/IP/TCP/DHCP),
   USB descriptor parsing, and the FAT reader all parse attacker-influenceable
   bytes with full kernel privilege on both architectures. Until the privilege
   boundary exists everywhere, these are the practical attack surface, and
   they remain kernel-resident even after.
2. **Privilege boundary not yet load-bearing (both arches).** The ring-3/EL0
   boundary now exists on BOTH architectures (x86 U1a/U1b: ring-3 round-trip +
   per-page perms + fault→task-kill; aarch64 M6a/M6b, the pioneer). x86 U2 runs
   the FIRST real program loaded FROM DISK in it (a flat ring-3 binary read off
   the FAT volume) — **metal-confirmed on the real 2012 rMBP (2026-07-03): a
   Realtek USB3 SD reader → FAT16 card → `HELLO.BIN` (72 B) read + executed in
   ring 3 (`hello from disk` -> PASS)**. But that program is still trusted only by
   ring-3 isolation (no signature/allowlist check yet — U2's untrusted-loader note
   below), and the kernel's own subsystems (drivers, FS, net) remain ring-0.
3. **No identity or authorization layer yet** — no principals, no grants;
   any code that runs can do anything. This is what the U-chain builds.

## The model: capabilities first, POSIX-layerable

Decision (2026-07-02): UnaOS targets a **single primary human with
capability-isolated software principals**, not classical login/uid multi-user.

- Every vessel, handler, and agent is a **principal** with an explicit grant
  set (e.g. Comscan: `serial:acm0`, `gpio:*`; Vug: `fs:/models rw`; an
  untrusted download: nothing).
- **Handles are capabilities.** The per-process handle table is the enforcement
  point: every syscall that touches a resource goes through it. Grant, attenuate,
  revoke are first-class operations; handle transfer over the bandy bus is
  unforgeable. *(Status: arc **U4** built the table STRUCTURE — child-process
  handles, keyed by ASID, with reaping owner-scoped by construction — on aarch64;
  the enforcement CHECK — routing resource syscalls through it, plus
  grant/attenuate/revoke — is **U5**, which adds its check at the same handle
  lookup U4 built. See the aarch64 ledger below.)*
- **UnaFS stores the metadata natively**: `owner` and `grants:*` are ordinary
  typed attributes — queryable ("show every file the midi-agent can write"),
  and no on-disk format change is ever needed.
- **POSIX hedge**: if human multi-user is ever wanted, a "user" becomes a
  named bundle of capabilities layered on the same attributes. Nothing in the
  chain below has to be redone.

Implementation chain: **U1a → U1b → U2 → U3 → U4 → U5 → U6** (x86 leads, Pi
ports, Jetson joins — full table in `ROADMAP.md` §1).

## Hardening ledger

### x86_64
- [x] Ring-3 boundary: user GDT segments (DPL-3 code/data, SYSRET-compatible STAR), `TSS.RSP0`, SYSCALL/SYSRET path (`EFER.SCE`, `LSTAR`, `STAR`, `FMASK`) (U1a, 2026-07-02, **QEMU-verified; metal pending**)
- [x] EFER.NXE enabled; NX on all user data/stack pages; user **code page W^X enforced across cores** — mapped ring3-RX **read-only from the start** at `USER_BASE` (the blob is copied through the identity alias, never through `USER_BASE`), so no core can ever cache a writable mapping of it; supersedes the U1a single-core `invlpg` flip (U1a/**U1b B4**, 2026-07-02, **QEMU-verified + metal-confirmed** on the real 2012 rMBP: `u1b-code-write` faulted with `err=0x7` (Write bit set) on the real page tables)
- [x] User fault → task kill, never kernel halt — a ring-3 fault (`CS.RPL == 3`) on #PF/#GP/#UD/#SS/#NP/#DE/#BR/#AC `swapgs`es, logs `(task, vector, cr2)`, and kills the task via `sched::exit()`; a CPL-0 fault stays fatal (kernel bug never hidden). (**U1b A**, 2026-07-02, **QEMU-verified + metal-confirmed** on the real 2012 rMBP: 3 kills at `vec=14 err=0x7/0x7/0x15`, `exited=1 killed=3 -> PASS`, **kernel continued past all three kills** — proving `swapgs`/GS restore work on silicon)
- [x] SYSRET boundary hardening: caller-saved GPR scrub (`rdi/rsi/rdx/r8/r9/r10` zeroed before `sysretq` — no kernel-dispatcher pointer leaks to ring 3) + canonical-`rcx` guard (a non-canonical return RIP — the CVE-2012-0217 shape — is refused and the task killed, never `sysret`ed with the user rsp loaded) (**U1b B1/B2**, 2026-07-02, **QEMU-verified + metal-confirmed for the pass-through** — the ring-3 round-trip returns cleanly through the scrub+guard tail on real silicon. The guard's *refusal* logic is now **logic-tested** (U2 Part-0c, 2026-07-02: the callable twin `rcx_canonical` refuses `0x8000_0000_0000_0000`, QEMU-verified — `:: U2-0c: canonical-rcx guard refuses … -> PASS ::`); the end-to-end refusal — ring-3 code actually returning to a non-canonical RIP, which is unreachable from our 1 TiB window — is still future)
- [x] NMI on a dedicated IST stack — an NMI landing in the pre-`swapgs`/pre-stack-switch window of `unaos_syscall_entry` switches to a kernel stack unconditionally, so its frame can never be pushed onto the ring-3 stack; the handler stays GS-free (**U1b B3** + **U2 Part-0c**, 2026-07-02, **QEMU-verified, fire path now exercised**: a real self-NMI — `apic::send_ipi(<own apic id>, 0x4400)`, level-assert | NMI delivery mode — is confirmed **taken on the NMI IST stack** (the handler compares its RSP against the IST bounds): `:: U2-0c: self-NMI taken on IST -> PASS ::`. This positively demonstrates the unconditional IST switch, upgrading the earlier "slot installed" claim. Still future: metal re-confirmation of the self-NMI, and a fixture that lands the NMI *specifically* mid-syscall-entry — the IST switch is CPL-independent, so the self-NMI is representative, but the exact window has not been targeted)
- [x] CR4.SMEP set — code gates it on `CPUID.7:EBX.SMEP` and sets it when present; **metal-confirmed active on the real 2012 rMBP** (`:: SMEP on ::` photographed 2026-07-02 — TCG `qemu64` does **not** expose SMEP, logging `SMEP unsupported`, so this is the one line QEMU cannot show). A SMEP-*violation* functional test (supervisor fetch from a ring-3 page → #PF) is still future. **SMAP unavailable pre-Broadwell** — compensate with explicit `copy_from_user` discipline
- [x] #DB (vector 1) + #MC (vector 18) each on a dedicated IST stack (**U2 Part-0a**, 2026-07-02). #DB closes a user-triggerable DoS: `RFLAGS.TF` is writable at any CPL (`popfq`), so ring 3 can arm single-step then `SYSCALL`; the pending trap lands on the first `LSTAR` instruction at CPL 0 with GS/RSP still ring-3, and with #DB absent from the IDT that escalated to a same-CPL #NP whose frame landed on the user-writable stack → misread as a kernel fault → halt. The GS-free #DB handler kills a ring-3 #DB, and for a CPL-0 #DB whose RIP is inside the `unaos_syscall_entry` stub clears TF and `iretq`s (resumes the syscall); any other CPL-0 #DB is fatal. #MC is fatal on its own IST. **QEMU-verified**: installed + boot-verified, `:: U2-0a: TF+SYSCALL survived -> PASS ::` (kernel not halted). **Fire path of the #DB *resume* branch is metal-only** — QEMU TCG does not model the TF-on-`SYSCALL` trap (`db_resumed=0`; the fixture exits cleanly instead), so the resume itself is exercised only on real silicon; the #MC fire path is untested (no machine-check fixture). **DR7 is now cleared per-CPU at syscall init (U2.5 Part 0-ii, 2026-07-03, QEMU-verified)** — `mov dr7, 0` beside the SMEP write, logged once as `:: U2.5-0: DR7 cleared ::` — so a firmware-left hardware breakpoint can no longer raise a #DB inside the entry stub: the resume policy's "TF is the only #DB source there" assumption is now *enforced*, not merely assumed
- [x] First-entry GPR scrub (`user_task_trampoline`) — every GPR but `rsp` is zeroed after the five `iretq`-frame words are pushed and before `iretq`, so no live kernel value (the Task Box pointer, kernel-stack top, entry VA) reaches ring 3 in a register at first entry. The x86 twin of the aarch64 M6d first-`eret` scrub; complements the U1b SYSRET scrub, which covered only the return half (**U2 Part-0b**, 2026-07-02, **QEMU-verified**: U1a/U1b/U2 ring-3 entry all still function — the scrub does not disturb the entry ABI, which takes no register arguments)
- [ ] W^X audit of kernel mappings (no page both writable and executable) — note: `CR0.WP` is briefly cleared around the U1a/U1b/U2 page-table edits (firmware maps its tables read-only) and restored; scope is the mapper only. (The U2 loader writes the loaded program through the code frame's identity alias, NOT through `USER_BASE`, and needs no `CR0.WP` toggle — the frame is ordinary RW heap; the ring-3 mapping stays read-only, so W^X across cores holds by construction.)
- [ ] Validated user-pointer access (`copy_from_user`/`copy_to_user`)
- [x] **Per-process address spaces (U3, 2026-07-04, QEMU-verified; metal-pending) — the x86 mirror of aarch64 M6d.** Each user process now runs in its OWN top-level page table (its own CR3): a static 8-slot pool (`memory.rs` `SLOT_PML4/PDPT/PD/PT` + backing + `SLOT_USED`), each slot SHARING the kernel half — `build_slot` copies every live kernel PML4 entry EXCEPT PML4[2], so the kernel mappings (identity map incl. high MMIO like the xHCI BAR at 768 GiB, heap, kernel code/stacks, IST/percpu/GDT) are shared by pointing at the SAME kernel next-level tables — while owning a PRIVATE PML4[2] user window at `USER_BASE`. `user_task_trampoline` installs the task's CR3 (`Task.user_cr3`) before the `iretq`; `exit` restores the kernel CR3 then frees the slot. Two processes can map the same VA to different frames. **Evidence:** a deterministic kernel isolation probe (two slots, same VA, distinct sentinels, swap CR3 and read — `:: U3: per-process CR3 isolation … distinct -> PASS ::`) plus two ring-3 tasks each in their OWN CR3 each reading their slot-private sentinel (`:: U3: 2 ring-3 tasks each in a private CR3 read their own sentinel … -> PASS ::`); U1a/U1b/U2/U2.5 byte-identical (the `user_cr3 == 0` shared-window path is untouched). **Scope is honest:** plain `mov cr3` (full non-global-TLB flush) — **no PCID** (the x86 analogue of M6d's ASID) yet; a **static 8-slot pool** (hard cap = STOP tripwire) — no dynamic user-memory allocator yet; **per-slot table freeze** (a kernel PML4-*entry* added post-boot would need mirroring into live slots — the kernel never adds one; edits BELOW the PML4 propagate via the shared tables); ring 3 still **cooperative** (the CR3 switch lives in the trampoline/`exit`, not a preemptive dispatch path — that moves when preemptible ring 3 lands). The probe's supervisor read of a user page relies on **no SMAP** (correct on the Ivy Bridge target; a SMAP-capable port must use an AC-toggle or validated copy). **Metal-pending** (rides the next reflash / FTDI cable day).
- [ ] **Preemptible ring 3 (x86 twin of aarch64 M6e) — not yet.** Ring-3 code currently runs with the timer unable to evict it on its AP, so a program that never syscalls (`jmp $`) wedges that core forever — a one-core DoS from any loaded program. Contained today only by the one-shot loader (one program per boot); becomes urgent the moment programs are spawned freely. (Surfaced by the U2 integrator review, 2026-07-02.)
- [x] **Ring-3 FP/SIMD hygiene (x86) — first-entry scrub (U2.5 Part 0-i, 2026-07-03, QEMU-verified; metal-pending FTDI cable day).** `user_task_trampoline` now runs `FNINIT` then eight `FLDZ` + eight `FSTP ST(0)` before the GPR scrub, so all eight *physical* x87/MMX registers hold 0.0 at first ring-3 entry — `FNINIT` alone only empties the tags, and an MMX move reads the aliased mantissa bits regardless of tag, hence the `FLDZ`/`FSTP` pass. The x86 twin of the aarch64 M6f FP/SIMD scrub. **Scope is honest — first entry only:** there is still NO FXSAVE/FXRSTOR context switching, so cross-*task* FP residue once multiple programs share an AP is NOT yet covered (rides the x86 context-switch work), and there is no negative residue-read fixture — this is exercised transitively (U1a/U1b/U2 still enter ring 3 and pass). The x87 mnemonics assembled cleanly under the `+soft-float` kernel target, so no `FNINIT`-only fallback (and no MMX-alias residue caveat) was needed. SSE stays contained separately by `OSFXSR=0` (#UD → kill), untouched. (First step surfaced by the U2 integrator review, 2026-07-02.)
- [ ] Self-vs-non-self loader check for U2-loaded programs — **not yet.** The U2 FAT loader treats `HELLO.BIN` as UNTRUSTED INPUT: it is bounded only by size (must fit one 4 KiB ring-3 code page; oversize/missing → clean skip, no panic) and is contained solely by ring-3 + NX + W^X + SMEP + the U1b fault-kill net (a malformed program cannot corrupt kernel state or escalate privilege — though it *can* still spin forever and wedge its AP; see the preemptible-ring-3 ledger item below). The loader now **zeros the ENTIRE ring-3 window** (all four pages — code + data + two stack) through each page's identity alias before copying the program in (U2.5 Part 0-iii, 2026-07-03), not just the code page, so a second loaded program cannot read the previous program's / the U1a/U1b fixtures' residue from the data or stack pages; the writes go through the identity aliases, never `USER_BASE`, so the code mapping stays read-only (W^X across cores holds). No signature or allowlist gate exists yet — that is the U-chain's code-signing item (design: `dev/OS/04_SECURITY_IMMUNITY/intrusion_detection.md`), the first consumer of which is exactly this loader. **The aarch64 M6g loader (2026-07-03) is the exact twin of this posture** (size-bounded only, contained by EL0 + per-page perms + the M6b fault-kill net — see the aarch64 ledger below); the code-signing gate, when it lands, must cover BOTH loaders

- [x] EL0/EL1 privilege split (M6a-0/M6a, 2026-07-01, metal-confirmed)
- [x] Per-page user permissions: user code EL0-RX, stacks RW-XN; UXN/PXN on user pages (M6b)
- [x] EL0 fault → task kill with syndrome-matched accounting (M6b)
- [x] Preemptible EL0 — SP_EL0 banked in the IRQ frame; `spawn_user` starts I-unmasked (M6e, 2026-07-02, QEMU-verified + **metal-confirmed** real Pi 4: `IRQs-taken-at-EL0=18`, spinner resumed correctly, no faults). W^X map **unchanged**: the shared user stack is retained (no EL0 program writes its stack), so no new user page and no permission change — the audit table below still holds.
- [x] Kernel W^X / WXN audit (SCTLR_EL1.WXN feasibility) — audit complete; WXN enable pending review (M6c/H1; table below)
- [ ] PAN (Privileged Access Never) where silicon supports it
- [x] Validated user-pointer access — `copy_from_user`/`copy_to_user` (M6f, 2026-07-02, QEMU-verified; ★ metal-confirmed real Pi 4 2026-07-04 on the M6g reflash) — every user pointer crossing the syscall boundary is range-checked before any deref: `copy_from_user` requires `[va, va+len)` fully inside the caller's EL0 window with a non-wrapping length (`checked_add`); `copy_to_user` additionally excludes the read-only code page from its writable range, so a write aimed there is refused with `-EFAULT` **before** the store (never the faulting EL1 write a code-page target would otherwise take). SYS_WRITE now streams through `copy_from_user` (validate-whole-range-then-chunk, so a bad pointer produces `-EFAULT` with no partial output). A bad pointer is an **error return, not a task-kill** (kills stay for hardware-raised faults). Evidence: the M6f hostile fixture issues four bad pointers — `sys_write`(kernel RAM VA), `sys_write`(unmapped window-adjacent VA), `sys_write`(wrapping length), `sys_getinfo`(RO code-page target) — and the kernel refused all four with `-EFAULT` and **0 kills, 0 kernel halts** (`:: M6f: 4 hostile pointers refused (EFAULT), 0 kills -> PASS ::`), while the well-behaved `sys_getinfo` round-trip (`copy_to_user` then EL0 read-back matching `SYS_GETPID`) passed. Scope is honest: A72 is Armv8.0 with **no FEAT_PAN**, so this is pure software validation — the direct EL1 access is sound only because a syscall executes with the caller's TTBR0/ASID live (M6d), so an in-window VA can reach only that task's frames; a PAN-capable port (Jetson A78) must switch to an unprivileged (LDTR) or validated-copy path. **Metal-confirmed (real Pi 4, 2026-07-04):** all four hostile pointers refused with 0 kills / 0 kernel halts and the getinfo `copy_to_user` round-trip passed on silicon (`:: M6f: 4 hostile pointers refused (EFAULT), 0 kills -> PASS ::`, `getinfo/copy_to_user round-trip -> PASS`).
- [x] Per-task address-space isolation via ASIDs (M6d, 2026-07-02, QEMU-verified + **★ metal-confirmed** real Pi 4) — each EL0 task runs in its own translation-table branch with its own 16 KiB backing mapped at the same VAs; user-window leaves are non-global (`nG=1`, ASID-tagged 1..8), kernel leaves stay Global; `TTBR0_EL1` is switched (root + ASID) on dispatch and the slot is broadcast-`TLBI ASIDE1IS`'d and repointed off at exit. A task can no longer see or corrupt another task's user memory at a shared VA. **Metal proof (2026-07-02, EL=1/54 MHz — the class of thing QEMU cannot test):** `same-VA isolation A=0xa5a5…1 B=0x5a5a…2 distinct -> PASS` on real A72 TLB/caches (backed by a deterministic kernel-side TTBR0-swap `nG` probe), EL0 stack write/readback + SP-sentinel `-> PASS`, and with EL0 preemption live in the same boot (aggregate `IRQs-taken-at-EL0=21`, QEMU=0 — a demo-wide counter with no per-task attribution) all four slot tasks reported correct sentinel/stack values across interleaved per-task `TTBR0`/ASID dispatches; M6b `exited=1 killed=3 -> PASS` unchanged, 0 unexpected faults.
- [x] EL0 first-entry GPR scrub (M6d, 2026-07-02) — `user_task_trampoline` zeroes x0–x30 before the first `eret` to EL0, so no live kernel value (the raw `Task` pointer, kernel x29/x30, ...) reaches EL0 **in the general-purpose file** at entry. The FP/SIMD file is NOT yet covered (next item). The aarch64 twin of the x86 SYSRET GPR scrub (merged with U1b).
- [x] Loadable program from storage — the untrusted-loader path (M6g, 2026-07-03, QEMU-verified; ★ metal-confirmed real Pi 4 2026-07-04) — the block layer dispatches over a registered backend so a read-only BCM2711 EMMC2/SDHCI microSD driver (PIO, single-block CMD17, polled, no writes; every wait CNTPCT-bounded) sits beside the untouched xHCI path (x86 read/write byte-identical — the seam is cfg-gated to `aarch64+baremetal`). The M6g loader reads `HELLO.BIN` off the card's FAT volume, **rejects it up-front from the on-disk directory size** if it does not fit one 4 KiB code page (the U2 truncation lesson: `read_file` caps at `min(size, cap)`, so a post-read check could never SEE an oversize file), copies it into a fresh M6d per-task slot, and protects the page EL0-RX/EL1-RO **before the task exists** (so the untrusted bytes are never writable-and-executable). **The loaded bytes are UNTRUSTED and bounded ONLY by size** — contained by EL0 + per-page perms + the M6b fault-kill net, exactly the x86 U2 posture; there is **no signature or allowlist gate yet** (see the shared code-signing item below). Same residual DoS as U2/x86: a program that never `svc`s can spin its EL0 core (M6e makes EL0 preemptible on metal, so the timer *can* evict it there; QEMU delivers no timer IRQ). QEMU proves the seam, the whole SDHCI ladder against the legacy base, FAT mount off SD, and the EL0 load + run + name-routed exit accounting; the EMMC2 base actually carrying the card is metal-only — and it **ran on silicon (2026-07-04):** no fallback line, `SD card @0xfe340000 identified — 31116288 blocks (15193 MiB, CSD v2)` (a real ~16 GB SDHC card, block-addressed — vs QEMU's 64 MiB/CSD v1 legacy fallback), then FAT mount + `HELLO.BIN loaded from SD (51 bytes) -> EL0` + `disk-loaded EL0 program exited ok -> PASS`, with 0 unexpected faults.
- [x] Minimal process model — `sys_spawn` + `sys_wait` (M7, 2026-07-04, QEMU-verified; ★ metal-confirmed real Pi 4 2026-07-04) — an EL0 program can spawn a child program (`SYS_SPAWN = 8` loads the fixed on-disk `HELLO.BIN` into a fresh per-task slot and runs it at EL0, returning its pid) and reap it (`SYS_WAIT = 9` blocks on a per-child counting `Semaphore` the child posts once — on its normal exit **or** on a fault-kill, so a killed child can never hang its parent). **The security scope is deliberately narrow and stated honestly: there is NO capability or permission check on spawn yet** — any EL0 program that reaches `SYS_SPAWN` gets a child. What contains the child is the SAME chain as every prior EL0 program, nothing weaker: it runs on its own fresh slot (own ASID, per-page EL0-RX/EL1-RO code protected *before the task exists*), **inherits nothing** from the parent (no shared memory, no shared handles — there is no handle table yet), and is bounded by EL0 + per-page perms + the M6b fault-kill net. The child bytes are the same size-bounded **untrusted** on-disk program as M6g (no signature/allowlist — the shared code-signing item below gates BOTH the child load and the M6g loader). Resource bounds are fixed, not grown under load: a 4-entry process table and the 8-slot pool both return `-EAGAIN`/`-errno` on exhaustion rather than expanding. Residual DoS is unchanged from M6g/U2 — a child that never `svc`s can spin its EL0 core (the timer evicts it on metal, M6e; QEMU delivers none). **`sys_spawn` takes no name/path argument** — the program is fixed to `HELLO.BIN`; arbitrary program-by-name is M8 and needs a validated `copy_from_user` name (a spawn argument is a new attack surface, held off deliberately). The capability model — *which* principals may spawn *what*, plus inheritance/grant semantics — is U5/U6. QEMU exercises the whole reap round-trip end to end (the waker is a scheduler post, not the timer): `:: M7: parent spawned child pid=<p>, waited, child exited status 0 -> PASS ::`, with every M6b/M6d/M6e/M6f/M6g verdict byte-identical (the child-exit accounting is routed by pid through the process table, never through the M6b/sentinel counters). **Metal-confirmed (real Pi 4, 2026-07-04):** `:: M7: parent spawned child pid=41, waited, child exited status 0 -> PASS ::` on silicon — the child loaded off the real card via the EMMC2-first path QEMU cannot exercise (`SD card @0xfe340000 — 15193 MiB, CSD v2`), and the parent's blocking `sys_wait` was woken by the child's scheduler post and reaped it under a live timer (EL0 preemption live, `IRQs-taken-at-EL0=23`), with 0 unexpected faults / 0 FAIL lines and the whole prior battery green (M6b `exited=1 killed=3 PASS`, M6d ×3, M6f ×3, M6g PASS, CAPSTONE 6/6, EL=1/54 MHz).
- [x] Per-process handle table + owner-scoped reaping (U4, 2026-07-04, QEMU-verified; no metal this arc — fully QEMU-verifiable scheduler/syscall logic) — evolves M7 into the ownership substrate. `SYS_SPAWN = 8` now installs the child into the *spawner's* per-process handle table and returns a small **handle index** (not the raw pid); `SYS_WAIT = 9` takes that **handle**. The table is a static, const-init `HANDLES[[AtomicU64; 8]; USER_SLOTS+1]` keyed by the caller's **ASID** (read from `TTBR0_EL1[63:48]` synchronously in the SVC handler — the caller's root is live there); `PROCS` stays keyed by pid (exit-accounting control blocks) while `HANDLES` is keyed by ASID (the spawner's private namespace of child capabilities). **Honest scope — this is STRUCTURE, not yet a CHECK:** the per-process handle table now holds child-process handles and **reaping is owner-scoped BY CONSTRUCTION** — a task can only reap children whose handles are in ITS table, so the M7 review note (any EL0 task could `sys_wait` any pid) is folded structurally — **but there is NO capability CHECK yet.** The capability model proper — handles-as-capabilities with grant/attenuate/revoke, routing resource syscalls (e.g. `sys_write`) through the table, and bandy handle-transfer — is **U5**, which adds its check at *exactly the handle lookup this arc builds*. `sys_write` is deliberately **left as the `fd==1` path** (routing it through the table now would force seeding a table for every existing EL0 writer for no capability benefit — a STOP tripwire). No new syscall number, no name/path argument to `sys_spawn` (that is still M8), no new scheduler primitive; the child bytes remain the same size-bounded **untrusted** on-disk program as M6g/M7 (no signature/allowlist — the shared code-signing item still gates the load). Resource bounds stay fixed (a 4-entry process table + the 8-slot pool return `-EAGAIN`; the 8-slot-per-process handle table likewise). Evidence — the demo proves the isolation the structure gives: a parent (`el0-u4parent`) `sys_spawn`s two children and reaps **both by handle**; an ownership negative (`el0-u4orphan`, its own slot/ASID) calls `sys_wait(0)` on an Empty handle in its OWN table and gets `-ECHILD` — same handle *index* 0, different tables, different outcomes: `:: U4: process model — parent reaped 2 children by handle, non-child sys_wait -ECHILD (per-process handle tables) -> PASS ::`, with every M6b/M6d/M6e/M6f/M6g verdict byte-identical (child-exit accounting stays pid-keyed through `PROCS`, never the handle or the sentinel counters).

#### aarch64 W^X map audit (H1, M6c — report only; WXN not enabled)

Walk of the EL1&0 boot page tables as built in `arch/aarch64/boot.rs` (`build_l1`,
`protect_user_code`; TTBR0_EL1 → one L1 of 1 GiB blocks, with L1[0] demoted to L2_USER/L3_USER for
the 4 KiB EL0 window). `AP[7:6]`: `0b00` = EL1-RW/EL0-none, `0b01` = EL1+EL0 RW, `0b11` = RO at both
ELs. `UXN` = bit 54 (EL0 execute-never), `PXN` = bit 53 (EL1 execute-never).

| Region (VA == PA) | Descriptor | Attr | AP | EL1 | EL0 | UXN/PXN | W∧X? |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 0–1 GiB general RAM (L2_USER blocks + L3_USER pages outside `USER_REGION`) | 2 MiB block / 4 KiB page | Normal | `0b00` | RW+X | — | 0/0 | **yes (EL1 RWX)** |
| `USER_REGION` code page `[0x100000,0x101000)` after `protect_user_code` | 4 KiB page | Normal | `0b11` | RO, no-X | R+X | 0/1 | no |
| `USER_REGION` data/stack `[0x101000,0x104000)` | 4 KiB page | Normal | `0b01` | RW, no-X | RW, no-X | 1/1 | no |
| 1–2 GiB RAM (L1[1]) | 1 GiB block | Normal | `0b00` | RW+X | — | 0/0 | **yes (EL1 RWX)** |
| 2–3 GiB RAM (L1[2]) | 1 GiB block | Normal | `0b00` | RW+X | — | 0/0 | **yes (EL1 RWX)** |
| 3–4 GiB Device (L1[3]) | 1 GiB block | Device | `0b00` | RW, no-X | — | 1/1 | no |

Transient: the code page is a data page (`0b01`, UXN=PXN=1, RW no-X) during the blob copy, then
`protect_user_code` flips it to the row above — so it is never W∧X, at either EL, at any point.

Since M6d the two `USER_REGION` rows are also **non-global (`nG=1`)** and replicated per task: the shared
window is the ASID-0 boot context, and up to 8 per-task slots (`boot::alloc_user_slot`, ASID 1..8) map the
same two VAs to their own frames with identical AP/UXN/PXN. The W^X properties of both rows are unchanged
(nG affects only TLB ASID-tagging, not access permission); the VAs shown are illustrative and shift with
the kernel image size (the pool adds ~224 KiB BSS). Kernel rows stay Global (`nG=0`).

**Every EL0-reachable page already satisfies W^X**: the user code page is R+X but read-only, and the
data/stack pages are RW but execute-never. The only W∧X coincidences are in the **kernel's own coarse
RWX identity RAM** (0–3 GiB, `AP=0b00`, PXN=0): the kernel image `.text` (which must be executable)
shares one RWX attribute set with the heap/stack/BSS/data (which must be writable).

**SCTLR_EL1.WXN feasibility.** With `WXN=1` the EL1&0 regime forces "writable ⇒ execute-never":
EL1-writable regions become PXN, EL0-writable regions become UXN. The EL0 window is unaffected (the
code page is not writable at either EL; data/stack are already XN). But the kernel executes from the
`AP=0b00`, PXN=0 identity RAM above — under WXN that RAM becomes EL1-non-executable and the next
kernel instruction fetch faults, so the kernel cannot boot. Enabling WXN therefore requires FIRST
splitting the identity map into a read-only-executable kernel text/rodata region and RW-execute-never
data/heap/stack/BSS regions (a linker-symbol-driven map, mirroring the 4 KiB EL0 code/data split M6b
already performs). That refactor is a separate, review-gated change; **WXN is not enabled in M6c.**
